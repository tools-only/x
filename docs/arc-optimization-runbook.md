# Agent 机制诊断与自主调优手册

用途：供开发 Agent 从真实任务行为中发现问题、优化机制、设计实验并决定是否保留改动。适用于 ARC 等需要探索规则、持续决策和自主构建 harness 的任务。

在本项目使用时，以 [development-workflow.md](development-workflow.md) 为开发与证据标准。所有规章和评测记录留在开发侧，**不得将本手册、开发模板或 AGENTS.md 注入任务 Agent 的常驻上下文**。

## 1. 调优目标与分析原则

目标是提高 Agent 在给定资源下完成任务、获取有效认识和适应变化的能力。

| 分析原则 | 执行方法 |
| --- | --- |
| 任务结果优先 | 先核对任务完成、动作、时限和成本，再用组件和调用解释原因。 |
| 追查因果链 | 沿观察、表示、解释、假设、实验、反馈、更新逐段查证；定位最早有证据的断点。 |
| 审查机制负担 | 核查限制的必要性、当前依据和副作用，比较更简单的替代方法。 |
| 检查竞争是否真实发生 | 比较候选是否跨越不同解释框架、能否预测不同结果、是否实施了区分实验及据此更新。 |
| 促进 self-harness 转化 | 查看重复认知工作是否被沉淀为可复用能力，以及后续是否产生实际帮助。 |
| 区分能力生产与自主使用 | 鼓励扩充组件库，保持低成本创作路径；组装、使用、修订、撤下由 Agent 按任务需要决定。 |
| 坚持项目与解题方法的边界 | 通用机制提供执行、存储和生命周期；ARC adapter 提供领域原始数据与低级接口；Agent 创作派生分析。 |
| 优先修复阻断项 | 持续 length、上下文膨胀、工具不可达、反例写入失败尚未解决时，先诊断这些断点。 |
| 使用真实实验反复纠正方案 | 本地测试只证明相应功能；实际采用和任务收益要回到真实 provider/ARC 日志。 |
| 持续监测但保持实验完整性 | 运行中记录问题；正常实验结束后修改下一候选。异常停止按预先规则处理。 |

核心原则：**让机制减少 Agent 从证据到有效行动的负担，并用任务进展验证；把科学判断留给 Agent，把重复手续交给程序。**

## 2. 启动与授权：每次续跑先恢复事实

执行者首先读取当前目标、适用开发规范和唯一变更记录。涉及观察压缩、adapter 边界或研究职责时，按需查阅 [deferred-research-todos.md](deferred-research-todos.md)，仅提取与当前命题相关的未决问题。

从已有材料恢复以下内容，仅补缺失项：

- **工作范围**：只分析、允许实现、允许真实实验，或允许持续迭代；目标结果和停止条件。
- **现场**：工作区、分支、共享修改、正在运行的实验、归属、冻结版本、最近已确认的环境动作。
- **预算**：当前适用的总时间、总 token、动作、并发等约束，已用量及在途未知量。所有参与者计入同一授权口径，组织层级不产生额外额度。
- **配置**：provider/model、实际请求中的 reasoning 配置、观测模态、已启用机制和组件版本。
- **汇报**：用户指定的频率、内容、时区，以及是否已有可持续运行的监测设施。

配置以实际请求和环境为准，不仅检查界面标签或启动参数。遵守当前能力与预算约定，不以默认值静默改变机制开关，不因续跑重新授予预算。组件的局部成本应结合任务贡献评价。

已授权的必要工作自动继续，不重复索取确认。缺少付费实验授权或必要边界时，先完成独立可做的日志分析、候选实现与检查，再只询问缺失部分。用户只要求分析或手册时，不启动新实验。

**启动完成条件**：能明确回答“当前做什么、基于哪个版本、哪些运行属于本任务、什么时候停止、下一步是否已授权”。

## 3. 自动执行主循环

| 状态 | 执行动作 | 完成条件与下一状态 |
| --- | --- | --- |
| 恢复现场 | 核对授权、版本、进程、动作和已存记录；复用在途实验 | 无重复启动、预算或动作歧义；进入取证 |
| 取证 | 用真实日志重建关键事件及实际 provider 输入输出 | 观察、解释、未知分开；进入诊断 |
| 诊断 | 按第 4 节定位最早断点，检查竞争解释 | 得到可证伪的主要原因；进入设计；证据不足则做最小诊断 |
| 设计 | 比较删除/复用、接口简化、提示调整和新增机制 | 明确一个主要因素、减负路径、负例及预算；进入实现 |
| 实现 | 在适当隔离分支或工作树修改，保护其他会话的改动 | 相关检查通过、候选与协议可审阅；进入实验 |
| 实验 | 在授权范围内冻结候选，启动真实 ARC/provider；按第 6 节监测 | 自然结束或命中预设停止条件；进入评估 |
| 评估 | 对账、查语义利用、检查反例处理、比较任务与总成本 | 按第 7 节决定保留、修订、撤下或证据不足 |
| 继续或交付 | 在同一记录写入决定、下一因素和剩余预算 | 目标已达成则交付；仍有授权和可判别检查则回到诊断 |

有界伪代码：

```text
恢复当前合同与现场
如果已有本任务运行：接管只读监测，不重复启动
while 目标未达到 且 当前授权允许下一步 且 预算可覆盖下一步与收尾:
    核对 canonical 事件、实际配置及已完成/未知成本
    定位最早断点；保存观察与竞争解释
    如有未修复的确定性阻断：优先复现并修复
    否则：选择一个最有机会改变任务结果的主要因素
    复用唯一变更记录，预定义反证、比较条件和停止规则
    实施最小候选，完成相称检查，冻结代码与配置
    若允许真实实验：执行并监测；结束后按预定标准评估
    否则：交付当前证据层级和待验证项
    根据证据保留/修订/撤下；没有新因素或新诊断价值则不重复付费跑
持久化终态、在途状态、未知成本及下一可执行检查
```

调度器只推进机械步骤；诊断、假设取舍和收益判断由获授权的开发 Agent 完成。脚本不能用关键词或组件计数代替这些判断。

## 4. 诊断顺序与分支

### 4.1 执行可信度与运行稳定性

先对齐 runner、bridge、trajectory、provider usage 和最终 summary。检查实际动作是否完成、日志是否重复/缺失、源码是否漂移，以及 length、超时、空输出、取消分别发生在哪个请求主体。

环境动作结果未知时保存现场并核对 bridge，不能向同一环境盲目重发。独立重启是新样本，保留旧失败与未知成本。summary 的 `passed`、`errors=0` 不能替代逐层检查。

持续 length 或不完整工具调用：先检查实际 payload、输出额度是否包含 reasoning、续接是否保留上下文与调用状态、是否误执行重复副作用。保持用户要求的推理配置；不能以关推理换取表面稳定。

### 4.2 上下文与机制施加的负担

按实际请求测量：system、工具 schema、memory、历史、Skill 输出、观测、Critic、重试与同一决策内重读。字符、token、reasoning、缓存和墙钟分别记录。

优先采取以下方向，并验证后续行为：

- 将不常用工具和创作说明渐进暴露，保留低成本发现、加载和恢复路径。
- 将完整持久知识与当前工作集分开；保留反证、适用条件和未完成实验，按需恢复原文。
- 将重复计算交给 Agent 自创组件；将事务、装配、记账等机械工作合并执行。
- 将最终交付长度与生成该交付所需的推理预算分开。

新增或保留任一硬限制时，查明其来源、解决的真实问题、当前依据、误伤和替代方案。权限、总预算、版本及环境完整性检查保留；展示预算不能直接变成少量假设的存储上限。拒绝反例更新、强制删除知识、工具恢复不可达，都作为机制缺陷单独评估。

### 4.3 观察、表示与认知模型

沿以下链条找断点：

```text
原始观测 → 可见表示 → 对象/关系解释 → 规则与目标假设
        → 区分实验 → 预测反馈 → 认识更新 → 后续策略与行动
```

检查 Agent 当时实际看到什么，不使用开发者后来获得的真相指责其“应该知道”。像素变化、工具计算值和自然语言解释分别验证；代码可执行、返回 JSON、被列为 ok，都不能证明解读正确。

跨关、RESET、地图原点变化、新对象出现或版本变化时，核对旧组件的适用条件。区分未识别失效、识别但未修订、修订失败、修订未装配、结果未利用。有效措施应针对实际断点，而非统一再加提醒。

### 4.4 竞争性假设与实验质量

开发 Agent 在关键失败处审阅：

1. 候选是否只是同一解释的参数变化，还是包含不同机制？它们是否共享未经验证的前提？
2. 现有观察能排除什么？假设的前提是否真的满足？一个必要条件失败或成立，分别能支持多强的结论？
3. 哪个可执行实验使候选产生不同预测？是否可以先复用历史证据，减少无信息重复动作？
4. 反例产生后，存储、工作集、策略依据和后续行为是否一致更新？

反证的强度与被检验命题一致：推翻充分条件不能自动否定其必要性，推翻一个解释不能自动证明另一个解释。

候选数量、动作变化、同一策略 ID 的保留都不是充分指标。记录首个关键反例到有效区分实验的耗时、动作和总成本；截止前未完成下一轮更新，与获得反例后仍坚持旧结论，分开归因。

### 4.5 Self-harness 的生产、组装和利用

逐段核对机会：

```text
实际需要 → Agent 识别 → 投入 → 候选 → 保存/暴露/组装
        → 语义使用 → 反馈 → 保留/修订/停用
```

覆盖 skills、tools、memory、prompt、subagents 的能力，但按实际任务评估适用机会。没有某类组件时，先找是否存在值得转化的工作，再查能力发现、接口摩擦、运行成本与结果可达性。组件数和调用次数不作为任务奖励。

能力生产与使用可分离，但路径应简短。保留创建、校验、试用等可合并操作；默认保存并选择的现有便利性不能被拆成多轮必选手续。扩充组件库应允许选择性组装、合理不使用、复用旧组件和及时放弃。

通用 harness 负责执行、存储、版本和装配；adapter 提供领域原始数据与低级接口；Agent 编写对象识别、跨帧分析、目标推断和预测等派生方法。低级领域库应保留 adapter 归属，通用机制不携带任务答案。

### 4.6 台账与 Critic

台账保存真实事件及 Agent 声明，帮助审阅前提、预测和反馈；它不自动判断自然语言假设的真伪。

Critic 评审对象是策略、假设、目标模型和证据质量。可指出遗漏解释与区分实验的性质，由游戏 Agent 决定具体动作。触发以新证据、策略变化、关键反例及实质停滞为依据，避免仅以动作次数机械复读。

按下列阶段分别记录结果：

```text
触发 → 请求 → 有效正文 → 证据核验/解析 → 送达
     → 父 Agent 考虑 → 后续策略或实验变化
```

空正文、reasoning 用尽输出额度、解析丢失、过时结果分别计为相应断点。触发成功与请求结束均不算完成 review。保留推理，按实际 provider 行为设置有界计算和恢复；给父 Agent 的短报告不等于只能给 Critic 极小总输出预算。

## 5. 从诊断到候选：一次改变一个主要因素

默认优先顺序为：执行完整性与稳定性 → 阻碍学习/纠错的机制 → 有效观察与规则学习 → self-harness 的复用和修订 → 吞吐与成本优化。若证据显示另一断点决定当前结果，可调整顺序并说明。

在现有计划中复用 [变更记录模板](templates/meta-harness-change.md)，写清：真实事件、主要命题、减少的负担、改变因素、预计行为、反证、相关负例和有界实验。仅记录与本次变化有关的内容，不生成重复表单。

选择方案时先比较删除限制、合并往返、复用现有接口与修改展示，再考虑增加提示、字段、评审或 worker。需要新增机制时，明确谁推进、何时失效、如何恢复，以及增加多少常驻内容和决策步骤。

先修确定性缺陷并做相称验证；之后再花真实实验预算验证行为。已授权的完整集成方案可以作为整体候选，但后续不能将收益归因于其中某个未隔离因素。

## 6. 评测设计与监测

### 6.1 先定义可证伪命题

每轮在唯一变更记录中写清：

> 在【适用情境】下，改变【主要因素】，减少【具体负担】，使 Agent 出现【可观察行为变化】，进而改善【任务主指标】。如果【反证或可接受退化被突破】，则修订或撤下。

同时说明合理不使用的情境、相关负例和恢复方式。评测要求与改动范围相称，不把开发表单变成任务 Agent 的义务。

### 6.2 按问题选择评测手段

| 手段 | 适合验证 | 结论边界 |
| --- | --- | --- |
| 静态检查、单元或协议测试 | 输入契约、事务原子性、错误处理和边界行为 | 不证明模型自主采用或任务改善 |
| 历史日志重放 | 表示准确性、已知反例、上下文保留、计算一致性 | 不证明未执行环境动作的收益 |
| 确定性完整链路检查 | 接口、装配、动作边界及后续回合的可达性 | 不证明真实 provider 的采用或解题质量 |
| 真实模型有界诊断 | 特定关键转移、调用修复、结果交付和利用 | 显式引导成功不等于普通自主行为 |
| 普通真实任务运行 | 自主选择、能力转化、纠错和实际进展 | 单次成功不等于稳定改善或单因素因果 |
| 匹配对照、重复运行及保留任务 | 净收益、波动和迁移能力 | 结论限定在已测模型、环境与预算 |

先用低成本检查排除确定性缺陷，再将真实实验预算用于行为和收益的不确定性。已有检查通过后，仅因新改动、失败或未解疑点扩大测试。

### 6.3 保持可比较与可复现

启动前核对当前协议：实际模型/provider、推理 wire、模态、场景、版本、初态、预算、比较器、引导条件和停止标准。冻结代码与配置；不将运行中的共享工作区修改算入同一个干净实验。

性能比较按相近条件安排独立样本，样本量根据基线波动和可承受预算预先选择。证据不足时报告不确定，不反复试到满意为止。用于调优的任务归入开发集，迁移验证使用未参与调优的保留任务。

### 6.4 运行监测

采样与用户汇报分开，频率遵循当前任务约定，重大故障及时报告。每份摘要包括：

| 内容 | 需要回答的问题 |
| --- | --- |
| 任务进展 | 完成多少关、当前关、已确认动作、RESET、剩余预算？ |
| Self-harness | 新增/修订/停用什么、何时语义使用、是否改变解题？ |
| 台账 | 最新关键假设、反例、待区分解释、更新是否成功？ |
| Critic | 触发、有效交付、送达、利用分别如何？ |
| 稳定性与成本 | 主请求和其他请求的 length/超时、长决策、已记录与未知用量？ |
| 后续 | 当前结论、待运行结束后优化的问题及证据位置？ |

运行中观察到性能偏低或策略不理想，记录问题并让冻结实验按协议结束。只有命中已定义的完整性、安全或资源停止条件，或用户明确要求时，才提前停止。停止影响可比性，保留截断样本。

持续运行须有实际可用的调度/监测设施和可恢复状态；如果只存在当前交互会话，明确监测覆盖范围，不宣称会话结束后仍会定时汇报。

## 7. 指标、验收与决策

### 7.1 指标目录与测量口径

每轮选择与命题直接相关的最少指标集合，预先确定主指标、可接受退化和停止标准。以下为可选目录，不要求全部采集，也不设置脱离任务的统一数值门槛。

| 层面 | 指标及口径 | 判读方法 |
| --- | --- | --- |
| 任务结果 | 固定预算完成率/关卡数；完成所需动作、时间和总成本 | 主要验收依据，未完成样本不得被排除 |
| 稳定性 | 各类请求可用完成率、length/超时率、恢复成功率、重复副作用 | 完成包含可交付正文或完整调用，按请求主体分列 |
| 学习效率 | 到有效规则的动作/时间/成本；关键反例到区分实验及实际修订的延迟 | 有效性需证据支持，未到达事件标记为截止而非零 |
| 实验质量 | 无新信息重复实验、候选预测分歧、关键预测正确性、反例处理 | 恒真或无关预测单列，命中率不单独代表学习质量 |
| 上下文负担 | 各部分输入 token、同一决策重读、恢复往返、峰值上下文 | 同时核查反证、条件和计划的保留及后续利用 |
| Self-harness | 适用机会到语义使用的转化、首次获益延迟、修订与复用 | 分母为经证据审阅的适用机会，合理不使用单列 |
| Critic 效果 | 有效报告/调用、送达率、实质新意见、被考虑及后续改变 | 采纳不必然正确，合理拒绝正常，另验任务效果 |
| 总资源 | 所有参与者的输入、输出、reasoning、缓存、成本、墙钟与管理轮 | reasoning 已含在 output 时不重复相加，并发耗时不直接求和 |
| 适应性 | 场景变化后失效识别、修订/停用延迟、任务恢复 | 区分未识别、已识别未处理、处理失败和结果未利用 |

比率同时报告分子、分母、未知项与样本范围；无适用机会标记为不适用。字符缩短、token 减少和延迟下降分别测量，不能相互替代。辅助指标改善不能代替任务目标。

### 7.2 四层验收

| 层级 | 通过所需证据 | 结论边界 |
| --- | --- | --- |
| 功能正确 | 目标行为及相关负例、失败恢复符合预期 | 所测条件下机制可用 |
| 全链路可达 | 实际运行路径到达后续回合，输入输出语义可核验 | 能力可达，不等于自主采用 |
| 自主采用 | 普通真实运行中识别机会、选择能力并实际利用 | 所测情境下的行为，不等于净收益 |
| 净收益 | 可比较实验中主指标达到标准，资源与退化符合边界 | 报告效应、波动和限制，不超出样本泛化 |

每层独立标记通过、失败、不确定或未验证。合理放弃是正常判断，但不计为组件采用成功。

按开发流程分别报告功能正确、全链路可达、自主采用、净收益。需要旧 ARC 路径五类组件完整闭环声明时执行 [development-workflow.md](development-workflow.md) §3 对真实链路、语义结果和 length continuation 的验收；普通局部改动按范围验证，不把完整矩阵变成每次小改的额外负担。

### 7.3 依据结果选择下一步

| 结果 | 自动后续 |
| --- | --- |
| 功能失败或链路断开 | 定位并修复；保留失败；不启动同缺陷的大规模性能比较 |
| 功能可用、Agent 未采用 | 区分无适用机会、未识别、投入太贵、接口摩擦、不可达与合理放弃 |
| 已采用、语义错误 | 审查组件算法、适用范围、反馈和修订路径 |
| 语义正确、任务无收益 | 审查能力是否解决真实瓶颈；撤下或更换主要因素 |
| 任务改善、总成本或配置不可比 | 保留探索性结果，净收益标为不确定 |
| 达到预设目标且证据充分 | 保留候选，交付范围、限制与可复验材料 |

baseline 被提前停止、provider/推理配置不同、环境失败、源码漂移或多因素变化时，显式降低比较结论。任务改善但成本退化时，按预先定义的取舍判断，不事后更换成功标准。

停止依据为当前目标完成、用户停止/暂停、预算或时限到达、必要外部条件缺失，或已没有能在授权范围内完成的可判别检查。不得反复重跑同一候选直到偶然成功；需要重跑时记录新因素、已诊断基础设施故障或明确的不确定性检查。

## 8. 持久化、续跑与交付

复用一份变更记录作为语义真值源，原始日志保持独立。调度或长任务需要 checkpoint 时，只保存导航和执行状态；以下是字段示意，**不是新增 runtime schema 或游戏 Agent 填表要求**：

```yaml
objective_ref: 当前用户目标或合同
phase: diagnose | implement | evaluate | monitor | done | waiting
record: 唯一变更记录路径
candidate_ref: 分支/commit/冻结目录及哈希清单
runs: [运行目录与归属；进程身份；状态]
authorization_ref: 实现/实验范围及当前预算来源
budget_status: 已用、剩余、在途未知；绝对截止时间
next_step: 下一项可执行工作或所缺外部条件
last_report_at: 带时区时间
```

恢复时重新核实进程身份、日志增长和动作完成情况，不能只相信旧 PID、checkpoint 或 summary。已完成工作不重做，未完成流不填零，不重新授予预算。

交付写清：主要发现、改动、真实结果、四层证据、未知项和下一检查。给出可点击材料。报告方法改进时说明它减少了谁的什么负担，以及哪些行为证据支持结论。

## 9. 执行入口

以下指令供已授权的调优任务调用：

> 按 `docs/arc-optimization-runbook.md` 执行当前 ARC 优化任务。先恢复最新用户合同、适用开发规范、现有运行和唯一变更记录，再从真实日志定位最早断点。保持用户约定的推理、台账、Critic 和机制开关；优先解除阻碍任务进展的上下文与接口负担，保持 Agent 对假设、派生分析、组件创作和组装的自主权。在当前授权预算内自动完成诊断、实现、验证、冻结、真实实验和评估，每轮改变一个主要因素；按约定频率汇报，保留失败和未知成本。到达停止条件后保存续跑状态，分别报告功能、接线、采用和净收益。授权不含真实实验时，完成独立可做的工作并列出待验证项。

## 10. 少量应用示例

| 现象 | 诊断与调优方法 | 验收重点 |
| --- | --- | --- |
| Critic 请求结束却无报告 | 区分推理耗尽额度、解析丢失与送达失败；分开计算预算和交付长度 | 有效正文、后续送达及判断质量，保持所需推理能力 |
| 加入新假设时反例更新被拒绝 | 检查存储上限是否被误用为工作集控制，简化原子修订与展示 | 反例保存并影响后续决策，同时常驻上下文受控 |
| 场景变化后旧 Skill 输出失真 | 定位识别、修订、装配或利用断点，缩短修订/停用路径 | 后续使用适用版本，失效结果不再误导决策 |
| 多个候选始终无法推进 | 检查是否共享错误前提，选择能产生不同预测的实验 | 获得可区分证据并实际更新，而非候选数量增加 |
