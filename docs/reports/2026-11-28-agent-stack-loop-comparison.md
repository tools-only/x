# Agent 四层架构与当前分层 Harness 的对照

2026-11-28。代码口径为本地工作树，分支 `codex/qwen27b-cognitive-harness`，基线 `be34208`，包含尚未提交的修改。分析对象是当前 layered ARC 执行路径。此前撤销的可执行 loop 原型不计入现有能力。

## 一、原文的四层架构

原文按工程师可以改变的对象分层。Harness 执行循环；循环的每一步组装 Context；一次调用的 Context 包含 Prompt。这个嵌套关系解释了为什么对同一个失败，四种调整会有完全不同的结果。下表沿用原文的认证模块迁移案例，例子为中文转述。[推文](https://x.com/beamnxw/status/2119806541821776215) · [文章](https://x.com/i/article/2119469016557187072)

| 层 | 核心与工作单位 | 迁移认证模块到 Clerk 的例子 | 如何定位故障 |
|---|---|---|---|
| Prompt | 一次模型调用。明确意图、约束、角色与输出要求 | 说明迁移目标，要求已有测试通过 | 已拿到正确材料，却误解交付要求，可先改指令 |
| Context | 本次调用可用的全部信息和能力。决定检索什么、何时载入、保留多少历史、暴露哪些工具 | 加载项目测试命令和认证文件索引，按需取相关文件，只提供编辑和测试所需工具 | Agent 理解任务却猜错文件或测试命令，应查材料是否进入了这次调用 |
| Loop | 一次自主运行。定义目标、重复体、判定依据、继续和退出条件 | 每一轮检查迁移结果，将失败反馈带入下一轮，测试确认完成才交付 | Agent 宣布完成但测试仍红，应查失败结果能否驱动下一轮，以及谁有权判定成功 |
| Harness | 承载上述逻辑的执行系统。落实工具调用、隔离、重试、检查点、上下文装配和退出规则 | 编辑后运行 lint，处理瞬时 API 故障，保存检查点，对生产环境修改设置人工关口 | 即使循环设计正确，测试命令未执行、回执丢失或重复写入，仍会使结果失真 |

图中的 completion check 与迭代、时间、成本、无进展等停止条件承担不同职责。前者提供成功证据，后者决定继续投入是否合理。两种情况都可能结束运行，但只有前者支持“目标已满足”。图中一次 pass 包含收集信息、行动和验证，因此一次模型调用或一个环境动作都不能天然充当一次 iteration。[文章与原图](https://x.com/i/article/2119469016557187072)

## 二、当前架构、执行机制与对应关系

项目有两个分类维度。L1–L5 描述正在补足的解题能力；Memory、Tool、Skill、Prompt、Subagent、Orchestration 是承载这些能力的六类组件。同一个 L4 策略可以通过 Prompt 被表达、通过 Context 被呈现、在 Loop 的分支上发挥作用。下表按当前演化器实际审查的能力归纳。[演化系统提示](../../demo/arc_layered_extension.ts#L162) · [组件定义与版本存储](../../demo/arc_layered_components.ts)

| 能力 | 当前机制 | 对应原文 |
|---|---|---|
| L1 感知 | 从帧、局部差异、工具读数中提取与决策相关的现象 | Harness 取得观测；Context 把选中的证据带给模型 |
| L2 轨迹与探索 | 利用动作历史、重复尝试、失败路径决定还值得探索哪里 | 轨迹属于 Context；停滞引发审计属于 Loop |
| L3 状态与因果建模 | 用局部假设、Memory.verify、只读工具或可选预测器检查状态转移 | 规则属于 Context；宿主执行检查属于 Harness；反证触发审视属于 Loop |
| L4 策略与方法 | 策略卡记录候选目标、进度、下一探针和证伪条件；Skill 承载可复用步骤 | 已表达 Loop 的目标和候选方法。呈现卡片、按需读取 Skill 是 Context 机制 |
| L5 纪律与编排 | Prompt 规定决策纪律；Orchestration 调整探索、利用、重构模式及载体优先级 | 指令属于 Prompt；面板排序属于 Context；可修改的模式分支是局部 Loop 策略 |

**主任务循环。** Python runner 启动行动段，宿主取得环境回执并检查胜利、预算和错误，再决定是否继续。这里已经有自主重复和由环境确认的任务级 completion check。一次行动段是调度单位，是否构成有意义的科学试验仍由任务决定。[主循环及停止条件](../../src/autoresearch_pi/arc_layered_e2e.py#L339)

**演化审计循环。** 死亡、过关、反证或停滞等边界触发审计。演化 Agent 读取轨迹和组件反馈，选择检查、修订或结束；工具回执可以驱动下一轮。组件修订后有版本，并通过后续上下文或工具调用回到主任务。审计结束说明本次审计收尾，组件净收益要靠后续任务证据检验。[审计输入](../../demo/arc_layered_extension.ts#L826) · [审计运行与退出](../../demo/arc_layered_extension.ts#L1638)

**Orchestration 的控制权限。** 修改死亡阈值能改变何时切入 REFRAME；渲染器随模式改变工具、Skill 和子 Agent 的呈现顺序。handoff 和 batch_hint 会影响模型看到的建议，实际是否 consult、是否按建议执行一批动作仍由主 Agent 决定。因而可以分别验证“模式切换”“入口出现”“调用发生”“行动改善”，四者不能共用一个计数。[模式推导](../../demo/arc_layered_extension.ts#L573) · [面板组装](../../demo/arc_layered_extension.ts#L2185)

**真实运行给出的证据边界。** su15 第 2 关的策略卡从规避危险坐标转向检查三次死亡前后的计数，随后主 Agent 确实回查了历史帧。它证明策略修订能够改变下一次分析操作。该局最终 224 个动作，通过 1/9 关，因预算耗尽结束。这个案例可以验证策略采纳和外部停止判定，无法单独证明 Agent 修改了循环控制流，或带来了过关收益。[策略 v7](../../runs/arc-local-su15-20261128-173946/harness/components/memory/strategy_card/v7.json) · [策略 v8](../../runs/arc-local-su15-20261128-173946/harness/components/memory/strategy_card/v8.json) · [会话](../../runs/arc-local-su15-20261128-173946/session.jsonl) · [最终结果](../../runs/arc-local-su15-20261128-173946/summary.json)

## 三、暂时缺少或仅部分匹配的机制

| 对照点 | 当前已有 | 具体缺口 |
|---|---|---|
| 可定义的 iteration | 宿主有行动段，审计有模型轮次，Skill 可描述多步方法 | Agent 尚不能把“一次有效试验”定义为由运行时跟踪的工作单位。只读观测可能完成一次试验；执行了动作也可能没有获得证据 |
| 子目标 completion check | ARC 有过关回执，Memory.verify 能判断局部规则，策略卡能陈述成功信号 | 尚无通用关联把“本轮产物、检查器、判定结果”绑定到同一子目标。局部预测成立，不一定代表目标推进 |
| 可修订的控制流 | Agent 可改模式阈值、策略卡、Skill 和交接建议 | 尚不能普遍定义“若证据有效但未达标，则保留结果并改候选；若测量无效，则修复评估后重试”，并由宿主执行新版分支 |
| 无进展与成功的区分 | 有 idle、重复、停滞、死亡和预算保护 | 局面变化可以没有目标进展，负实验结果也可以带来认知进展。现有稳定推进判断参考本关 changed/new 等统计，未直接读取 L4 的任务进度判据 |
| 对自改效果的归因 | 已记录组件版本、注入、调用、动作和任务结果 | 要证明 loop 被优化，还需将同类输入下的新旧分支、检查器回执及端到端成本关联起来。组件发布数和提示出现次数不足以支持这个结论 |

### 设计判断与跨任务检验

通用 Loop 策略可以复用现有分工：L4 定义目标及证据要求，L5 决定一次尝试包含什么、如何解释检查结果以及下一步转向哪里，Harness 执行、记录并落实外部预算。Agent 可以修订工作流；benchmark 的最终成功标准应保持独立，否则放宽自评条件也会表现成“提升”。

| 场景 | 合理的一次 iteration | 能检验 loop 自改价值的例子 |
|---|---|---|
| ARC | 完成一个能区分目标或机制假设的探针 | 同样观测到“对象移动、目标进展未知”，旧策略继续移动，新策略转去验证目标。由宿主记录分支，再由环境判定过关 |
| Auto-Research 类任务 | 完成一项有假设、对照和有效测量的实验 | 对照失效时先修评估；有效的负结果进入知识记录并换候选。比较达到同一研究验收标准所需的有效实验数与总成本 |
| OpenEvolve 类任务 | 生成候选、验证有效性、评估并决定是否保留 | Agent 将廉价正确性检查移到昂贵评估之前，观察相同评价器和预算下的有效候选数、最佳分数与耗时 |

后两项是设计例，不代表当前 ARC 路径已在这些 benchmark 上验证。最小可证伪标准分两步：先用同一份回执证明工作流修订改变了宿主实际执行的下一步，再在相同外部验收条件下比较质量与成本。前者检验控制流是否可演化，后者检验这次演化是否值得。
