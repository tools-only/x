1. 模块职责与边界

公开环境证据 → Pi 主 Agent：推理／计划／研究问题／组件内容／选择
                     ├─ task_harness → 确定性校验、路由、版本池、装配、回执
                     ├─ auto_research → broker／child → 结构化研究结果 → 主 Agent
                     ├─ delegate_task → 独立或预配置上下文 → 返回结果
                     └─ arc_action → ARC bridge／adapter → SDK 环境 → 新证据
组件使用与环境结果 → 主 Agent 评估／修订；需要时继续研究
主体承担什么不承担什么
主 Agent决定问题、解释证据、提炼方法；读取 creator 并撰写组件；选择装配；决定研究启动、实验动作与结果采纳。不能把读取、写入成功或 child 完成状态当作正确性证明。
Self-Harness runtime非 LLM 机制。规范化请求、检查结构与来源、调用原生写入器、保存版本、检查生命周期、投影装配内容、记录实际使用和评估。不从轨迹自动编造 Skill、工具程序、角色指令或研究结论；不替主 Agent 决定语义相关性。
组件 pool任务局部的版本化资源集合，包括历史、当前版本及状态。读历史与当前可用性分开。不是本轮已启用配置；pool 中 active 不意味着被选中。
装配主 Agent 声明精确组件版本和 prompt contributions；runtime 按声明投影或允许调用。不负责创造组件，也不自动把所有新组件启用。
Auto-Research child在授权的只读证据与工具上研究机制、表示、规划、方法或未决猜想，返回结果、反例、候选方法和实验请求。不直接写父任务组件，不执行 ARC 动作。研究不是创建组件的必经步骤。
Bridge／adapter／runner环境交互、执行编排与进程生命周期；公开状态与动作回执由环境边界提供。狭义 adapter 不应决定研究目标或编写组件。现有 Pi extension 仍混合部分 runtime 职责，全面拆分尚未完成。

2. 五类持久组件与 task_prompt

类型定位与适用内容载入／执行不应混同
system_prompt有明确作用范围、值得持续暴露的行为指导，例如对推断与观察的处理原则。父 Agent 撰写 segment，选入装配后进入系统指导投影。不是长期事实仓库，不宜保存当前坐标、关卡地图或单次路线。
Skill由 Agent 执行的流程：何时使用、读取什么、如何判断和操作、怎样停止或应对失败。单场景、未验证方法也有效。通过 skill-creator 撰写完整正文；入池、装配、focus/read 后由主 Agent 执行。实际遵循时引用精确版本。不是轨迹复述；不要求跨任务普适，也不要求先成功通关。
Pi Tool可执行计算或授权操作，把重复计算交给程序。tool-creator 撰写结构／程序；注册 Pi tool，通过支持的声明式程序或授权 implementation_ref 执行。不是 MCP。文字描述不能替代实现；不是任意 shell／任意代码执行授权。
Subagent可复用的独立推理角色、干净上下文或准备好的上下文配置。subagent-creator 撰写 instructions、tools、可选 context_recipe；装配后经委派路径执行。定义角色不等于启动进程；一次性独立推理可以直接 delegate_task，不必先造组件。
Memory有范围的事实、假设、计划内容及证据归属。真假与适用性允许后续修订。版本化 atom、作用域、可选 task_state／task_policy 投影与 activation。不是所有知识的唯一归宿；当前位置、最新 frame、剩余预算已有 runtime 状态，不宜重复固化为长期知识。
task_prompt（输出通道）当前任务上下文的装配结果，可来自 Memory、Skill、method、finding、validation、research report 等来源的精确版本。父 Agent 选择来源并给出 contribution 内容，runtime 投影。不是第六类持久组件，也不是 Memory 的同义词。review 中仍保留 task_prompt 分类用于兼容表达。

组件类型按执行需要选择，不按推理高低级排列。识别对象、解释目标、规划路径三个层次，都可能同时产生 Memory、Skill、Tool、研究问题或临时计划。

3. 从观察到能力：当前指导流程

  1. 识别操作机会：分析输入、操作、判断与结果，找出值得降低成本或提高可靠性的工作；成功、失败、新需求、重复工作都可能触发。
  2. 分离实例与方法：实例值和观察结果保留为证据或 scoped Memory；方法说明如何消费输入、转换、判断和产出。把不确定性绑定到受影响的步骤或条件。
  3. 形成可执行契约：表达触发条件、输入、操作、输出、停止及失败处理。未知可以成为显式测试分支，不必等全部机制查明。
  4. 选择载体：Agent 操作流程→Skill；已实现计算→Tool；独立上下文→Subagent；持续行为→system_prompt；事实或假设→Memory。先比较现有覆盖，再决定复用、修改或新建。
  5. 作者创建并使能：读取匹配 creator，提交完整候选；检查 native receipt；选择版本装配；读取或调用。
  6. 使用后修订：对比预期与实际结果，记录反例、成本、边界和后续检查；保留、改版、暂停适用或退役。
上述是面向 Agent 的工作流程，不是要求填满所有 method 字段的硬性入池表。没有“每关必须产出几个 Skill”、没有各类组件数量配额，也没有“必须先做研究”的条件。

两个可达创建入口

task_harness(action="change", changes=[...], decision={reason, expected, basis_refs}) 是主写入入口。语义候选经确定性分类落到原生 Memory／Skill／Tool／Subagent／system_prompt 写入器。create、update、reuse、retire 等操作的具体参数由当前接口披露。

task_harness(action="review") 的 create/update 条目若附完整 candidate，会在同次调用应用相同 change 实现并返回 application_receipt；只有意向而没有正文则为 pending_candidate_body，runtime 不补写内容。一个 review 每类型最多一个条目；同类型多资源可在一次 direct change 的 changes 数组提交，随后 review 用 reuse 引用多个结果。

4. 当前准入、结构与执行限制

下表区分当前硬性检查与方法指导。现有约束并非已经全部证明必要；本文不把它们描述为用户新增的要求。

位置当前规则性质／影响
通用写入主 Agent 写入边界；请求结构、名称、引用和版本需合法。先做 creator／内容预检，再执行 native mutation。来源与结构检查；不能据此声称整个多步骤执行具备任意故障下的事务回滚。

Subagent安全 name、用途、完整 instructions；显式 tools 字符串数组，[] 对纯推理有效；可选 context_recipe 必须合规。recipe 支持 checkpoint、最近 observation/action 数量、精确 inherit_harness_refs、output_contract、max_chars。当前数量范围0–100，字符上限80000，默认12000；这些是当前结构边界，不是质量门槛。
system_prompt安全 name、父侧非空内容、显式 scope 文本或 scope.statement。持续指导的范围声明；没有强制 creator 对应项。
可选 method如果提交，就规范化已提供字段；列表字段须符合规范，不能用任意对象冒充字符串列表。不要求完整档案；runtime 不补造方法论。creator 模板中的丰富示例不是全部必填。
Review合法 component／disposition、reason；create/update 要 next_use 与 validation；引用须存在。未提交类型被补为 runtime_default unresolved/defer。validation 文本只是拟做检查，不代表检查已经通过。默认占位不是主 Agent 主动拒绝创建。
装配与调用精确版本、当前 eligible、assembly CAS revision、必要依赖和调用权限。入池后的使能规则，与创建内容的语义价值判断分开。
支持性效果评估supported 需要关联精确组件版本的实际使用证据；单纯曝光不能支持 utility。评价声明规则，不应成为首次创建与试用门槛。复评目标自动绑定目前存在缺陷，见第8节。

5. 版本、候选池、装配与 runtime

资源引用形式为 kind:name@vN；creator 则使用 baseline_method 的 SHA256 引用。组件改版保留历史，更新需面向当前版本；历史可读不等于当前可选。依赖失效、作用域过期、退役等会影响 eligibility。

候选内容 → native 写入回执 → pool 中的精确版本
                               ↓ 主 Agent 选择
assemble(expected_assembly_revision, selected_resource_refs,
         prompt_contributions, decision)
                               ↓
系统／任务上下文投影；Skill 按需载入；Tool／Subagent 调用
                               ↓
真实执行证据 → 评估 → 新版本或退役 → 必要时重新装配
  • 装配 revision 独立于组件 version。CAS 冲突应读取当前 assembly 后重新判断，不应猜版本或盲目覆盖。
  • 没有装配时选择集合为空；装配跨轮保持，变化时才需重新装配。直接 arc_action 不要求先调用 harness。
  • prompt contribution 带可解析的 source_ref、正文及可选 priority、activation、depends_on_refs；如果来源是组件，也须在 selected 集合中。
  • basis_refs 记录历史依据；depends_on_refs 表示有效性依赖；supersedes_refs 表示显式替换。三者不能互换。
  • 选择仍有效但 activation 条件不满足时，可抑制投影。runtime 只执行声明的条件，不替主 Agent 判断“哪个知识最有用”。
  • 创建 Tool／Subagent 只是定义，尚需选择与实际调用。Skill 正文写入的是文本，不能把 [object Object] 当成可载入流程。

6. Auto-Research：问题持续性与父子边界

研究对象：对象控制、因果机制、目标条件、状态表示、约束解释、探索策略、规划算法、恢复规则、方法有效性等。轨迹是证据来源，不是研究目标的上限。结果可以是否定结论、未决问题、计划影响或实验请求，不必产出组件。

  1. 父 Agent 直接发起问题，或 review 形成 handoff。当前 handoff 优先采用 limiting_uncertainty，而非把 capability_opportunities 自动当成必造组件任务；未明确 kind 时可为 unspecified。
  2. 读取／使用 research-orchestration；说明可访问材料、可达阶段目标、预期可观测结果、局部检查和成本／停止条件。缺少信息可以缩小问题或说明证据缺口。
  3. 父 Agent 选择 blocking／non_blocking 路径启动，broker 负责子进程和结构化返回。proposed handoff 不会自己变成正在运行的研究。
  4. Child 在只读权限内提出并检验解释，报告证据、反例、不确定性、下一次区分实验。环境新动作仍由主 Agent 决定和执行。
  5. 父 Agent 对 next_experiment 检查当前状态与 as_of_event；唯一请求可通过 action decision 的 approve_research_experiment 接受；多个请求需选择精确 request_ref 与正的 approved_max_actions。
  6. 新动作和 observation 回流研究记录。eligible pending/failed 会话可 resume；已完成工作采用引用先前 run/report 的有界 follow-up，而不是把 completed 当成任意可 resume。
  7. 研究结果若值得转化，由父 Agent 读取对应 creator 并撰写候选。代码 router／adoption 处理结构化来源与原生应用，不授权 child 直接修改父组件。

研究完成或研究者同意主观点，都不会自动提高置信度；需要新的相关证据、反例处理或区分实验。持续研究与一次性 delegate_task 不同；保存的 Subagent 是上下文／角色配置，Auto-Research 是持续研究协议，两者也不等价。

7. Memory 的生命周期

scope当前绑定适合内容
task本次任务带控制模式条件的方向规则；不能据此声称跨任务 long-term memory 已实现。
episode当前 episode；公开 RESET 等边界改变实例当前尝试有效、重置后需重查的假设或约束。
level当前关卡实例；换关／重置改变绑定地图、当前关卡目标候选、地形信息。
state当前观测实例非常局部的知识；优先避免与 runtime 状态重复。

runtime 从公开执行边界机械绑定 task_ref／instance_ref，而不是从自然语言猜是否换关。scope 过期影响可用性／投影；日志中某条旧记录仍写 active，不代表当前投影仍有效。主动 retire 会留下新版本退役记录。失败模式、适用范围、成功模式可以通过组件内容、method 元数据、assessment 与 trace 记录，但不能声称已有自动完善所有这些字段的语义管理器。

8. 实际使用、评价与已知复评缺陷

trace 的主要连接是：观察引用 → 作者决策 → 组件精确版本 → 装配 → 曝光／调用／行动引用 → assessment。Skill 使用可在后续 arc_action.decision.basis_refs 标注版本；Tool／Subagent 调用有执行结果。效果结论为 supported、unsupported 或 inconclusive；结论范围是已观察使用，而非普遍真理或因果性能证明。

尚未修复的目标选择缺陷：assessHarnessEffect 的隐式候选只包含未评估过的 decision。新运行第20步引用了方向 Memory v1，但 direction 的 decision-1 已评估；省略 decision_id 的复评无法选中原目标，出现 supported 缺实际使用证据的错误。这不是第20步未引用版本。显式选择原 decision 是现有接口路径；自动选择仍需修复与回归测试。退役的“内容不再出现”也应与“组件被使用”分开评估，尚需专门核对。

因此当前不是可靠的自动持续调优系统：主 Agent 仍须提出评估与修订；有轨迹文件不代表语义反思已经执行，也不能把未来计划写成已实现能力。

9. ARC 运行、观察与复盘

  • 每个决策周期可包含分析、创建、研究和委派，最后以一个可用 arc_action 结束；当前公开 frame 已注入上下文。
  • 每5次成功环境动作生成增量 review 机会，每20次为 consolidation。两者是建议，不是阻挡行动的闸门；创建无需等窗口。
  • 换关、RESET、失败触发 whole-level review 相关流程；最终 terminal review 为只读。复盘应覆盖具体应用、浪费、机制、失败与下一次建议。
  • validation_window 是局部假设检查窗口；到期或被替换并不证明假设成立或失败，也不是全局动作上限。
  • max-actions=0 移除本地 runner 上限，不移除游戏内燃料、危险、计时器或原生终止条件。
  • 观察投影近期修复为保留紧凑 changed_cells、bbox、frame_available；不携带巨大 cells 数组。窗口省略重复声明时也保存 progress。旧进程不会自动热加载这些修改。

10. 用户提出的三层推理如何映射

以下为设计解释，不是声称这些组件已经全部由运行生成。

推理层次Memory／证据Skill／Tool／Subagent研究问题
定位可控对象与动作某动作造成某位移，条件与反例；方向映射是候选事实。Skill：如何选择探测、比较前后帧、排除非对象变化。Tool：已支持的差分与统计。Subagent：独立检查对象归因。变化是否来自控制、动画、计时器或隐含条件？哪些实验能区分？
目标与限制目标候选、门／开关条件、资源消耗假设，保留证据和作用域。Skill：提出竞争解释并选择区分实验。Tool：资源计数／可达性计算。Subagent：反例搜索。覆盖标记是否必要／充分？阻挡是几何、状态门还是动作无效？
约束下规划当前计划及依赖假设；关卡变化后重新判断。Skill：建模、选择算法、检验计划与重规划。Tool：在已实现运算面上求路／预算校验。Subagent：独立可行性审查。计划为何失败？补给、状态变化、模型遗漏还是搜索策略不足？

各层可以交替推进：允许用暂定假设规划，通过实验修订，再更新方法。没有“先把所有低层规律证实，才能规划”或“Memory 转化完才能创建 Skill”的阶段锁。
