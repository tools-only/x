1. 核心判断：把任务数据库与模型工作集分开

基于 Pi 构建长期 Agent，值得采用的上下文机制可以归纳为：完整证据外存、当前状态有界、知识按需展开、研究会话隔离、失效依据明确、恢复路径精确。压缩只是其中一个环节。优秀机制应让模型更容易取得下一步所需的信息，并降低父子总负担；它不以摘要更短、组件更多或工具调用更频繁作为成功标准。

本工程已经实现了相当完整的基础：任务内版本化资源、组件池与显式 assembly、Memory 的阶段有效性、Skill 索引、动态工具选择、工具结果冷存储、读取页 lease、ARC 历史差分、独立 child session、持续研究职责和短增量交付。当前主要问题更接近这些能力是否被及时发现、正确使用，以及是否保住关键认识，而非缺少另一套存储系统。

2. Pi 原生机制：适合复用什么、边界在哪里

2.1 Session tree：保留完整历史，选择当前分支

Pi 将 session 保存为 JSONL，用 id / parentId 组织树；请求上下文取当前 leaf 的祖先路径。失败尝试可留在树里，新分支不必背负失败分支的完整日志。/tree 导航原文件，/fork 和 /clone 创建新的会话文件，普通 custom entry 可存扩展状态而不进入模型，custom message 则可见。

这是一种优秀的 episodic history 基础，但不是自动语义记忆：没有额外索引与检索策略，模型并不会主动知道树中的全部旧证据。编码任务中的分支也不会撤销已经写入的文件；ARC 中更不会回滚环境动作或免费恢复生命。Pi sessions，固定版本。

2.2 Compaction：旧历史摘要 + 近期原文 + 持久原始条目

0.80.6 默认 reserveTokens=16384、keepRecentTokens=20000；当估算上下文严格大于 contextWindow-reserveTokens 时触发。前者给输出留空间，后者是保留近期消息的估算目标。摘要模板保留目标、约束、进展、阻塞、决策理由、下一步、关键上下文与文件操作，比单纯流水账更适合续做任务。

摘要存为新的 CompactionEntry，原条目仍在持久 session。再次压缩携带 previous summary，形成增量更新。切分点必须满足消息协议；不能从孤立 tool result 开始。长 turn 的前缀可能额外做一次摘要，带来一至两次摘要模型请求及延迟。原生估算并非精确 tokenizer，中文、图片和特定 provider 均需单独看实际 usage。Pi compaction 文档、实现。

不能只依靠原生摘要保存 ARC 认识：摘要序列化每条 tool result 仅取前 2000 字符，图片不进入文本序列化；文件跟踪只识别 read/write/edit 的 path，不能自动涵盖 bash 写文件和自定义环境工具。尾部反证、图形关系及自定义 action 语义可能没有进入摘要模型。完整当前 grid/PNG、有效反证和 exact evidence 应由应用层独立恢复。摘要序列化源码。

2.3 Branch summary：移交离开分支的理由

离开探索分支时，Pi 可以只摘要共同祖先之后的那条路径，将结论带到新导航位置。它尤其适合保留“为何放弃 A”“什么反例已排除 B”，同时隔离冗长探索。默认 branch summary 输出上限为 2048 token，与 compaction 的近期保留预算不同。建议在摘要中区分 refuted、abandoned、pending：放弃一个低收益试验不等于它的假说已被推翻。Branch summary 源码。

2.4 Extension / transformContext：存储与请求投影分离

Pi agent-core 的 transformContext、coding-agent 的 context 事件可在请求前调整工作投影；before_agent_start 可调整该运行的 system prompt；session_before_compact 可接管摘要策略；active tool 选择控制实际 schema。扩展状态可以存为不进入请求的 custom entries。这些接口让应用在保留原始证据的同时缩小输入。

优秀用法是确定性去重、生命周期管理、精确引用和授权恢复；需要语义判断时由 Agent 创建认识，不让字符串删减器擅自“总结科学结论”。多个 hook 的顺序也属于实际行为：最后注入的完整当前观测可能不在较早 lifecycle 的 after_chars 中，最终请求仍要独立测量。Pi extensions、agent-core。

3. Memory：从“保存内容”走向“有出处、有时效的认识”

3.1 值得采用的机制

Memory 至少包含三种职责：episodic 原始经历、working 当前认识、procedural 可复用方法。Pi 原生 session 解决第一种的一部分；应用层 checkpoint / memory 解决第二种；Skill 更适合第三种。不要把所有类型混写到一个不断增长的 NOTES.md，再每轮全量注入。

推荐把认识按条目保存：结论、事实或假设类型、适用任务/阶段、支持与反证引用、版本、待做检验、取代关系。这些是设计语义，不是建议把所有字段变成每次调用的必填表单。能从现有 observation、version、report 或 scope 机械取得的内容应复用。只在当前决策需要时把少量相关条目送入热工作集。

外部存储检索宜先做 task/scope/version/validity 过滤，再做语义相关性排序。向量相似度有利于模糊问题检索，但 exact ref 更适合已知证据恢复，两者并用更可靠。对于阶段变化很快的 ARC，先失效旧假说、保留反证，比引入更大向量库更紧迫。跨任务长期记忆还要考虑来源许可、环境变化与能力迁移，不应把一局中的局部规律推广到所有游戏。

3.2 本工程已经怎样做

task-memory.jsonl 是任务内版本日志；task_memory 更新内容，task_memory_pool 捕获 observation/hypothesis/plan/retrospective，但进入池不代表进入输入。有效性根据 task、episode、level、state 的公开边界计算，RESET 或过关可使局部条目过时。knowledge lifecycle 将 loaded/unloaded/suspended/retired 与 untested/supported/contested/refuted 分开，能传递依赖失效、取代和循环阻断。

常规 Memory 投影主要展示 metadata、summary、scope 和 basis_refs；显式 focus 才加入完整 content。pinned 影响排序，不能绕过 assembly 和 validity。没有 basis 的内容标注未验证假设；有 basis 也仍需核查推论是否成立。Memory 另可进入 task_prompt 的 task_state/task_policy，但应保持来源和条件，不自动改写固定宿主规则。

这里已具备优良骨架。未发现默认跨任务 embedding retrieval、自动语义 consolidation 或检索质量已验证的证据。下一步宜检查有效假设、关键反证、未完成实验和下一判别动作是否保存在现有 checkpoint / memory，并在压缩后仍影响选择。相关位置：demo/pi_memory_validity.ts:5、demo/pi_task_knowledge_lifecycle.ts:28、demo/pi_task_local_self_harness.ts:3610, 4496。

3.3 一个具体例子

假设父 Agent 认为“黑色区域不可穿越”，后来真实动作显示某一区域可穿越。好的 memory 更新是：将旧命题标 contested/refuted，记录精确 action/observation、适用阶段，并保留尚未排除的差异条件。压缩后的工作集应带上这条反证及下一检验；旧原图留在 cold store。单纯写“继续探索黑色区域”会失去为何探索的理由；单纯保留一条 ref 则可能无法让模型知道应该恢复什么。

4. Skills 与 System Prompt：程序知识按需，当前认识可更新

4.1 Skill 的三层披露

优秀 Skill 结构是：名称与触发描述 → SKILL.md 核心程序 → references / scripts / assets。Pi 原生支持这种渐进披露；目录仍有常驻成本，模型也不一定自主读取。读过的正文会成为工具历史，渐进加载不自动等于加载后卸载。Pi skills。

工程 ARC 禁用原生扫描，改用任务内 Skill 索引、受限 reader 和 assembly。通常只送名称、短描述、path、exact ref；显式 focus 展开 instructions。读取成功记录为 read_by_agent，明确 actual_use=false，后续 decision/action 的语义证据才可能支持使用。历史版本应用 exact resource 读取，而非默认读取指向当前内容的文件路径。

creator 手册也属于冷程序知识。本工程 read_method 默认 8192 字符分页，最大 65536，返回 heading offsets、hash 和继续调用；作者成功应用后可以把先前手册历史替换成精确来源回执。这样减少长篇创作程序持续占据父输入。它仍有一次阅读成本，也不证明模型识别机会或创作质量已经改善。

4.2 Prompt 的职责边界

system prompt 适合稳定身份、权限和宿主契约。任务假说、计划和研究 inbox 宜放入来源明确的工作层；否则旧结论可能因指令权重长期压制新观测。工程已有 immutable host + versioned task overlay，并用 task_prompt 的 task_policy / method / working_plan / hypothesis / task_state / research_inbox 分层装配。

一个重要实现细节：focus 不过滤 system overlay。system overlay 按 assembly + eligibility 选取；要减少其常驻成本需调整 assembly 或 availability / validity。自然语言“仅当前阶段”不是机械期限，需要已有 scope/依赖支撑。generic history 的字符预算也不能直接约束最终 system prompt。

可考虑的改进是减少重复规则与大段 overlay，复用现有 creator/contract 引用，保留触发入口。增加常驻“必须复盘、必须调用、必须产组件”会提高管理成本，并可能造成沉没成本；只有真实失败定位到必要提醒缺失时才值得试验。代码详见附录 B 的 Skill、System Prompt 小节。

5. Tools：分别管理 schema、参数数据与返回历史

5.1 Schema 是每轮付出的能力目录成本

工具多并不自动更强。应有足够短的发现表面、按当前需要使能的 active schema，以及真正执行时的权限/version 校验。Pi 可用 active tools 选择；社区 loader 可以按需展开复杂工具，但是否省成本要同时看发现/加载往返，以及 schema 变化是否破坏 provider cache。

工程 ARC 已使用较薄管理 facade，选中动态 Tool 后才进入 active schema；非 ARC adapter 的表面不同。动态 pure JSON tool 使用小 envelope，richer schema 仍在 description 并由 runtime 校验，成本只是改变位置，不能按“schema 很小”计算为零。执行边界会重查 loaded、validity 与 exact assembly，避免历史工具名越过当前选择。

5.2 数据靠近计算，避免重复抄写完整网格

适合确定性计算的内容，最好通过 exact resource binding 交给工具：正确的 numeric grid、授权 ref、path、所需输出。父只选择问题与精确输入，不重抄上千个格值。输出交付当前决策需要的指标、失败条件与来源；完整中间数组留在资源里。工程已经有 parent-only binding、pure executor 与 adapter operation，绑定并不扩大权限。

正确绑定还包含语义责任：选错 frame、把展示字符串当 numeric grid、历史状态未标截止点，都可能使一个运行成功的工具返回无关结果。验收应看实际语义值和后续 action，不能只看 status=completed。

6. Subagent 与 Auto-Research：隔离上下文，也隔离责任和证据

6.1 Pi 官方例子与社区候选

Pi 官方 subagent 是扩展示例，并非默认内置编排。它启动独立 Pi 进程，用角色、任务和允许工具形成新 transcript，再向父返回结果。示例的新进程不会自动隔离 AGENTS、skills、extensions、文件和环境：上下文隔离与权限隔离是两项工作。官方 subagent example。

社区 nicobailon/pi-subagents 提供更多可参考设计：fresh/fork、clean prompt、显式继承 project/global/skills、角色 MEMORY.md、按需 subagents_enable、前台 session 与后台 runner 区别。它的角色记忆前 200 行注入属于有界文件记忆，而非 embedding 检索。本工程没有安装或测试此候选；当前文档/包与 Pi 0.80.6 的兼容性未验证，不能直接替换现有 broker。社区项目，附录 A 保留读取 commit 与版本边界。

fresh 适合独立搜索、盲审、验证另一个假说；fork 适合同一代码状态下继续复杂子任务。fork 减少重建背景的成本，却可能带入父偏见与大量无关历史。固定证据 + fresh 更利于比较竞争解释，但如果缺少真实任务目标、反例和授权范围，独立 child 也可能回答错误的问题。

6.2 本工程的显式 context_recipe

普通 delegate 使用 context_recipe 明确选择 include_checkpoint、recent_observations、recent_actions、inherit_harness_refs、output_contract、max_chars。默认不带 checkpoint，recent observation/action 为 0，继承 refs 为空；recipe 默认 12000 字符、最多80000。它限制的是选择窗口，不是整个后续 provider request。

child 的启动 prompt 另受 PI_AUTORESEARCH_CHILD_INPUT_MAX_CHARS 等控制，默认80000，包含 workset 与 bounded state；这仍是字符信封，不包含每轮全部 system/schema/image 的精确 token。角色、工具、证据不同，provider/model 通常继承父运行设置，不能假设 child 一定使用更便宜模型。

工程将 child 放入独立原生 session，禁用自动 context files / skills / writable host tools，只授 exact evidence/resource。ARC 只读研究通常读取父发布的固定 snapshot，而非 live bridge。若显式选择完整 scene ref，可以每轮交付该不可变完整 text/PNG；它可能是历史帧，不应误认为最新环境。ordinary delegate 的有界 action lease 属于独立显式授权，Auto-Research 不继承它。

6.3 Child 也需要工作集寿命与连续性

child_context 可 inspect/compact/read/restore/tools；选择 schema 只能从已授权工具集合中取，不能扩大权限。显式 compact 需要 child 自写 continuity summary；短卡最多呈现2000字符，标注 Agent interpretation，而非 runtime fact。完整摘要和原结果仍可读。child 的共享 lifecycle 最近消息默认12条，父默认24条。

provider output length 应续接同一 child native session，而非要求父重新描述任务。工程保存 partial output / durable checkpoint，broker/runtime 处理 Auto-Research 与普通 delegate 两条 continuation。它不能重建未保存的私有 reasoning；status pending 也不等于已有可用结论。父 length 的 session rotation 只换 Pi 会话，不 RESET ARC；恢复原始 purpose、当前观测、budget 和必要证据。

6.4 研究线持续，模型进程可以有界结束

本工程 Auto-Research 是授权、证据组织、调度、交付和反馈机制。research_line_ref 标识持续问题，worker 标识职责，session/run 标识一次有界执行；窗口只是证据批次。没有必要每个窗口新建 worker，也不要求一条研究线对应永久模型进程。

父通过 assign 授权问题、职责、证据种类、有限 run/output budget 与停止条件。runtime 在后续父请求边界 route/refresh/schedule；默认最多2个worker并发，可配置1–4；每片段最多32个 offered refs。active snapshot 固定，新材料排队；只有 consumed_evidence_refs 的显式分析确认推进消费；completed 后新 session 可续同线，保留前序报告和反例。

当前/紧急结论以短增量交付，未来相关结论只送索引。每次最多2条，总4000 JSON字符；单条超过3600退成详情入口。未放入本次 inbox 的尾部不误标已交付。版本修订、撤回和独立分歧保留；runtime 不作多数表决。父仍负责科学采纳与组件创作/装配，use/assessment 回流研究线。位置：pi_auto_research_worker_runtime.ts:26, 128；机制 ADR 与2026-10-01实施记录见附录。

6.5 子 Agent 什么时候值得用

值得委派：独立大量检索、可平行的竞争解释、需要独立视角的反例检查、需要持续追踪而不应常驻父输入的研究线。宜直接行动：答案只需一个已注册确定性工具、历史结果已经足够、任务即将结束、结果到达时可能过时、需要频繁共享动态状态。没有足够证据时应允许不使用、暂停、放弃和 retire。

child summary 不是免费减负：父还要解释任务、等待、读回结果、处理冲突；child 自己有 system/schema/历史、input/output/reasoning和失败成本。必须对照父+所有child总成本、首次有效行动延迟、管理轮和任务进展，不能只以父 token 下降认定收益。

7. Observation、Reasoning 与预算：防止“看起来更短”的假改进

7.1 当前完整观测 + 历史可逆表示

ARC 应保留当前 canonical observation 的完整 grid，以及配置要求的 PNG。历史小变化可以用 before→after 的可逆稀疏 delta 表示；本工程仅在 changed_cells 0–128 且 cells 完整合法时使用小变化路径。大变化、partial transition 和动画不能无条件用同一差分代替全量。

公开几何匹配属于确定性事实；把某个 changed pattern 命名为“动画”“UI”“角色”则是科学解释。工程已有相关修复，报告不把几何出现次数当因果验证。检验历史压缩也必须审阅实际后续 provider payload，而不只看缓存存在或字符串变短。

7.2 历史 reasoning 与新 reasoning 是两种成本

默认 reasoning history policy 为 preserve。工程有 provider allowlist / opt-in 的 completed editable field 短化；某路径保留末2500字符，另一 ARC 路径保留末1200字符。它们是尾部摘录，不是保真语义摘要。signed/encrypted/redacted reasoning 与尚未完成的工具交换不应被通用文本截断器改写。

短化旧 thinking 可以减小以后输入，却不自动减少当前输出推理。已有真实 Qwen 轨迹显示历史被短化后新 reasoning 仍占很高比例；这只是定位因素的线索。若目标是父推理负担，应分别检验确定性工具、研究职责、计划执行和模型/推理设置，避免把多因素改变归因给一次历史压缩。

9. 推荐实施方向：先复用，逐项证伪

这些建议不构成运行改动或启动付费实验的授权。排序按当前代码优势与已有真实失败决定，而非组件流行程度。

9.1 首选：复用现有 checkpoint 的认知工作集

机会：归档、ref 和读页都能存在，但父在后轮仍可能回到已被反驳的解释。窄命题：在有明确反证的长任务里，将反证、当前假设、未完成检验与下一判别动作保留在现有短checkpoint，比仅有最近状态/摘要更能减少重复取证，且不增加总体成本。

先核对现有字段和失效行为，再改变一个主因素。无需增加必读提醒、第二份状态库或新的管理worker。首次获益路径应是既有决策更新 → runtime投影 → 后续行动；权限、版本和环境检查保持。若此前材料已完整进入payload但选择仍错，应改 semantic use/解释环节，而非扩大恢复量。

9.2 次选：按用途控制研究交付和竞争视图

规则归纳、盲审反例、方法设计和计划跟踪需要不同上下文。复用现有profile、exact grants、competition view与fixed cutoff，避免研究者自动继承父完整解释。短卡带核心修订、证据截止点、当前影响和ref；完整研究状态继续由研究线承载。不能通过隐去反证让“盲审”变成无信息猜测，也不能把不同worker同意当验证。

对明确缺失证据，可以复用现有 experiment_request 或规划请求，请父在环境边界取得材料；不要让runtime从自然语言猜研究目标或额外扩权限。父子主动通信的质量仍是延期事项 C。

9.3 第三步：沿成功应用清退重复中间正文

优先比较现有typed receipts、creator分页和candidate后继引用能否覆盖真实增长点。已经成功出版的同一candidate、已应用creator读页、重复静态contract，比未解决错误或关键假设更适合退场。负例要包含partial写入、版本变化、长失败尾部与需要重试的条件；出错时用exact raw恢复。

9.4 低优先级候选：向量记忆、额外curator、永久worker

当 exact refs 和 task/scope过滤不足以找到未知相关知识时，才考虑语义检索。其收益应覆盖索引、查询、误召回和失效成本。额外curator需要证明现有父/研究职责无法承担局部更新，不能为“管理上下文”另建持续常驻的解释层。永久worker也可能比有界session更贵；连续性应靠研究线状态和交接合同，而非进程一直活着。

相关研究提供启发：MemGPT强调分层外部记忆；ACE强调条目级更新，避免反复整体摘要造成知识侵蚀。这些论文不等于本项目已有对应实现，更不能用论文基准分数证明本项目ARC收益。MemGPT、ACE。Anthropic的一手工程文建议按需检索、结构化笔记和隔离子任务，并提醒过度压缩可能丢掉后来才显重要的细节；这里只借鉴原则，不移植其产品行为。上下文工程。

2. 建议采用的上下文分层

以下是基于 Pi 能力的设计归纳，不是新的 Pi 内置 API：

  1. 稳定合同层：权限、工具语义、预算、必要环境规则。短且稳定；每请求常驻有理由。
  2. 任务工作集：当前目标、最新 canonical observation、有效假设与反证、当前计划、必要失败、下一项可执行检查。随着任务推进更新。
  3. 检索索引层：skill/tool/subagent 名称、purpose、范围与精确定位。目录常驻必须有界。
  4. 外部证据层：完整工具返回、轨迹、source、研究线、候选与原始认识。保留在持久 store，通过精确 ref 或分页恢复。
  5. 分支/研究会话层：尝试与分析在独立上下文进行，以小结、结论与证据定位回交。

这五层回答不同问题：存盘解决可追溯，摘要解决当前容量，检索解决选择，隔离解决污染，反馈与证据管理解决过时知识。任何单一层都不能证明模型下一步已经理解或正确使用了知识。

3. Session tree：持久化完整历史，只发送当前分支

3.1 原生结构

Pi session 是 JSONL，每行一个 entry，通过 id 与 parentId 构成树。默认位置为 ~/.pi/agent/sessions/--<path>--/<timestamp>_<uuid>.jsonl。同一文件可保存不同探索路径；模型上下文从当前 leaf 的 ancestor path 构建，不是将整个树展开给模型。[P2, P3]

这适合编码任务中的多种方案：保留 A 的尝试与失败，回到公共 ancestor 尝试 B；之后仍能检视 A，而 B 的请求无需重复 A 的全部对话。/tree 在原文件内导航；/fork 从较早 user message 建新文件；/clone 将当前 active branch 建成新文件；两者没有默认 branch summary。--no-session 只禁用持久会话，不是“没有上下文”。[P2]

SessionManager.buildSessionContext() 将当前分支的消息、最新 compaction 的 summary 与保留区重建成模型消息；plain custom entries 是扩展状态，默认不进入模型上下文；custom_message 是模型可见消息，两者不可混用。[P3, P10]

3.2 对 memory 的启示

Session log 可视为 episodic 记录，但它不是自动长期语义记忆库。完整保存旧对话，不表示旧对话仍 resident，也不表示会自动检索到；树中有 evidence 不表示当前模型知道其存在。好的应用层接口应返回“核心结论 + 精确来源 + 需要时如何读”的小回执，避免每次恢复重播整个 session。

一个重要边界：分支对话不是环境回滚。回到旧 message 或 fork 不会撤销已经执行的文件写入、外部动作、游戏 RESET 或真实环境状态。ARC 上尤其不能把 session tree 当作可重新获得生命、免费试错的 simulator。此项是对 Pi session 语义及本工程不可回退 ARC 历史约束的设计解释。

4. Compaction：增量摘要、近期尾部与协议完整性

4.1 真实默认值

0.80.6 原生默认：[P4, P5]

{
  "compaction": {
    "enabled": true,
    "reserveTokens": 16384,
    "keepRecentTokens": 20000
  }
}

自动阈值为 contextTokens > contextWindow - reserveTokens，严格大于。reserveTokens 为生成留空间，keepRecentTokens 为选择保留近期消息的估算目标；两者不是同一个预算，也不是工具输出限制。设置可来自 global 或项目 settings；实际有效设置还受 launcher/SDK overrides 影响。

token 估算优先采用最后一个有效 assistant usage；跳过 error、aborted 与全零 usage；然后加上之后新增消息的估算。没有 usage 时用文本字符数 /4；图片每块估 4800 字符，即约 1200 token。这是 heuristic，不是中文/图片/provider 精确 tokenizer，不应将它作为真实成本测量；native 源码自身的“conservative”注释也不能保证对所有语言与图像实际保守。[P5]

4.2 过程和 cut point
  1. 从尾向前累计消息估算，找到接近 keepRecentTokens 的合法 cut point。
  2. 将较早消息摘要；保留较新原文。
  3. 若已有 summary，将 previous summary 一并交给模型进行增量更新。
  4. append CompactionEntry(summary, firstKeptEntryId, tokensBefore, details)。
  5. 重建成 summary + 从 firstKeptEntryId 开始的原始消息 + 后续消息。[P4, P5]

原始 entry 没有因 compaction 被删除。第二次摘要从上次 kept boundary 开始，避免把上次保留的消息永久跳过。文件操作信息通过 details 累积。[P4, P5]

工具调用与返回不可拆散：允许在 user、assistant 及某些 user-like/custom 消息处切分，不能从 toolResult 起头；在有 toolCall 的 assistant 处切分时，后随结果一起保留。若一个 turn 特别长，允许在 assistant 处 split turn；历史 summary 与当前 turn prefix summary 合并。完整历史与 prefix 都存在时最多需要两次顺序摘要模型请求，这种压缩有 input/output、latency 与潜在推理成本。[P5]

4.3 摘要内容与真实丢失点

原生 checkpoint 模板包含 Goal、Constraints & Preferences、Progress（Done/In Progress/Blocked）、Key Decisions（理由）、Next Steps、Critical Context，以及 read-files/modified-files。这比只写“做过什么”更有利于跨轮连续性，但它是摘要 prompt，不是保真证明。[P4, P5]

需要明确四个限制：

限制 一手依据 影响
每条 tool result 摘要序列化只保留前 2000 字符 TOOL_RESULT_MAX_CHARS=2000 关键结论若藏在大结果尾部，摘要模型看不到
user/toolResult 的图片块不进入文本序列化 只 filter type === "text" 图形关系若未转为文本或精确 ref，不能依赖原生摘要恢复
file tracking 只识别名称 read/write/edit 且有 path 的 toolCall extractFileOpsFromMessage 的 switch bash 写文件、自定义工具或远程 mutation 不自动获得完整操作清单
摘要由模型输出 summarization provider 调用 可能丢失反证、置信度、未完成实验、推断和观察区别

以上均来自 [P6]，对 ARC、多模态与自定义工具特别相关。由此应将可验证关键状态、完整当前图像/网格、有效反证与精确证据引用作为独立恢复输入；不要把 native summary 当作唯一 canonical memory。

默认历史摘要 output ceiling 为 min(floor(0.8 × reserveTokens), model.maxTokens)；split prefix 为 0.5 × reserveTokens 再受模型 ceiling 限制。这不是固定“摘要 2000 token”：2000 是 tool result 字符限制；branch summary 的 output cap 另为 2048 token。[P5, P7]

4.4 主动阈值与 overflow

Pi 将正常超过阈值后的 compaction 与 provider context overflow 区分。源码解释为：threshold 压缩不会自动重放已完成 turn；overflow 可删掉对应错误消息、压缩并重试，且 recovery 有一次 compact-and-retry 上限。session_before_compact 提供 reason 与 willRetry，使扩展可按差异行为处理。[P12]

不要将 context overflow 与 provider output length 混同。agent-core 遇到 length 的 message 所携带 toolCalls 时，默认让该批 calls 失败而不是执行可能截断的参数；没有完整 toolCall 的 output 截断也不保证自动继续文本。工程 child continuation 和验收因此需要自身真实路径验证。[P11]

5. Branch summary：交接被放弃分支的结论

切换 /tree 分支时，可选择不摘要、默认摘要、带自定义 focus 摘要。Pi 找 oldLeaf 与 target 的公共 ancestor，只收集离开的路径，按 tokenBudget 从最近内容优先纳入，调用模型生成 summary，附着在新的 navigation position，继续当前分支。[P2, P7]

这用于保留“方案 A 为何失败”“已排除哪个解释”，同时隔离 A 的长日志。默认 branch summarization input 预算为模型 contextWindow 减 reserveTokens（默认 16384），默认 maxTokens 为 2048；不是默认再 retain 20k 最近消息。[P7]

branchWithSummary 的实现先将 leaf 移到 branchFromId，再 append summary entry。某版 compaction.md 的 ASCII 图易让读者以为 summary 挂在 abandoned leaf，应以 session-manager 实现与 sessions.md 的描述为准，不要照图误解。[P3]

设计上应保留“被放弃”“被反驳”“暂未完成”状态，避免 summary 把一次失败的假设写成既定事实。分支 summary 本身不会产生独立实验，多个模型同意同一摘要也不构成环境证据。

6. Skills：常驻目录、按需正文、正文之外再按需引用

Pi 在启动时扫描 skill，提取 name/description/filePath，system prompt 以 available_skills XML 展示；模型通过 read 加载匹配的完整 SKILL.md，再通过相对路径读取 references/scripts/assets。这是原生 progressive disclosure。[P8]

收益主要来自：几十页手册只占目录几行，只有当前任务需要的 capability 正文 resident；详细 reference 甚至可以不与 SKILL 正文一起加载。disable-model-invocation: true 可将 skill 从自动目录排除，由用户 /skill:name 调用；没有 description 的 skill 不加载，同名碰撞保留先发现者并发 warning。[P8]

但应核查三个边界：

  • 目录本身也有成本：几百个 description 与路径仍每请求 resident；要减少不相关注册、过长 description 与重复用途。
  • 模型不一定自主读取：官方文档明确说明 models 不总这么做；“目录已暴露”不等于采用。
  • 读过的正文进入工具返回历史：progressive disclosure 不意味着读取后会自动卸载；后续移出 projection 或 compaction 仍有应用层策略。

Skill allowed-tools 的 experimental 元数据不应取代实际权限 allowlist 或子进程 capability ceiling。skill 是 workflow/procedural knowledge，memory 是任务认识/evidence；把创作手册存为长期任务记忆会制造不必要的 resident 程序负担。

适合本工程的归纳：creator 是按需 skill，组件目录只显示 purpose/location/version；task memory 存观察与认识；全文 creator、研究细节和旧 source 留在资源中，通过精确引用恢复。该段是建议，是否已经做到需当前工程 code audit。

7. Tools：同时控制 schema、调用结果和历史结果

工具造成三类不同成本：active 工具 schema 的每请求成本、刚返回的 payload、被反复带入的历史 payload。只压缩 output 不能解决巨大 schema，只隐藏 schema 不能解决旧结果。

registerTool 注册能力，setActiveTools 控制现在给模型哪些 tools；注册可以动态发生，同 session 不需要 reload。工具 snippet/guidelines 也只在 active 时参与 system prompt。[P10]

8. Memory：Pi 原生边界与三种可实现方案

8.1 原生提供什么、不应代称什么

在已审阅 0.80.6 文档与 APIs 中，Pi 原生提供：session persistence、compaction/branch summary、context file（global、ancestor、cwd 的 AGENTS.md 或 CLAUDE.md 全文拼接）、custom entry 持久状态和 extension hooks。没有在这些一手资料中发现默认自动写入的 task memory store、向量检索式长期 memory 或自动抽取/遗忘/事实验证 pipeline。[P2, P3, P10, P14]

AGENTS.md 可承载人维护的稳定说明，但它始终拼入 prompt，不能当作免成本长记忆。appendEntry 是隐藏持久状态；sendMessage 是模型可见消息；前者不会自动让 Agent 知道，后者会消耗上下文。应用要明确“保存 → 索引 → 选择 → 暴露 → 使用 → 更新/撤销”。

8.2 Memory 方案 A：简短文件索引 + 按需正文（推荐先复用）

在 task-local 范围保存主题化 note，仅给模型简短目录与当前任务高相关条目；完整内容通过 ref/read 恢复。每个条目可以带来源范围、版本、事实/假设区别、反证与 replacement ref，但不要为了规范增加无必要管理字段。

适用于中小知识量、已有精确 resource store 的项目。优点是可审计、不需 embedding 服务、能针对性读取；成本是检索决策与读页；负例是索引无限增长、同义重复、旧 memory 未失效。与当前工程的版本池/装配/focus 接口应先考虑复用，而不是另建 memory worker。

8.3 Memory 方案 B：scope/version-aware 检索（候选，不是原生）

为大量研究轨迹建立全文或语义检索，先做 task/worker/permission/environment/version 过滤，再做 lexical/semantic 排序，返回有限 evidence snippets 与 exact refs。检索以可能帮助当前决策的证据为目标，不以“多找几个相关段落”为目标。

它有 embedding/index/update 成本，也有错检与沉默漏检；semantic similarity 不证明证据有效、事实未过时、权限允许或解决当前任务。对代码路径/错误文字/精确 observation，lexical lookup 常更确定，宜先评估已有 ref/全文接口能否满足。没有证据表明当前工程已具备这种自动 RAG，本项仅为未来候选。

8.4 Memory 方案 C：角色私有长期记忆（community 已有实现描述）

社区 nicobailon/pi-subagents docs 提供 memory: { scope: project, path: ... }。每次 child run 读取其 MEMORY.md 前 200 行，注入该 child system prompt；项目 scope 位于 <project>/.pi/agent-memory/<path>，用户 scope 位于 ~/.pi/agent/agent-memory/<path>。拥有 write/edit/bash 的角色可追加有日期笔记，readonly 角色仅得到 readonly memory block；目录不是预先建好，而是首次写入产生。[C1]

这比把 reviewer/scout 各自所有经验交给父更合理，但 200 行不是 token cap，超长行仍可能膨胀；固定前缀注入也会携带无关或过时知识。父 memory、role memory、task memory、global memory 的 scope 应明确，持续研究主题不能靠永不退出的模型进程保存。

社区 README 自称其 namespace 独立于 Pi 自身 memory 系统，这个措辞不应倒推实际 0.80.6 存在新的原生 memory 产品。社区 main 与实际 Pi 环境版本不同，需兼容性验证。

9. Extensions/SDK：非破坏投影与“存盘不等于可见”

9.2 一个可靠的应用模式

canonical store → 提取当前合法工作集 → 注入当前请求 → 记录最终 provider payload → 下一轮验证决策。

例如最新 ARC grid/PNG 与 canonical frame 存在环境记录；历史大型工具结果保存在资源；当前请求只恢复当前完整 observation、有效决策和仍有租期的 evidence pages。这种模式可以避免“摘要失去图像后反复读当前图”“已读页下一工具轮就被删”等问题。但存档存在、读页成功、ref 有效只是 data reachability；后续模型有没有保留假设、反证、未完实验与决策理由，仍要检查真实 provider 输入与行动。

非破坏投影尤其值得借鉴：history/store 留存，projection 可以变小；不能为了较小请求删掉唯一证据或把模型 reasoning/signature 任意改写。permission/budget/version/environment 检查仍需保留。本文没有运行 provider 实验验证这些方案净收益。

10.3 可借鉴的职责与交接设计

父承担当前行动选择；research worker 承担长文读取、证据跟踪、反例搜索和后台分析；child 回交立即有用的结论、置信度/条件、反证、精确证据 refs、仍需父决策的请求；长分析留在线/worker store。不要每收到 observation window 就必开新 worker；研究线连续性是持久 topic/assignment，不等于永久模型进程。

合理 launch recipe 包含 task purpose、授权 observation scope、需要的数据/反证、交付格式与预算。若独立复核价值重要，可不提供父先入结论；若 child 负责延续父计划，则传递决策理由与未完成实验。盲审/揭盲是研究方案，不是默认多 Agent 共识规则。

subagent 只能在减轻父负担或获得新的可用证据时有净收益：父启动/管理轮、child 启动与模型 input/output、重复读取、交接与修订都要计入。把父 history 整体 fork 到每 child 会复制 input；把所有 child transcript 复制回父会撤销隔离收益；只返回短结论但没有证据也会失去可验证性。
