# P1-P6 Self-Harness implementation result

Date: 2026-10-31. Status: implemented; focused functional and scripted wiring verification completed (regression run recorded below).

## Problem and falsifiable claim

The supplied job identifies path exploration, a diary-sized Hook, and RESPONSE-only publication as avoidable Agent work. The narrow claim is that a checked parameterized Python function can become a named callable through one explicit promote call, then produce successful component_runs evidence without a conversion note or Maintenance turn. A bad generic harness write must redirect to logical tools without filesystem exploration.

Burden removed: path selection, format scaffolding, category walks, conversion-note authoring, and a required publish response. One save/promote decision and one named Task call remain. Saving or sensing alone must not satisfy L0. Negative cases: missing function, unbound dependencies, bad body/name, repeated call failures, stale candidates, level boundary, and end-of-budget Hook skip.

## Design and lifecycle cost

Reuse NativeRuntime, session extraction, Binder and existing append-only logs. Runtime senses function fingerprints from successful Task Python cells; drafts stay private until explicit promote. Candidates enter the next Task/Hook head unasked. A four-call Hook replaces trajectory review and path inspection. The next saved-component call updates Failures/Successes through component_runs; new versions reset call counts, publication removes the candidate, and level changes remove old candidates. Named compatibility retirement removes mounted components. No workers, extra provider calls, auto-publication, or semantic action gates were added. Resident text is capped at 2400 characters, including at most three Failures and three Successes; Hook calls use the Task budget.

Permissions, workspace confinement, versioned Binder checks and environment action authority stay in their existing owners. The legacy daemon response is opt-in via ARC_THIN_DAEMON_RESPONSE_COMPAT=1; normal sensing does not switch identity, tool table or Task history. Meta process publication also has a logical compatibility kind, separate from Self tools.

## Bounded evaluation protocol

Environment: local Windows, pinned Pi 0.87.0, Python/WASI kernel, production bridge, mock ARC SDK, scripted offline provider. Fee-free focused tests and two scripted runner smokes; no paid runs or game-source inspection. Functional checks use negative cases and actual sandbox calls. Smokes test bad-write recovery and repeat tool calls, plus Hook promote/skip and budget-boundary suppression. Scripted runs are wiring evidence only. No claims about autonomous save rate, comparative token/latency savings or task benefit are made.

## 2026-11-02: non-tool Hook adjustments

### Problem and claim

The actual post-action Hook exposed only `promote`, `save_tool`, `read_component`, and `skip`, even though the existing `self_component` already stores scoped memory, prompt/process text, Markdown skills, and subagent definitions. This made Hook edits tool-biased and kept the other existing component paths unreachable there. Narrow claim: a Hook can save an applicable non-tool component and have it enter the next Task context, while Python tool execution and ARC actions remain unavailable in the Hook. This removes the need to route every useful adjustment through Python. No component is required when the evidence does not justify one.

### Change and bounded check

The Hook now exposes `self_component` and allows its existing non-tool paths, while `self_component(kind="tool")` is explicitly refused; tools remain publish-only through `promote` or `save_tool`. The four-call Hook budget remains unchanged. A focused extension test saved a prompt, confirmed the content in the next ordinary Task context, and confirmed tool and action refusal. The test used the local extension harness, not Pi's real provider or ARC SDK: `node --experimental-transform-types --test --test-concurrency=1 tests/arc_thin_self_hook_components.test.ts` (1 passed). A separate pre-existing dirty surface test still fails earlier because its injected DIARY text is present in its original user prompt while its assertion expects that text to be stripped; this was not changed here.

The authorized real-provider check is one AZ/qwen low run, bounded at 1 hour and 100 actions, with no total token cap; it is owned by the parent runner. It must inspect whether a non-tool component was independently chosen, projected, and semantically used. A projected prompt alone does not establish use. The negative case is a Hook tool/action attempt, both of which must remain blocked; choosing Skip when no useful adjustment exists is valid.
