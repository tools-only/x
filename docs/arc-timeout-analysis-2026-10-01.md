# ARC 两次真实运行的超时原因

日期：2026-10-01。此次只分析已有真实运行记录，没有更改生产代码或重新启动实验。

## 结论

两次退出都由实验总时限触发：runner 把 `experiment_timeout_seconds` 转成 Pi session 的 monotonic deadline，截止后返回 124。截止时正在等待父模型的下一轮输出，随后正常关闭 ARC scorecard。动作预算尚未耗尽。

主要耗时来自长模型输出及等待，核心运行还被周期窗口的连续门禁往返放大。没有 Auto-Research/child 执行、provider `length` 恢复或 scorecard 关闭失败导致本次超时的证据。历史所谓数百秒 HTTP 响应延迟，部分来自遥测 FIFO 错配，需要纠正。

## 原因 1：每轮生成量大，串行循环消耗总时限

核心运行单轮约 18.8–324.0 秒；追加运行四个完成轮次分别为 137.8、165.7、289.1、350.0 秒。追加运行首次点击之前，先生成了 8564 token 去读取 arc_state，再生成 9400 token 去更新 checkpoint 并点击；前两轮已消耗约 303.5 秒。

追加运行第三个动作前的单轮输出为 21411 token，耗时约 350 秒。它尚未达到第 5 步周期门禁，也未启动研究或创建组件，已经接近总时限。因此长生成是两次运行共同的主要耗时，不能把共同原因归给 Harness 管理或 Auto-Research。

两次模型配置的输出上限都是 65536 token。完成轮次没有 `length` 截断；大的上限允许长输出，没有形成与剩余总时间关联的短决策预算。不能从日志认定 reasoning_effort 被显式设为 high；本次没有保存该参数的具体值。

### 为什么父模型会生成这么多：推理占比补查

补查原生 `pi-events.jsonl` 的 assistant message usage，而非省略 reasoning 字段的 provider telemetry 摘要，确认核心 23 轮的 232022 output token 中有 213547 reasoning token（92.0%）；追加 4 轮的 56734 中有 54496 reasoning token（96.1%）。Pi OpenAI Completions 解析器把 completion_tokens 作为 output，另将 completion_tokens_details.reasoning_tokens 记入 reasoning，后者已经包含在 output 中，不能重复相加。

例如核心 14:52:04 完成轮次总输出 26352、推理 24659，非推理 1693；追加第三个动作前总输出 21411、推理 20892，非推理仅 519。巨量生成主要为推理，不是动作参数本身膨胀。

可确认或由启动配置推导的因素：

1. **启用推理能力，未配置独立的短决策预算。** ARC runner 将模型注册为 reasoning=true，未传 --thinking，运行专用 settings 只有 compaction 配置。安装的 Pi 0.80.6 DEFAULT_THINKING_LEVEL=medium，SDK 没有显式值时使用该默认。因此启动路径预计 medium；原始 payload 的字段名证实 reasoning_effort 存在，但没有保存具体值，网关如何落实档位仍未验证。medium 是档位而非固定 token 上限，不能预期它自动限制到几百 token。
2. **65536 是整轮输出上限，未区分探索与日常执行。** 游戏探索、状态读取、checkpoint、周期延期都使用同一父模型路径，没有已实现的、与剩余时间关联的 reasoning token 预算。上限不是长推理的充分原因，但允许这些长推理持续到自行结束。
3. **父承担多个分析职责，缺少实际计算/研究分担。** prompt 要求目标与规则推断、预测反证、规划与竞争比较、Harness 价值判断；同时允许已知情况简化执行，并未要求每轮重做全套。真实运行未创建组件或启动研究，相关工作仍由父处理。不能仅由这些要求认定每一段具体推理在做什么，因为完整输出正文未保留。
4. **重复管理与状态读取带来新的推理机会。** 旧窗口依次拦截、skip 失败重试、自行读取已自动提供的状态，使父重新进入模型生成；有些只产生简短管理动作的轮次依然生成两万以上 reasoning token。
5. **历史压缩只作用于下一轮输入。** `compactHistoricalArcFrames` 将已完成、非当前 assistant 的长 thinking 截成尾部短摘要；这能缩短后续输入，不会对当前 stream 的推理 token 设限。不能把压缩开启当作已控制输出长度。

目前确定的是推理 token 占据主要输出；无法仅凭 usage 将其进一步拆成有效视觉分析、重复计算、犹豫或循环。对应改进需要显式、可调整的父决策计算预算及阶段差异，并验证 token 降低是否牺牲行动质量。不能只靠要求“简短回答”控制隐藏推理。

## 原因 2：旧周期窗口连续拦截同轮动作

核心运行 23 个完成轮次细分如下：

| 轮次结果 | 轮数 | 请求至输出完成 | 输出 token |
| --- | ---: | ---: | ---: |
| ARC 动作成功返回，包括有界批量 | 10 | 1323.7 秒 | 91646 |
| 周期判断门禁拒绝动作 | 4 | 790.7 秒 | 71627 |
| 动作契约错误：点击缺少 x/y | 1 | 213.9 秒 | 12642 |
| 其他工具轮：读取、checkpoint、候选拒绝等 | 8 | 956.4 秒 | 56107 |

四个周期拒绝分别要求处理窗口 5、15、10、5。其中多次父先成功延期当前窗口，随后的动作又被另一个旧窗口拒绝。例如 15:03:34 的父延期后，动作被窗口 10 拒绝；15:07:51 的父延期后，动作又被窗口 5 拒绝。这证明“最新窗口优先”虽然避免旧窗口独占提示，却仍会逐个消耗旧窗口的管理轮。

791 秒是这些已发生轮次的输出耗时，不能直接声称移除门禁就净节省 791 秒；同一轮也可能包含游戏推理。7 次成功 defer 不等于 7 次独立额外模型请求，因为不少 defer 与 checkpoint/动作在同一条 assistant 工具批次内。

旧代码中的 auto_research(skip) 路由错误另有 4 次失败调用，分布在 2 个模型轮中；这两个轮次分别约 30.0 秒和 200.5 秒，不能全额归为 skip 成本。该缺口已在前轮修复，核心运行的旧进程未热加载；追加运行没有调用此接口。

## 原因 3：动作边界取消尝试与响应遥测错配

核心运行有 36 条真实 provider_request hook，追加运行有 8 条。其中分别有 12 和 3 次在动作/拒绝边界附近立即取消的额外请求尝试，随后新父轮再次发起请求。不能假定这些尝试已在服务器完整执行或产生计费。

已核查安装的 Pi 0.80.6：`shouldTerminateToolBatch()` 要求批次内所有工具结果都 `terminate=true`。项目只给 ARC 动作结果设置 terminate；checkpoint/defer/读取等结果在混合批次里不会满足该条件，仍可能进入下一次 provider 请求。项目 ARC `tool_result` hook 的 ctx.abort 和 Python runner fallback 会取消续轮；日志显示边界处仍出现了很短的请求尝试。此处是生命周期兼容问题，直接本地耗时很小，服务器侧负担未知，不能单独认定为主要超时原因。

项目 `demo/pi_provider_telemetry.ts` 的 after_provider_response 用 `inFlight.shift()` 配对。被取消、没有收到响应 hook 的请求未从队列移除，后续响应持续错配到更早的请求；message_end 使用的 lastResponse 关联也随之受影响。request_index 还包含 fallback 分配的记录，最后序号 48 不等于 48 次真实网络请求。

例如核心日志最后一个响应标为 request 31、latency=1198.18 秒，但真实 request 31 早在 14:54:59 已完成输出。这条 15:12:33 的响应位于 request 48 发起后约 8 秒，不能拿 1198 秒认定 provider HTTP 等待或迟到响应。

移除没有响应的边界取消尝试后，按串行活跃请求顺序重建的响应头等待为：核心中位约 6.8 秒、最大约 14.4 秒；追加中位约 5.7 秒、最大约 6.6 秒。这是有源代码和完整生命周期支持的重建，不是原始 request ID 的可靠关联，也不是首 token 时间。provider_response hook 在 OpenAI SDK 的 withResponse() 后、消费流之前触发；HTTP 200 仅说明拿到响应头，不说明整轮生成结束。

此前实施快照关于“取消请求迟到响应”的判断没有可靠 request ID 支撑，本报告取代该判断。真实长生成仍由消息完成时间和 usage 独立证明。

## 因素 4：上下文扩大可能加重成本，但尚未做因果对照

核心请求体从约 47k 增至最大 153k JSON 字符，追加请求最大约 93k。核心高水位时主要模块为观测约 47k、system prompt 约 28k、工具 schema 约 25k，此外还有历史消息与结果；当前组件池仍未装配，因此并非创建了大量组件导致上下文膨胀。

字符包含图片 base64，不能当作真实模型 token。图像与观测的重复载体、较大的常驻 system/schema，以及反复自行读取已自动提供的当前状态，都是候选成本来源；现有日志没有同模型固定输出量的对照，不能证明输入增大导致了多少输出延迟。尚无 context overflow 或压缩失败导致本次退出的证据。

## 优化优先级

1. 修复请求生命周期遥测，显式记录取消、响应头、首 token、流结束、工具边界与未完成请求，避免 FIFO 错配及错误归因。
2. 给父决策配置可调整的输出/推理预算并关联剩余时间；先做同模型有界对照。单纯硬砍输出可能产生 length 和不完整工具参数，必须保留现有续接与结构化返回处理。
3. 允许父明确对一组到期窗口作一次 review/defer，或同一父动作边界只处理一个管理决定；保留各窗口事实与父理由，避免刚延期又被旧窗口拦住。
4. 核对 Pi 的混合工具批次终止语义，减少动作之后立刻取消的续轮请求；保持一次不可回退环境历史及后续父轮。
5. 减少重复状态读取与常驻上下文，再在相同动作/时间预算下比较生成 token、有效动作和关卡进展。

以上为基于本次证据的建议，本次未实施这些新修复。直接扩大实验时限只会延后截止，不能消除长输出和重复管理轮成本。
