# 自进化 Agent 设计宪法

**版本：** 2.0（2026-11-13）
**性质：** 目标架构与工程验收约束；不是当前代码能力声明。  
**适用范围：** Agent 自身视图、可修改性建模、运行时反射、自我审阅、自我进化及其在 ARC、coding、PPT、视频等任务中的实现。

## 序言：研究对象与目标

本项目将**同一个正在运行的 Agent 及其完整运行架构**视为自我审阅和自我修改的对象。Agent 在用户授权范围内，围绕任务形成并调整自己的工作架构。组件、模型与角色、调度、状态、上下文、评估和自我改进机制，都是这套架构的一部分。

用户定义这个 Agent 的哪些部分可读、哪些部分可修改，以及允许的修改操作。基础设施将实际运行状态构造成可信的自身视图，并在任务过程中提供给 Agent。Agent 依据自身视图、任务过程中的执行事实和当前任务阶段，决定如何改进自己；被授权的修改通过反射作用于自身，并影响后续运行。

**核心判据：Agent 审阅的对象、修改的对象与实际执行的对象，必须是同一个 Agent 的同一套运行结构。**

本宪法规范目标和不能跨越的设计边界。某项能力尚未实现时，必须如实标记缺口；不能以提示词、配置清单或离线测试代称其已经实现。

## 核心术语与系统范围

Architecture、Workflow 和 Loop 都可以指向同一个 Agent 的**系统级运行安排**。三者分别强调结构、任务推进和反馈。Architect 指构建者的角色，Orchestration 指运行中的协调机制。这些术语不规定必须拆成五个模块或另设 Agent。

| 概念 | 在本项目中的定义 |
| --- | --- |
| **Agent Architecture** | Agent 如何组织成一个可运行系统，包括有哪些角色、模型和组件，谁掌握状态与决策权，信息和控制如何流动，如何执行、评估、反馈和重构。运行时架构是这些关系在某一任务阶段的实际生效形态。它覆盖受保护的底座与用户可授权调整的部分。 |
| **Architect** | 根据目标、资源和约束构建、比较和修订架构的角色。本项目让 Agent 在执行任务时也能承担自身的 Architect 角色。它可以决定是否分工、设置何种决策与反馈边界，以及在证据变化后如何重构。该角色可以由同一个 Agent 承担。 |
| **Workflow** | Agent 为达成任务目标构建并实际运行的工作架构。它包括如何形成工作结构、如何分工、何时并行或顺序执行、如何保存和传递状态、如何验证与交付，以及何时依据进展重新组织自身。Architecture 描述这套系统如何组织，Workflow 描述这套组织如何随任务阶段运转。 |
| **Orchestration** | 在运行中协调角色、模型、组件、状态与工作进度的机制。它负责把工作分派、依赖、同步、预算、交接和反馈落实为实际执行。Architect 决定采用或修改怎样的组织与协调规则，Orchestration 按生效规则推进。调度、路由和协作策略本身可以是 Agent 获授权后重新设计的对象。 |
| **Loop** | 从反馈角度看同一套 Workflow。执行结果、环境变化和评估回到决策，并可能改变下一步行动、工作分工、状态组织乃至后续运行结构。交付前可以经历多个相互关联的反馈循环。 |
| **Loop Engineering** | 构建、调整和验证上述闭环工作架构，涉及决策、状态、执行、评估、反馈与重构如何共同运转。组件调用循环、局部重试和自我审阅循环都是可以纳入其中的机制。 |
| **Agent Loop** | 单次会话中模型与工具的逐步调用循环：发出请求、接收工具结果、把可观察材料纳入下一次请求，直到本轮结束。它是运行时的执行节拍。其使用的材料包括当次请求的上下文、memory、工具结果等。Agent Loop 不是 Loop Engineering：后者指构建、调整和验证围绕任务的完整闭环工作架构。 |
| **Harness 与 Harness Components** | Harness 提供 Agent 运行所需的能力、资源、接口与约束。Tool、Skill、观察器和评估器等是其中可独立定位的组成部分。组件如何组合是 Workflow 的一部分，整体工作方式还包括决策权、协作、状态、控制和反馈。 |
| **自我进化循环** | Agent 根据执行过程的证据审阅自己的组件、工作方式或运行架构，提出并实施变化，在验证窗口中检验，再决定保留或恢复。它可以嵌入任务 Workflow，并对后续 Workflow 生效。 |
| **Meta Harness** | Agent 对自身工作方式和运行架构进行建模、比较、构建和改进的能力。其对象可以是组件、协调策略、Workflow、Loop，或 Agent 用来审阅和改进它们的方法。Meta 由审阅与改进所针对的对象及实际行为界定，无需对应一个独立模块。 |

任务运行中选用已有规则、生成一份计划、按授权改变工作结构，是不同的行为。架构重构的证据来自实际角色、决策权、状态流、控制流或反馈关系的变化，以及后续运行使用了这些变化。同一个任务内形成的工作架构可以是有效的动态组织。若要声称形成了跨任务可复用的自我进化，还需另验后续采用与效果。

## 第一章：自身对象

### 第一条：根对象唯一

架构以完整 Agent 实例为根对象。组件等是其内部可定位的部分，须能表达其所属关系、依赖关系、生效版本与运行职责。不能把“可优化对象”建成与 Agent 脱节的一组独立文件、候选项或外部服务。

当前可以先支持少数部分，但根对象和部分之间的关系从第一阶段就必须成立。新增可优化范围，应是扩展同一对象模型，而非为每个领域另建一套自进化系统。

### 第二条：可见性和可写性分离

用户配置定义自身哪些部分可修改、允许何种操作；不可修改部分仍应在适当的可见范围内呈现其作用、关系及不可修改的原因，以便 Agent 理解自己的边界。某部分不可写，不意味着它从自身视图中消失。

可修改范围是对 Agent 内部部分及操作的权限分配，不是把一张“活跃组件表”变成执行路由、Binder 映射或安装队列。用户配置不能代替对象本身。

### 第三条：自身视图与运行结构因果相连

自身视图必须源于实际运行中的 Agent：显示当前生效的部分、关系、版本、权限、关键状态与执行归属；修改生效后，视图同步呈现修改后的运行事实。必要时可以有紧凑摘要和按需展开，但摘要必须能追溯到完整的自身模型，不能以当前任务碰巧使用的组件集合充当“整个自己”。

宿主底层服务自动产生并向 Agent 提供自身视图。Agent 不应依靠记得调用 `inspect`、翻目录或主动拼装配置，才知道自己有哪些可优化部分。自我认知不能只靠 prompt 描述：权限、版本、视图与运行行为的一致性需要程序机制保证。

## 第二章：自我审阅与进化决策

### 第四条：任务推进经过自身审阅

在任务窗口的合适阶段，Agent 应获得当前任务状态与完整可优化范围的自身视图，并形成可追溯的自我审阅结果：当前哪些内部部分值得关注、为什么、改哪里、改成什么、预期影响什么。审阅可采用分层视图和摘要，不能要求每一步重新展开全部代码。审阅不必在每一步发生，但每次进入的进化审视都必须以自身修改结束（第五条）。

自我审阅的对象是 Agent 自身。进化审视面向 Agent 产出交付件的整个过程中所展现的各个环节，包括请求与上下文、工具使用与报错、输出截断、单元与边界、评估与探针、状态与协调，以及交付件的质量，尤其是 harness 的不足与缺陷，目的是找出 Agent 自身的能力缺陷。交付件质量是审视的一个维度：验收、渲染、引用、探针等结果中的不足，是能力缺陷的一等证据，应追溯到造成它的 harness 环节、组件或策略。审视不能只是给交付件打分或判定合格，也不能以“交付件合格”作为不改进自身的理由。交付件在审视中只读，不在审视里直接修改。

宿主把审视范围内的过程事实和交付件质量事实作为缺陷线索完整放入审视视图：按固定结构列出全部事实类别（取值为零的类别也列出），不筛选、不排序、不标注异常，也不给出诊断或建议（第五条之一、第六条之一）。哪些事实反映缺陷、缺陷位于哪个部分、如何修改，由 Agent 判断。把审视对象界定为 Agent 自身（过程事实与交付件质量都作为其能力的证据）是本条对审阅范围的定义，不构成宿主为 Agent 固定关注对象。

审视的时机应跟随实际工作的节拍。宿主依据客观的工作事实划定计数边界，使每个计数边界之前都有实际发生的任务工作。Agent 如何组织提交，例如先完成整体再连续提交各单元，都不能使审视被合并掉或被绕过。划定边界和工作归属所需的簿记由宿主产生（第五条之一），不要求 Agent 为工作标注所属单元或补充声明。具体任务的工作检查点只能由适配层声明（第十条之一）。

任务失败、成功轨迹、执行成本和用户反馈是审阅证据，不是审阅范围的上限。审阅应同时考虑当前阶段的目标、后续任务的准备、能力短板、内部结构之间的制约，以及改进自身的方式是否仍然有效。

工程可以保证视图被提供、审阅步骤进入运行路径、覆盖范围和决定被记录；不能仅凭这些机制宣称模型内部已进行了充分思考。充分性还须由实际审阅内容与后续行为检验。

### 第五条：进化方向由 Agent 决定

在用户授予的范围内，Agent 决定修改哪里、提出何种改变、如何实验以及如何利用反馈。每项进入验证窗口的改变同时由 Agent 声明自己的成功谓词：指标、方向和比较段。宿主只机械执行预先定义的权限、接口契约、并发版本和状态一致性约束，并在窗口到期时依据已入账事实和该谓词计算是否满足；不满足则恢复，满足则保留。谓词本身属于 Agent 的策略，可以按同一反射协议修改。若 Agent 尚未声明谓词，宿主可以依据用户声明的任务指标提供明确标注为“临时比较”的比较结果；该比较不能算作 Agent 的成功谓词，在 Agent 采纳或修改它之前也不能触发保留或恢复。未发生采纳仍记为未验证。宿主不诊断原因、不选择修改对象、不发明固定的“什么算更好”规则，也不成为独立的语义审批者。

进化审视不设“不进化”的结局。每次进化审视都必须以至少一项 harness 自身修改结束：修改经被授权的反射操作生效或进入待生效，宿主为其建立验证窗口；审视结束时生效（或待生效）的自身定义必须不同于进入审视时的定义。可修改的对象包括组件、协调与编排、审阅方法，以及 Agent Loop 材料的管理策略（如上下文、memory 策略，见第六条之四）。修订现有组件或策略即满足本条，不要求每次新建组件；恢复到先前版本也是一次可见的修改（第八条）。退出接口不得提供零改动结案的路径，宿主也不得把零改动记录为一种正常的审视结果。

这一要求由宿主在结构上保证：出现符合条件的修改之前不提供结案操作，而不是让 Agent 提交后再被拒绝。宿主不判断修改是否值得、方向是否正确，也不指定、代拟或生成修改；改什么、怎么改、预期影响什么完全由 Agent 决定。窗口到期后的保留或恢复只核对 Agent 已声明的谓词与事实，不能被宿主另行改写成固定采纳政策。预算耗尽、运行中断，或审视达到用户合同规定的上限时，宿主可以机械结束审视，但必须如实记为未完成的审视，不得记为 Agent 的进化结果或“无需修改”。

必须修改不等于修改有效。不能用强制新增组件、固定修改数量或宿主代拟的候选冒充进化；修改是否带来改进，仍须由后续运行和验证窗口检验（第六章）。

### 第五条之一：限制性条目由宿主产生和维护，Agent 负载最小化

Agent 的注意力、上下文和调用预算应集中在任务执行、自我审阅和自我进化本身。结案字段与取值、证据引用、验证窗口的基线、指标引用、范围与到期边界、审视边界与工作归属、条件楼层、下一任务的供给与切换、预算、恢复与重试等管理性和限制性条目，即使设计者认为必要，也应由外部程序或运行时等宿主依据客观运行事实产生、填充和维护，而不是要求 Agent 生成、记住或拼装。

设计者应尽量减少和规避要求 Agent 遵守的限制性条目。确需保留的约束，应由宿主机械保证：从运行事实自动取值或补全，在结构上使其无法被违反，而不是把它写成 Agent 的输入义务，再在事后拒绝。Agent 只表达宿主无法代替的内容：修改哪里、改成什么、预期影响，以及它如何解释证据。

宿主承担这些条目，不等于宿主替 Agent 作进化决定，第五条与第九条仍然适用。宿主产生的是事实、边界和簿记，不是诊断、关注对象或采纳判断。Agent 的表达不完整时，宿主以可见的方式机械补全，或按未完成结案并回到工作，不得让 Agent 在合同上反复被拒、空转消耗预算。

新增机制须报告它给 Agent 增加了哪些输入义务。把宿主能够产生或维护的条目转嫁给 Agent，按未满足本条处理。

### 第六条：完整工作架构及其改进过程属于可建模的自身

Loop Engineering 的对象是围绕任务运行的完整闭环架构。Agent 可以按任务需要构建和调整 Workflow，包括分工、协调、状态与反馈关系。审阅自身、发现机会、设计改变、实验、评价、保留或修订是自我进化循环，可以作为整体 Loop 的一部分。整体架构、任务运行方式和自我进化循环都应能在同一个自身模型中定位。

用户开放相应权限后，Agent 应能够审阅并调整实际工作架构，也能修改用于改进它的方法。初期实现可以从组件或局部审阅工作流开始，验收声明须标明实际覆盖的范围。

**本阶段单任务策略实验的限定例外：** 暂缓把进化策略本身暴露为反射对象。固定的、任务中立的入口方法可以要求 Agent 全面考虑可写部分，但不得替 Agent 选择对象、顺序、拟议改变、指标解释或采纳。Agent 的任务工作流以及审阅证据和方法仍然可写。报告不得声称固定入口策略本身已经进化。

### 第六条之一：Agent 定义并改进自身的工作架构

Agent 可以承担自身的 Architect 角色，提出、组织、试验和修订任务中的工作架构。其审阅对象可以是 Workflow 或 Loop 的整体行为、Orchestration 的协调策略、内部组件及其关系，也可以是自身用于改进它们的审阅方法。Agent 在第四条界定的审阅对象之内决定审阅范围、证据、修改与验证方法，并在验证后决定保留或恢复。获得对应权限后，它可以通过同一反射协议修改实际生效的部分。

运行时提供实际对象关系、任务阶段、原始执行事实（包括第四条所述的过程事实）、版本、预算和受控实验能力。在本阶段单任务策略实验中，前述固定入口方法属于限定例外：它可以要求全面考虑可写部分，但不得选择对象、顺序、拟议改变、指标解释或采纳；任务工作流和审阅证据/方法仍可由 Agent 修改，且不得声称该入口策略已经进化。具体诊断、分类、指标及其解释属于 Agent 的方法。领域适配器可以提供该领域的观测和执行入口，宿主不得据此为 Agent 固定诊断策略、审阅顺序或采纳规则。替换一个检查器或审阅工作流，可以验证相应的反射与执行能力。要验收 Meta Harness，还需观察 Agent 如何对其工作架构或工作方式建模、形成或检验替代方案，并根据证据选择。

### 第六条之二：对象类别与审阅层级分开

类别描述对象在运行中的性质，例如 Skill、Tool、Workflow 或进化方法。Mirror 根据实际运行结构呈现类别和关系。审阅层级描述 Agent 本轮选择的分析范围和组织方式，可以审阅单个对象、若干对象或它们的组合，也可以把自身审阅方法纳入审阅。同一层级可包含不同类别，同一对象也可在不同审阅范围中出现。不得把一套固定层级、类别排序或逐级审阅流程写进宿主。

审阅选择必须能追溯到实际的自身对象和证据。用户授予的权限附着于对象和操作。改变审阅分组、分类名称或所选证据不改变权限。

### 第六条之三：架构和策略的修改必须影响后续运行

新版工作架构或策略在约定边界实际运行。它决定的角色关系、调度、状态流、反馈，或审阅选择，应当进入对应的后续调用和判断，并可由执行回执追溯到版本。试验可以在受控范围内运行，试验结果由 Agent 解释，生效仍经被授权的反射操作。运行时执行权限、预算、版本、接口和隔离约束。

审阅工作流、单次诊断结果、任务产物和实际工作架构是可分别追溯的对象或证据。报告应说清变更发生在哪个范围，以及哪条后续运行关系实际受它影响。

### 第六条之四：Agent Loop 相关材料经由管理策略进化，而非直接编辑内容

上下文、memory，以及其他由 Agent Loop 在逐步调用中使用的工作材料，是 harness 中直接决定任务质量的关键部分，属于可进化的自身。它们与 Loop Engineering 不同：Loop Engineering 是构建、调整和验证围绕任务的完整闭环工作架构（决策、状态、执行、评估、反馈与重构）；本条约束的是 Agent Loop 使用的材料如何被管理和组织，而不是如何设计那套闭环架构。

对这类材料，Agent 进化的对象是管理策略与组织策略，以及实现这些策略、整合和控制它们的工具与方法：选取或写入哪些来源、如何压缩或摘要、如何索引、排序与分区、保留多久、何时取回被省略的内容。Agent 不直接逐条编辑某一次请求中的上下文内容或 memory 条目，也不手工搬运、删改这些材料的具体内容。

运行时按当前生效的策略为每次请求组装上下文、管理 memory 及其他同类材料，并如实记录结果（包含与省略了哪些部分、各部分规模、截断与取回），供 Agent 观察策略与任务质量之间的关系；策略修改经反射生效，并可归因到后续请求。这样 Agent 以较轻的负载获得更大的灵活性，专注于改进策略本身，而不被具体、繁琐的内容搬运占用。任务简报、工具定义和当前轮次等保底内容由运行时保护，不因策略修改而丢失。

## 第三章：直接反射与热修改

### 第七条：修改直接指向自身

对 Agent 来说，自我修改是针对自身内部部分的一次反射操作。修改成功应意味着它已在约定边界对同一 Agent 生效，并可在随后执行和自身视图中观察。无需 Agent 再执行“写文件—提交 Binder—绑定—挂载—激活”等第二套操作。

实现可以使用持久化、版本记录、快照或内部适配，但这些是反射操作的底层实现细节，不能把外部文件变成 Agent 实际修改对象，也不能将“已保存但未生效”报告为“已修改自身”。接口应尽可能简洁；不为每一种内部部分增设一串专用管理动作。

### 第八条：生效语义必须明确且一致

反射操作必须定义其原子边界、何时影响后续行为，以及正在执行的工作如何与版本对应。修改尚未生效时，结果和自身视图必须明确标记；已生效后，后续执行不能暗中沿用旧值。正在进行的工作可按明确的版本语义完成，必要的状态迁移由底层处理，并能归因到对应版本。

失败不得静默退回旧实现却向 Agent 报告成功。恢复旧版本也应是对自身的一次可见修改，而不是把历史状态伪装为从未发生过。

### 第九条：权限约束不能变成第二个决策者

用户定义的不可修改边界必须由运行时执行，Agent 不能自行提升写权限。对于边界内的合法修改，底层只能按照既定技术约束接受或明确失败，不能在 Agent 已作决定后另行根据“是否值得优化”选择是否让它生效。

## 第四章：适用范围与演进

### 第十条：通用机制先于领域补丁

ARC、coding、PPT、视频生成中的任务状态和可优化部分各不相同，但自身视图、权限分配、审阅、反射、生效归因与进化证据应共享同一套概念。领域适配只提供其真实的对象部分和运行状态，不复制一套独有的自我进化协议。

范围逐步开放时，可以从 harness 组件开始，再延伸至角色协作、Orchestration、状态与反馈关系、整体 Workflow 和 Loop，以及进化循环自身。每一步须维持完整 Agent 根对象的语义。局部能力的证据不能代替整体工作架构可构建、可重构的证据。

### 第十条之一：任务相关逻辑只存在于适配层

本项目是在线自进化的通用方案：同一套 Agent 与自进化核心会运行 ARC 游戏、视频生成、PPT 生成、coding 等不同任务。凡是针对具体任务或具体模型的适配与任务相关逻辑，包括任务的观测与执行入口、产物格式与渲染、领域验收与客观指标的采集、任务资产与快照、模型或 provider 的 schema 与调用差异，都只能放在适配层（adapter），不得纳入自进化的核心策略。

自进化核心（自身对象与视图、审阅、反射与热修改、生效归因、验证窗口与进化证据的簿记）只认识通用概念：任务、单元或边界、运行事实、指标、组件与编排。核心代码、核心提示词与核心合同中不得出现某一任务的名称、字段、阶段、启发式或特判分支；接入新任务时只新增或修改适配器，不改核心策略。若某个新任务暴露出核心缺少的通用能力，应将其抽象为与任务无关的机制后再进入核心，而不是在核心里为该任务加一个分支。

### 第十一条：抽象必须由实际因果关系支持

反射接口可借鉴元对象协议的因果连接、反射塔对自身机制的表示，以及 Erlang 风格的版本共存和热替换；借鉴的是满足本项目目标的具体机制，而不是名称。新的 registry、binder、selector、controller、manager 或额外审批阶段，只有证明它解决不可由现有对象/反射路径解决的实际问题时才可引入。

## 第五章：禁止的退化形式

以下实现即使功能测试通过，也不符合本宪法：

| 退化形式 | 识别标准 |
| --- | --- |
| 孤立组件优化 | 只有组件路径和操作，没有它与 Agent 整体、其他部分及实际行为的关系。 |
| 静态清单冒充自身对象 | 枚举可写文件或配置项，却无法映射到当前生效的自身结构。 |
| 手动 `inspect` 冒充自身视图 | Agent 必须主动发现、调用和拼装自我信息，漏调用时整个审阅路径消失。 |
| 提示词冒充系统保证 | prompt 要求全面审阅，但没有覆盖、生效版本、权限和执行一致性的技术机制。 |
| 文件修改再装配 | Agent 改了文件还需经 Binder、路由或人工激活，写入与自身行为可能分离。 |
| 宿主替 Agent 决定进化 | 用户已授权、接口合法，宿主仍以独立的优化偏好决定是否采用。 |
| 任务失败修补器 | 只根据当前失败的轨迹修改局部组件，忽略其他可优化部分和阶段性需求。 |
| 局部循环冒充整体 Loop | 用组件调用、重试或单段自我审阅循环代表 Agent 围绕任务形成的完整闭环架构。 |
| 组件组合冒充整体 Workflow | 只描述工具与 Skill 的排列，省略工作架构中的决策、分工、状态、协调和反馈。 |
| 工作流热替换冒充 Meta Harness | 只证明某段审阅流程换成了新版，没有观察到 Agent 如何审阅、构建或检验自己的工作方式。 |
| 领域特例堆叠 | ARC、coding、PPT、视频各有独立的反思提示词、专用开关和装配流程。 |
| 任务逻辑侵入核心 | 核心代码、核心提示词或核心合同中出现某一任务（如 PPT、ARC、视频）或某一模型的名称、字段、阶段、启发式或特判分支；接入新任务需要修改自进化核心而不只是适配器。 |
| 运行时诊断冒充 Meta | 宿主固定审阅层级、关注对象、领域指标或改进决策，Agent 只能使用这些现成规则。 |
| 修改分析结果冒充修改分析方法 | Meta 版本或输出文本改变，后续审阅仍使用原有的对象选择、证据组织或试验机制。 |
| 接口层层转发 | 为实现一次自身修改引入多个未承担独立职责的对象、策略选择器和管理阶段。 |
| 管理负担转嫁给 Agent | 宿主能从运行事实产生或维护的结案字段、验证窗口、证据引用、条件或任务切换，被写成 Agent 必须正确填写的输入，填错即被拒绝，Agent 在合同上反复空转而无法推进任务或进化。 |
| 直接编辑 Agent Loop 材料冒充策略进化 | Agent 通过逐条删改、搬运或重写某次请求的上下文内容或 memory 条目来“优化”这些材料，而不是修改决定它们如何被管理与组织的策略；或这类策略写死在运行时、不能被 Agent 反射修改。 |
| 可以选择不进化 | 进化审视可以在没有生效或待生效的自身修改时结案；退出接口存在不改动即可调用的路径；或宿主把零改动记为“无需修改”“no_change”之类的正常审视结果。 |
| 交付件评估冒充自我审视 | 审视只给交付件打分或判定合格，没有把质量不足追溯到产生它的 harness 环节、组件或策略；审视视图中过程事实缺席或只剩汇总；或审视以“交付件合格”为由不改进自身。 |
| 提交节奏绕过审视边界 | 计数边界只由 Agent 的提交动作决定，Agent 先完成全部工作再连续提交，即可使审视被合并或跳过；或为划定边界要求 Agent 自行声明工作归属。 |
| 形式上的进化 | 仅凭产生新文本、组件版本、离线测试通过就宣称 Agent 自主改进；或为满足必须修改而做出不改变生效定义的空修改。 |

## 第六章：工程验收与证据

任何实现或实验都应分别报告四类证据，不能用前一层替代后一层：

1. **对象与权限：** 从同一个运行实例生成自身视图；可写/不可写部分及操作由用户配置决定；未经授权的改动被程序机制拒绝。
2. **实际生效：** 对某一内部部分反射后，在同一 Agent 生命周期的约定边界，后续执行使用新行为；视图、版本和执行归因一致。失败明确可见。
3. **自主审阅与采纳：** 在没有外部强制指定修改目标的真实任务中，Agent 看到了完整可优化范围、本段过程事实和交付件质量事实，依据任务阶段形成面向自身过程的审阅，并把交付件质量的不足追溯到相应的自身部分，选择修改什么、如何修改，并实际按决定行事；每次进化审视都以至少一项生效或待生效的自身修改结束，验证窗口到期后由宿主依据 Agent 声明的成功谓词对已入账事实机械求值，未满足则恢复、满足则保留。
4. **净效果：** 比较任务质量、资源成本、长期稳定性与跨场景迁移；成功案例与负面结果均记录。功能测试或脚本提供者仅能证明前两层的局部机制，不能证明自主进化或能力提升。

验收要按实际改变的范围报告。组件替换、审阅工作流替换、整体工作架构重构需要各自的证据。系统级 Workflow 或 Loop 的验收应指出 Agent 构建或改变了哪条真实的组织、状态、控制或反馈关系，并验证后续执行实际经过该关系。Meta Harness 的验收还需观察 Agent 如何将其工作方式作为对象，形成或比较方案并依据结果决定。定向实验可以证明调用与生效，普通任务用于观察自主构建与采用。跨任务适用性和净收益分别验证。

新增机制还应检验其本身的运行负担：额外上下文、调用次数、延迟、误触发，以及要求 Agent 产生和维护的条目（见第五条之一）。实验报告还应列出进化审视的次数与时机、每次审视的修改及其验证窗口、机械结束的审视，以及计数边界是否随实际工作出现。真实实验中若审阅无法触发、修改无法生效或能力退化，应按未满足相应条款处理，而不是补一条只适用于该任务的提示词。

## 适用关系

此前的《Autoresearch Pi Kernel — Minimal Mutation Design & Implementation Constitution》限定的是 **Pi 最小运行时修改能力**的局部里程碑，明确暂不设计自我进化。本文规定的是更上层的**完整 Agent 自我进化目标**。局部最小实现可作为本文的一块基础，但不能用“已证明 Pi 可修改”代替完整自身对象、自身审阅、直接反射和自主进化的验收。

早期实验使用的 `evolution_loop` 指实验中的局部自我审阅工作流。它可被反射修改并实际执行新版，属于局部能力证据。项目对 Architecture、Workflow、Loop、Architect、Orchestration 和 Meta Harness 的用词，以本版术语定义为准。


### 1.9 amendment - thin Agent-facing surface

The Agent-facing meta-harness surface is thin. Runtime and base services own legal vocabularies, field matching, normalization, validation, request assembly, review and window bookkeeping, interpretation, defaults, and host floors. The Agent authors concrete component content and orchestration intent; it does not construct internal policy token lists or adjudicate host bookkeeping.

A mechanism is complete only when its runtime surface states what the Agent may operate and gives the name, meaning, current value, and required resources for each writable item. Internal composition sections and bookkeeping fields are not writable knobs. Validation failures normalize at the boundary or return an actionable same-turn correction surface. This preserves 1.8 success predicates, mechanical host evaluation, and restore on failure.
