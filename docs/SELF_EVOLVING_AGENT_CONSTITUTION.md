# 自进化 Agent 设计宪法

**版本：** 1.2（2026-11-10）  
**性质：** 目标架构与工程验收约束；不是当前代码能力声明。  
**适用范围：** Agent 自身视图、可修改性建模、运行时反射、自我审阅、自我进化及其在 ARC、coding、PPT、视频等任务中的实现。

## 序言：研究对象与目标

本项目将**同一个正在运行的 Agent 及其完整运行架构**视为自我审阅和自我修改的对象。Agent 在用户授权范围内，围绕任务形成并调整自己的工作架构。组件、模型与角色、调度、状态、上下文、评估和自我改进机制，都是这套架构的一部分。

用户定义这个 Agent 的哪些部分可读、哪些部分可修改，以及允许的修改操作。基础设施将实际运行状态构造成可信的自身视图，并在任务过程中提供给 Agent。Agent 依据自身视图和当前任务阶段，决定是否以及如何改进自己；被授权的修改通过反射作用于自身，并影响后续运行。

**核心判据：Agent 审阅的对象、修改的对象与实际执行的对象，必须是同一个 Agent 的同一套运行结构。**

本宪法规范目标和不能跨越的设计边界。某项能力尚未实现时，必须如实标记缺口；不能以提示词、配置清单或离线测试代称其已经实现。

## 核心术语与系统范围

Architecture、Workflow 和 Loop 都可以指向同一个 Agent 的**系统级运行安排**。三者分别强调结构、任务推进和反馈。Architect 指构建者的角色，Orchestration 指运行中的协调机制。这些术语不规定必须拆成五个模块或另设 Agent。

| 概念 | 在本项目中的定义 |
| --- | --- |
| **Agent Architecture** | Agent 如何组织成一个可运行系统，包括有哪些角色、模型和组件，谁掌握状态与决策权，信息和控制如何流动，如何执行、评估、反馈和重构。运行时架构是这些关系在某一任务阶段的实际生效形态。它覆盖受保护的底座与用户可授权调整的部分。 |
| **Architect** | 根据目标、资源和约束构建、比较和修订架构的角色。本项目让 Agent 在执行任务时也能承担自身的 Architect 角色。它可以决定是否分工、设置何种决策与反馈边界，以及在证据变化后如何重构。该角色可以由同一个 Agent 承担。 |
| **Workflow** | Agent 为达成任务目标构建并实际运行的工作架构。它包括如何形成工作结构、如何分工、何时并行或顺序执行、如何保存和传递状态、如何验证与交付，以及何时依据进展重新组织自身。Architecture 描述这套系统如何组织，Workflow 描述这套组织如何随任务阶段运转。 |
| **Orchestration** | 在运行中协调角色、模型、组件、状态与工作进度的机制。它负责把工作分派、依赖、同步、预算、交接和反馈落实为实际执行。Architect 决定采用或修改怎样的组织与协调规则，Orchestration 按生效规则推进。调度、路由和协作策略本身可以是 Agent 获授权后重新设计的对象。 |
| **Loop** | 从反馈角度看同一套 Workflow。执行结果、环境变化和评估回到决策，并可能改变下一步行动、工作分工、状态组织乃至后续运行结构。交付前可以经历多个相互关联的反馈循环。 |
| **Loop Engineering** | 构建、调整和验证上述闭环工作架构，涉及决策、状态、执行、评估、反馈与重构如何共同运转。组件调用循环、局部重试和自我审阅循环都是可以纳入其中的机制。 |
| **Harness 与 Harness Components** | Harness 提供 Agent 运行所需的能力、资源、接口与约束。Tool、Skill、观察器和评估器等是其中可独立定位的组成部分。组件如何组合是 Workflow 的一部分，整体工作方式还包括决策权、协作、状态、控制和反馈。 |
| **自我进化循环** | Agent 根据执行证据审阅自己的组件、工作方式或运行架构，提出并验证变化，再决定是否保留。它可以嵌入任务 Workflow，并对后续 Workflow 生效。 |
| **Meta Harness** | Agent 对自身工作方式和运行架构进行建模、比较、构建和改进的能力。其对象可以是组件、协调策略、Workflow、Loop，或 Agent 用来审阅和改进它们的方法。Meta 由审阅与改进所针对的对象及实际行为界定，无需对应一个独立模块。 |

任务运行中选用已有规则、生成一份计划、按授权改变工作结构，是不同的行为。架构重构的证据来自实际角色、决策权、状态流、控制流或反馈关系的变化，以及后续运行使用了这些变化。同一个任务内形成的工作架构可以是有效的动态组织。若要声称形成了跨任务可复用的自我进化，还需另验后续采用与效果。

## 第一章：自身对象

### 第一条：根对象唯一

架构以完整 Agent 实例为根对象。组件等是其内部可定位的部分，须能表达其所属关系、依赖关系、生效版本与运行职责。不能把“可优化对象”建成与 Agent 脱节的一组独立文件、候选项或外部服务。

当前可以先支持少数部分，但根对象和部分之间的关系从第一阶段就必须成立。新增可优化范围，应是扩展同一对象模型，而非为每个领域另建一套自进化系统。

### 第二条：可见性和可写性分离

用户配置定义自身哪些部分可修改、允许何种操作；不可修改部分仍应在适当的可见范围内呈现其作用、关系及不可修改的原因，以便 Agent 理解自己的边界。某部分不可写，不意味着它从自身视图中消失。

可修改范围是对 Agent 内部部分及操作的权限分配，不是把一张“活跃组件表”变成执行路由、Binder 映射或安装队列。用户配置不能代替对象本身。

### 第三条：自身视图与运行结构因果相连

自身视图必须源于实际运行中的 Agent：显示当前生效的部分、关系、版本、权限、关键状态与执行归属；修改生效后，视图同步呈现修改后的运行事实。必要时可以有紧凑摘要和按需展开，但摘要必须能追溯到完整的自身模型，不能以当前任务碰巧使用的组件集合充当“整个自己”。

宿主底层服务自动产生并向 Agent 提供自身视图。Agent 不应依靠记得调用 `inspect`、翻目录或主动拼装配置，才知道自己有哪些可优化部分。自我认知不能只靠 prompt 描述：权限、版本、视图与运行行为的一致性需要程序机制保证。

## 第二章：自我审阅与进化决策

### 第四条：任务推进经过自身审阅

在任务窗口的合适阶段，Agent 应获得当前任务状态与完整可优化范围的自身视图，并形成可追溯的自我审阅结果：当前哪些内部部分值得关注、为什么、是否要改、若改预期影响什么。审阅可采用分层视图和摘要，不能要求每一步重新展开全部代码或强迫每一步都修改。

任务失败、成功轨迹、执行成本和用户反馈是审阅证据，不是审阅范围的上限。审阅应同时考虑当前阶段的目标、后续任务的准备、能力短板、内部结构之间的制约，以及改进自身的方式是否仍然有效。

工程可以保证视图被提供、审阅步骤进入运行路径、覆盖范围和决定被记录；不能仅凭这些机制宣称模型内部已进行了充分思考。充分性还须由实际审阅内容与后续行为检验。

### 第五条：进化方向由 Agent 决定

在用户授予的范围内，Agent 决定是否修改、修改哪里、提出何种改变、如何实验以及如何利用反馈。宿主只机械执行预先定义的权限、接口契约、并发版本和状态一致性约束，不另设一个具有独立优化目标的语义审批者。

不修改也是允许的审阅结果。不能用强制生成候选、强制新增组件或固定修改次数，伪装进化路径已经触发。

### 第六条：完整工作架构及其改进过程属于可建模的自身

Loop Engineering 的对象是围绕任务运行的完整闭环架构。Agent 可以按任务需要构建和调整 Workflow，包括分工、协调、状态与反馈关系。审阅自身、发现机会、设计改变、实验、评价、保留或修订是自我进化循环，可以作为整体 Loop 的一部分。整体架构、任务运行方式和自我进化循环都应能在同一个自身模型中定位。

用户开放相应权限后，Agent 应能够审阅并调整实际工作架构，也能修改用于改进它的方法。初期实现可以从组件或局部审阅工作流开始，验收声明须标明实际覆盖的范围。

### 第六条之一：Agent 定义并改进自身的工作架构

Agent 可以承担自身的 Architect 角色，提出、组织、试验和修订任务中的工作架构。其审阅对象可以是 Workflow 或 Loop 的整体行为、Orchestration 的协调策略、内部组件及其关系，也可以是自身用于改进它们的审阅方法。Agent 决定审阅范围、证据、验证方法，以及是否采纳。获得对应权限后，它可以通过同一反射协议修改实际生效的部分。

运行时提供实际对象关系、任务阶段、原始执行事实、版本、预算和受控实验能力。具体诊断、分类、指标及其解释属于 Agent 的方法。领域适配器可以提供该领域的观测和执行入口，宿主不得据此为 Agent 固定诊断策略、审阅顺序或采纳规则。替换一个检查器或审阅工作流，可以验证相应的反射与执行能力。要验收 Meta Harness，还需观察 Agent 如何对其工作架构或工作方式建模、形成或检验替代方案，并根据证据选择。

### 第六条之二：对象类别与审阅层级分开

类别描述对象在运行中的性质，例如 Skill、Tool、Workflow 或进化方法。Mirror 根据实际运行结构呈现类别和关系。审阅层级描述 Agent 本轮选择的分析范围和组织方式，可以审阅单个对象、若干对象或它们的组合，也可以把自身审阅方法纳入审阅。同一层级可包含不同类别，同一对象也可在不同审阅范围中出现。不得把一套固定层级、类别排序或逐级审阅流程写进宿主。

审阅选择必须能追溯到实际的自身对象和证据。用户授予的权限附着于对象和操作。改变审阅分组、分类名称或所选证据不改变权限。

### 第六条之三：架构和策略的修改必须影响后续运行

新版工作架构或策略在约定边界实际运行。它决定的角色关系、调度、状态流、反馈，或审阅选择，应当进入对应的后续调用和判断，并可由执行回执追溯到版本。试验可以在受控范围内运行，试验结果由 Agent 解释，生效仍经被授权的反射操作。运行时执行权限、预算、版本、接口和隔离约束。

审阅工作流、单次诊断结果、任务产物和实际工作架构是可分别追溯的对象或证据。报告应说清变更发生在哪个范围，以及哪条后续运行关系实际受它影响。

## 第三章：直接反射与热修改

### 第七条：修改直接指向自身

对 Agent 来说，自我修改是针对自身内部部分的一次反射操作。修改成功应意味着它已在约定边界对同一 Agent 生效，并可在随后执行和自身视图中观察。无需 Agent 再执行“写文件—提交 Binder—绑定—挂载—激活”等第二套操作。

实现可以使用持久化、版本记录、快照或内部适配，但这些是反射操作的底层实现细节，不能把外部文件变成 Agent 实际修改对象，也不能将“已保存但未生效”报告为“已修改自身”。接口应尽可能简洁；不为每一种内部部分增设一串专用管理动作。

### 第八条：生效语义必须明确且一致

反射操作必须定义其原子边界、何时影响后续行为，以及正在执行的工作如何与版本对应。修改尚未生效时，结果和自身视图必须明确标记；已生效后，后续执行不能暗中沿用旧值。正在进行的工作可按明确的版本语义完成，必要的状态迁移由底层处理，并能归因到对应版本。

失败不得静默退回旧实现却向 Agent 报告成功。恢复旧版本也应是对自身的一次可见修改，而不是把历史状态伪装为从未发生过。

### 第九条：权限约束不能变成第二个决策者

用户定义的不可修改边界必须由运行时执行，Agent 不能自行提升写权限。对于边界内的合法修改，底层只能按照既定技术约束接受或明确失败，不能在 Agent 已作决定后另行根据“是否值得优化”选择是否让它生效。

## 第四章：适用范围与演进

### 第十条：通用机制先于领域补丁

ARC、coding、PPT、视频生成中的任务状态和可优化部分各不相同，但自身视图、权限分配、审阅、反射、生效归因与进化证据应共享同一套概念。领域适配只提供其真实的对象部分和运行状态，不复制一套独有的自我进化协议。

范围逐步开放时，可以从 harness 组件开始，再延伸至角色协作、Orchestration、状态与反馈关系、整体 Workflow 和 Loop，以及进化循环自身。每一步须维持完整 Agent 根对象的语义。局部能力的证据不能代替整体工作架构可构建、可重构的证据。

### 第十一条：抽象必须由实际因果关系支持

反射接口可借鉴元对象协议的因果连接、反射塔对自身机制的表示，以及 Erlang 风格的版本共存和热替换；借鉴的是满足本项目目标的具体机制，而不是名称。新的 registry、binder、selector、controller、manager 或额外审批阶段，只有证明它解决不可由现有对象/反射路径解决的实际问题时才可引入。

## 第五章：禁止的退化形式

以下实现即使功能测试通过，也不符合本宪法：

| 退化形式 | 识别标准 |
| --- | --- |
| 孤立组件优化 | 只有组件路径和操作，没有它与 Agent 整体、其他部分及实际行为的关系。 |
| 静态清单冒充自身对象 | 枚举可写文件或配置项，却无法映射到当前生效的自身结构。 |
| 手动 `inspect` 冒充自身视图 | Agent 必须主动发现、调用和拼装自我信息，漏调用时整个审阅路径消失。 |
| 提示词冒充系统保证 | prompt 要求全面审阅，但没有覆盖、生效版本、权限和执行一致性的技术机制。 |
| 文件修改再装配 | Agent 改了文件还需经 Binder、路由或人工激活，写入与自身行为可能分离。 |
| 宿主替 Agent 决定进化 | 用户已授权、接口合法，宿主仍以独立的优化偏好决定是否采用。 |
| 任务失败修补器 | 只根据当前失败的轨迹修改局部组件，忽略其他可优化部分和阶段性需求。 |
| 局部循环冒充整体 Loop | 用组件调用、重试或单段自我审阅循环代表 Agent 围绕任务形成的完整闭环架构。 |
| 组件组合冒充整体 Workflow | 只描述工具与 Skill 的排列，省略工作架构中的决策、分工、状态、协调和反馈。 |
| 工作流热替换冒充 Meta Harness | 只证明某段审阅流程换成了新版，没有观察到 Agent 如何审阅、构建或检验自己的工作方式。 |
| 领域特例堆叠 | ARC、coding、PPT、视频各有独立的反思提示词、专用开关和装配流程。 |
| 运行时诊断冒充 Meta | 宿主固定审阅层级、关注对象、领域指标或改进决策，Agent 只能使用这些现成规则。 |
| 修改分析结果冒充修改分析方法 | Meta 版本或输出文本改变，后续审阅仍使用原有的对象选择、证据组织或试验机制。 |
| 接口层层转发 | 为实现一次自身修改引入多个未承担独立职责的对象、策略选择器和管理阶段。 |
| 形式上的进化 | 仅凭产生新文本、组件版本、离线测试通过就宣称 Agent 自主改进。 |

## 第六章：工程验收与证据

任何实现或实验都应分别报告四类证据，不能用前一层替代后一层：

1. **对象与权限：** 从同一个运行实例生成自身视图；可写/不可写部分及操作由用户配置决定；未经授权的改动被程序机制拒绝。
2. **实际生效：** 对某一内部部分反射后，在同一 Agent 生命周期的约定边界，后续执行使用新行为；视图、版本和执行归因一致。失败明确可见。
3. **自主审阅与采纳：** 在没有外部强制指定修改目标的真实任务中，Agent 看到了完整可优化范围，依据任务阶段形成审阅，选择修改或保持，并实际按决定行事。
4. **净效果：** 比较任务质量、资源成本、长期稳定性与跨场景迁移；成功案例与负面结果均记录。功能测试或脚本提供者仅能证明前两层的局部机制，不能证明自主进化或能力提升。

验收要按实际改变的范围报告。组件替换、审阅工作流替换、整体工作架构重构需要各自的证据。系统级 Workflow 或 Loop 的验收应指出 Agent 构建或改变了哪条真实的组织、状态、控制或反馈关系，并验证后续执行实际经过该关系。Meta Harness 的验收还需观察 Agent 如何将其工作方式作为对象，形成或比较方案并依据结果决定。定向实验可以证明调用与生效，普通任务用于观察自主构建与采用。跨任务适用性和净收益分别验证。

新增机制还应检验其本身的运行负担：额外上下文、调用次数、延迟和误触发。真实实验中若审阅无法触发、修改无法生效或能力退化，应按未满足相应条款处理，而不是补一条只适用于该任务的提示词。

## 适用关系

此前的《Autoresearch Pi Kernel — Minimal Mutation Design & Implementation Constitution》限定的是 **Pi 最小运行时修改能力**的局部里程碑，明确暂不设计自我进化。本文规定的是更上层的**完整 Agent 自我进化目标**。局部最小实现可作为本文的一块基础，但不能用“已证明 Pi 可修改”代替完整自身对象、自身审阅、直接反射和自主进化的验收。

早期实验使用的 `evolution_loop` 指实验中的局部自我审阅工作流。它可被反射修改并实际执行新版，属于局部能力证据。项目对 Architecture、Workflow、Loop、Architect、Orchestration 和 Meta Harness 的用词，以本版术语定义为准。
