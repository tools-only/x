# Parent capability decisions after periodic review

The real-provider run `arc-skill-semantic-real-provider-20260922-171012`
recorded a parsing/localization/planning opportunity but submitted only memory.
Omitted components became runtime-default deferrals. Research handoff timeout
and the absent structured child report left no independent authoring followup.

This change derives durable capability followups from committed review records.
Runtime-default omission is unresolved, not a parent judgment. The parent receives
the same queue through inspect and subsequent Pi context projection, including
after restart and research deferral. Each item carries the original opportunity,
exact evidence references, and a callable capability_review entry point.

Parent workflow:

1. Decide whether a procedure, computation, or isolated context is worthwhile.
2. Read the corresponding fixed creator and submit parent-authored content through
   change; direct creation does not require research or a live review window.
3. Assemble applicable exact versions, read/invoke them, then assess actual output.
4. Record reuse with existing eligible component references, or explicit defer /
   not_applicable with a concrete reason (including when to reconsider).

The decision endpoint cannot author components. It rejects implicit omissions,
unknown references, wrong component types, and ineligible versions. A recorded
decision is not proof of utility. Authored but unselected capabilities receive a
bounded parent-context reminder with exact references; selection stays with main.

Single-situation procedures remain valid Skills. No component quota, automatic
semantic conversion, automatic assembly, research prerequisite, or environment
action gate is introduced. Explicit deferral remains a legitimate parent decision;
reactivation is currently parent-owned, rather than inferred from free text.

Validation uses the native Pi diagnostic fixture to exercise actual tool dispatch,
context projection, invalid decision repair, research deferral and parent restart.
It does not establish real ARC closure or real-provider method quality. The prior
child-report delivery failure and review wall-clock expiry remain separate issues;
this change ensures direct parent capability work does not depend on their success.
Deferred B/C/D acceptance items remain open.

## Procedural guidance

`demo/prompts/capability_extraction_process.md` supplies a task-independent process:
identify the operation behind experience, separate instance data and method, define
an executable contract, choose a carrier, author and enable, then exercise and
revise. Each step has a completion criterion. It prescribes no task algorithm,
observation heuristic, game representation or concrete solution. The parent
receives it during a pending periodic review or capability followup, through the
actual Pi context hook. Component-specific authoring stays with existing creators.
Provider-context assertions verify delivery, not the model's semantic compliance.
