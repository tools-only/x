# ARC 单局在线自进化 v3：上下文，而非控制

日期：2026-11-25 起草，2026-11-26 按用户决定改写（Asia/Shanghai）。状态：设计，未实现。分支：`codex/arc-evo-middle-layer`。
上游：[自进化设计 v2](2026-11-24-arc-layered-self-evolution-design.md)（与本文冲突处以本文为准，v2 的实施记录保留）；
设计基准：`docs/harness-design-principles.md`。

## 0. 原则与边界

### 0.1 上下文，而非控制

宿主不冻结、不拒绝、不强制 agent 回复。宿主只做三件事：

1. **诊断上下文**：把轨迹和结果摆在 agent 面前，让它自己看出哪里不足、哪里做对了，并归因到自己能力的某一部分。
2. **转化路径**：agent 写一个固定类型的文件，宿主立即装上，这条结论就变成一项能力。
3. **能力暴露**：后续执行时，明确告诉 agent 它有哪些能力、各自战绩如何、本步哪些能力起了作用。

agent 可以忽略任何一条材料；忽略本身会出现在下一次复盘里。

### 0.2 宿主与 agent 的分工

判别法：凡是体现“ARC 游戏长什么样”的判断（计数条、物体、目标、危险、怎么探索、何时止损），或换一个游戏就要改
宿主代码的东西，都归 agent 进化；宿主只写对任何网格游戏一视同仁、不含解题判断的东西。

| 归宿主（固定、通用、机械） | 归 agent（在线进化，只在本局有效） |
|---|---|
| 记录每次决策的动作和结果；按格子统计变化 | 判断哪些格子是计数条、什么算同一局面（`state_key`） |
| 执行 agent 写的规则、模型、程序，原样回显结果 | 规则、预测模型、目标与危险判断 |
| 压缩轨迹、计算线索、在固定时机发复盘材料 | 从复盘里看出问题、归因、决定改什么 |
| 装载 `work/` 下的文件，维护能力清单和战绩 | 写什么能力、保留还是删除 |
| 上下文裁剪的稳定性；裁剪后放回 agent 的笔记 | 笔记里写什么 |
| 预算、RESET 永远可用、完整性检查 | 自己的打法、止损和动作守卫 |

### 0.3 本方案删除的控制

- 冻结式评审：过关、第二次 GAME_OVER、长时间停滞、半程预算、同一动作重复三次、连续只看不动时冻结 `submit_actions`
  （`demo/arc_layered_python.ts` 中 `reviewRequired` 的各个来源和 `refuse("review required…")`）。
- `review()` 的必填项、`place`/`artifact` 放置声明，以及“声明的文件没写就不解冻”。
- 对评审产物的验收：存根 `world_model.py` 不解冻、claims 加载失败不解冻、从未适用的 claim 不解冻（`_probe_artifact`）。
- claims 被证伪或从未适用时冻结动作。
- `expect` 范围超过 16 格时直接拒绝。
- 系统提示里写死的方法：“回测好之前每批只走 1–3 步”“约十步内必须有回测数”等两条硬规则。

保留：预算、两次连续 RESET 需确认、GAME_OVER 后只能 RESET（游戏本身规则）、每次调用至多 16 个动作。

## 1. 问题与命题

### 1.1 材料

- 另一主机（基于更早提交）：同一动作/坐标循环；混淆关卡编号与预算；压缩 44/149/53 次，wa30 622 步压缩 148 次，

  token 约 1 千/动作，当前配置为 6.5 千–1.8 万/动作。high 档两臂都因 provider 长时间无响应在第 2 关开头终止，无结论。

  回测用最近 24 步做整帧精确匹配，不预测计数条的模型几乎全错。

### 1.2 根因

自进化闭环是：**看见问题 → 归因 → 写成能力 → 用上 → 量出效果 → 再修订**。现状断在三处：

1. **看不见问题。** 宿主给的是整帧口径的计数和冻结理由，没有轨迹，也没有把“重复”“裁剪后重做”“没预测到的死亡”
   和发生时刻、当时的笔记状态放在一起。agent 不知道自己在哪里打转、为什么打转。轻量校准说明：去掉证据后，
   agent 不会自己去找。
2. **归因没有落点。** 评审只问 action/rule/goal/representation 这类“游戏理解”层，不问“是我的记忆、方法还是工具出了问题”；
   结论的放置靠声明和冻结，写下的东西也不会再出现在 agent 面前。
3. **能力不被看见、不被量。** claims、world_model 是旁路，只出一行回测数；`work/lib` 下的程序不会被提起；
   宿主不区分动作是程序算出的还是手打的，因此说不清哪项能力起了作用。

此外，冻结把成本直接加在每个动作上（token/动作翻倍），而 never-applies 冻结这类负效应来自控制本身。

### 1.3 窄命题

在单局 ARC 游戏内，若宿主（a）在关卡结束和关内出事时给出压缩轨迹、线索、归因对照表和上一次复盘的核对，
（b）把四类文件即写即装，（c）在状态消息里列出能力清单与战绩，
那么 agent 会在复盘中指出具体的决策编号、把问题归到记忆/模型/方法/工具之一、改对应的文件，并且在下一关：

- 复盘时定下的核对数变好（例如裁剪后重复、最长无新局面步数）；
- 无效重复和每关动作数相对上一关下降；
- 程序算出的动作占比上升。

同时，过关数不低于当前配置，token/动作不高于当前配置。

### 1.4 减少的负担

- 去掉冻结、放置声明、产物验收这些记账往返。
- 去掉 agent 在裁剪后从帧重建认知的工作（笔记与能力清单被放回）。
- 去掉 agent 每次都要重新判断“我已经有什么”的工作（能力清单直接列出）。

### 1.5 推翻条件

- 三次运行中 agent 都不写 `REVIEW.md`、或写了但从不指出决策编号和能力部位：复盘材料不足以支撑归因，考虑把“当时的想法”
  补回轨迹（§3.7），而不是加冻结。
- 归因后改了文件，但下一关核对数连续两关都没改善：转化路径没有把结论变成有效能力，检查能力是否被调用（清单战绩）。
- 过关数低于当前配置，或 token/动作高于当前配置 1.3 倍：判负，关回。

### 1.6 范围与非目标

- 只做单局在线进化：不跨游戏，不跨 session，`work/` 只在本局存在。
- 不做独立进化循环、离线回放评估器、通用 artifact 注册表、宿主按规则拒绝动作。
- 暂不把 agent 在过程中的想法记入轨迹（§3.7）。
- 不改 ARC bridge 和动作语义；不改纯 Pi 基线。

## 2. 总览

```
 记录（宿主）            诊断上下文（宿主）          归因（agent）          转化（agent 写文件）
 每次决策：动作、结果、 ─→ 关卡复盘 / 关内小复盘 ─→ 卡在哪、归到 ─────→ claims / model.py /
 能力使用、笔记状态        压缩轨迹 + 线索 + 核对     记忆/模型/方法/工具    lib / GUIDE / WORKING
        ↑                                                                    │
        │                                                                    ↓
 战绩与核对（宿主） ←── 使用（agent 调用；宿主执行） ←── 能力暴露（宿主：清单、触发行、放回）
```

agent 的四个能力部位，是归因和转化的共同语言：

| 部位 | 含义 | 载体 |
|---|---|---|
| 记忆 | 记下并在需要时用上已知的事：已排除的做法、当前进度、跨关经验 | `work/WORKING.md`、`work/GUIDE.md` |
| 模型 | 对游戏的理解：局面怎么判断、动作会造成什么、什么会死、目标是什么 | `work/model.py`、`work/claims/*.py` |
| 方法 | 怎么探索、怎么排除假设、开局程序、何时换思路和止损、怎么复用上一关 | `work/GUIDE.md` 的打法部分 |
| 工具 | 可复用的程序：找物体、算路线、搜索、批量验证 | `work/lib/*.py` |

## 3. 诊断上下文

### 3.1 决策轨迹记录

agent 每调用一次 python 并真正执行了动作，记为一次决策。宿主记录：

| 字段 | 说明 |
|---|---|
| 编号、步数范围、关卡 | — |
| 之前只看不动的调用数 | 只看不动的调用不单独成条，合并到下一次决策 |
| 动作 | 动作名与坐标 |
| 结果 | 每个动作：是否出现新局面、是否死亡或过关、这个（局面，动作）之前试过几次、结果是否相同 |
| 能力使用 | 命中或失败的规则；`predict` 对错几格；动作是否由 `work/` 下的代码算出 |
| 标记 | 本次决策前发生了上下文裁剪；python 报错（类型） |
| 笔记状态 | 当时 `WORKING.md` 最后修改于第几步 |

记录写在 `harness/decisions.jsonl`，每关同时生成可读版 `work/replay/level_N.md`，agent 可以用 python 打开、搜索。

### 3.2 局面判断

“同一局面”默认按去掉 4 格边框后的棋盘内部判断（与现有 `stop_on_noop` 的口径一致）。agent 在 `work/model.py` 写了
`state_key(frame)` 时改用它。复盘里始终并列一个整帧口径的数，状态键写错时矛盾可见。

### 3.3 每步回显

每次动作的结果后面最多加三行，只在有事时出现：

- 重复：“这个局面下这个动作已试过 N 次，结果都一样”。
- 预测偏差：agent 写了 `predict` 时，“预测与实际差 K 格”。
- 死亡：致死动作；与本关上一次死亡是否同一局面、同一动作。

### 3.4 复盘材料

**关卡复盘**：过关、本关预算用完或局终时，在下一条状态消息里给出，约 1500 token 以内：

1. 第一行：上一次复盘定下的核对数及本关实际值（§3.6）。
2. 本关概况：动作、决策数、死亡、RESET、裁剪次数、报错次数、程序算出动作占比、预测准确率。
3. 压缩轨迹，规则如下：
   - 连续几次决策都在同一区域用同一种动作、并且都没有新局面，合并成一行，写明次数和期间出现了几个新局面；
   - 单独列出：第一次出现新类型的变化、每次死亡、上下文裁剪、最长一段无新局面、过关前的转折点；
   - 每行注明当时 `WORKING.md` 停在第几步；
   - 总行数不超过 15 行，其余见 `work/replay/level_N.md`。
4. 线索：只摆事实，每条对应归因表里的某一列（§3.5）。
5. 三个问题（§3.6）。

例（su15 第 2 关，未过）：

```
上次复盘你说：问题在方法；核对“最长无新局面 < 15 步”。本关实际：最长 52 步。

第 2 关复盘（预算用完）：210 步，84 次决策，死亡 4 次，裁剪 1 次，报错 7 次；程序算出 0%；无 predict
完整轨迹：work/replay/level_2.md
#1–#6   步 33–45   点击青色标记（6 次）→ 8 个青标记变成 4 个品红块，新局面 12 个
#7      步 46      点击品红块 → 死亡
#8–#21  步 47–98   点击品红块附近的黑格（14 次）→ 52 步只有 6 步出现新局面；
                   局面 B 下点(20,40) 试了 7 次，结果都一样；WORKING.md 一直停在第 40 步
#22     步 99      【上下文裁剪】
#23–#30 步 100–130 → 11 个（局面，动作）在裁剪前已经试过
#31     步 131     点击(30,12) → 死亡，与 #7 不同局面
……
线索：
· 11 次重复发生在裁剪之后，此前试过，且当时 WORKING.md 已 59 步没更新
· 最长一段 52 步只有 6 步出现新局面，期间同一区域同一种动作 14 次
· 4 次死亡都没有被任何规则或 predict 预见
· python 报错 7 次，其中 3 次是同一种
· 上一关写的 lib/route.py 本关没被调用
```

**过关时额外给出成功模式**：转折点在哪次决策；去掉没起作用的动作后的成功路线；哪些步是程序算出的、哪些可以由程序算出。
配套的问题改为“什么让它成功了？能否写成下一关可直接调用的程序或开局打法？”

**关内小复盘**：同一局面同一动作试到第 3 次，或同一原因（同一局面、同一致死动作）死第 2 次时给出。内容是最近 8 次决策的
压缩轨迹和线索，不提问。每关最多 2 次。

**裁剪前提醒**：保留部分超过上限的 85% 时给一行：“上下文即将裁剪，WORKING.md 上次更新在 N 步前。”每次裁剪前一次。

### 3.5 归因对照表

写在系统提示里，复盘时附简版。宿主只给线索，结论由 agent 下；一个问题可以归到多个部位。

| 部位 | 轨迹里的表现 | 宿主给的线索 | 改哪里 | 下一关看什么 |
|---|---|---|---|---|
| 记忆 | 裁剪后重做做过的事；试已排除的动作；已知规则没用上 | 裁剪后的重复；重复时 WORKING.md 多少步没更新；有规则预见死亡却仍然去做 | `WORKING.md` 的写法；`GUIDE.md` | 裁剪后重复；裁剪后到下一次有效动作的调用数 |
| 模型 | 预测错；死亡没预见；对物体或目标理解错 | `predict` 偏差；未预见的死亡；规则失败 | `model.py`、`claims/` | 预测准确率；未预见的死亡 |
| 方法 | 一直用同一种试法却没有新局面；不止损；没复用上一关；新关开局乱试 | 最长无新局面段；同区域同动作连续次数；上一关程序未被调用；新关前 20 步的新局面数 | `GUIDE.md` 打法部分 | 每关动作；无效重复；最长无新局面段 |
| 工具 | 反复手算同一件事；报错多；路线靠手打 | 报错次数与类型；只看不动的调用数；程序算出动作占比 | `lib/` | 报错；程序算出动作占比 |

### 3.6 复盘问题与核对

关卡复盘末尾的三个问题，不强制回答：

1. 这关卡在哪里？请指出决策编号。
2. 根因在你的哪一部分：记忆、模型、方法，还是工具？
3. 你改哪个文件？下一关看哪个数来判断有没有改好？

回答写进 `work/REVIEW.md`，建议格式：

```
## 第 2 关
问题：裁剪后重复已试动作（#23–#30）；52 步同一试法无进展（#8–#21）
归因：记忆 + 方法
改动：WORKING.md 增加“已排除”一节；GUIDE.md 增加“同一试法连续 3 批无新局面就换假设”
下一关看：裁剪后重复 = 0；最长无新局面 < 15
```

宿主不检查格式。下一次关卡复盘时，取 `REVIEW.md` 最后一节的“下一关看”一行，原文放在复盘第一行，并附上本关对应的实际值
（宿主能算出的数：裁剪后重复、最长无新局面、每关动作、无效重复、死亡、未预见死亡、预测准确率、程序算出占比、报错；
写了宿主算不出的指标时，只放原文和本关概况）。`REVIEW.md` 没有更新时，第一行写“上次复盘后无记录”。

### 3.7 暂不记录 agent 的想法

轨迹只用宿主能直接记录的内容，不截取 agent 回复中的想法和预期文字。好处是实现简单、不受 agent 写多写少影响；代价是
复盘时看不到当时依据的假设。agent 当时的回复若还在上下文里可以自己回看；已被裁剪时，只能依靠当时的 `WORKING.md`。

补回条件：第一轮运行中，agent 的复盘经常写出“不确定当时为什么这样做”，或归因与轨迹明显不符。

## 4. 转化路径

写一个文件就装上，出错原样回显，不验收、不审批。

| 想留下的东西 | 文件 | 约定 | 宿主怎么用 |
|---|---|---|---|
| 一条规则 | `work/claims/名字.py` | `check(transition) -> True/False/None`，文档字符串一句话说明规则 | 新写或修改后对已有转移回测一次，之后每个新转移执行，累计战绩 |
| 局面判断与预测 | `work/model.py` | 可选 `state_key(frame)`、`predict(frame, action) -> grid`（-1 表示不关心）、`is_fatal(frame, action)` | `state_key` 用于重复判断；`predict` 在动作前执行、动作后比较；`is_fatal` 为真时在动作结果里加一行，不拦截 |
| 程序 | `work/lib/名字.py` | 模块文档字符串第一行写用途 | 内核启动和文件修改后自动导入，以模块名直接可用；由其中代码发出的动作记为“程序算出” |
| 打法与经验 | `work/GUIDE.md` | 跨关的打法、规律、教训，上限约 4000 字符 | 新关开始、裁剪后放回上下文 |
| 当前进度 | `work/WORKING.md` | 本关当前假设、已排除的做法、下一步，上限约 2000 字符 | 裁剪后放回上下文 |
| 复盘记录 | `work/REVIEW.md` | §3.6 | 下一次复盘第一行 |

- 装载结果在下一次 python 输出末尾给一行：“已装上 claims/no_click_blue（回测 6 次适用，6 次成立）”或原样报错。
- `work/startup.py` 照旧在内核启动时运行。
- 超过上限的笔记按上限截断放回，并在一行里说明被截断。
- 复盘材料末尾固定一行写法提示：规则写 `claims/`，预测写 `model.py`，程序写 `lib/`，打法写 `GUIDE.md`，进度写 `WORKING.md`。

## 5. 能力暴露

### 5.1 能力清单

每项一行：名字、用途（取文档字符串或文件第一行）、战绩、来源（`REVIEW.md` 中第几关的记录提到了它，没有则空）。

```
你的能力（work/）：
- claims/no_click_blue：点蓝块会死｜适用 6，成立 6，失败 0｜来自第 1 关复盘
- lib/route.py：按已知规则算点击路线｜被调用 3 次，产出 14 个动作
- model.py predict｜最近 20 步对 17；未预见死亡 1
- claims/dig_under：40 次转移里从未适用
- GUIDE.md：更新于第 120 步｜WORKING.md：更新于第 180 步
```

战绩定义：

- 规则：适用、成立、失败次数；失败时显示最近一次失败的步数。
- `predict`：最近 20 个转移的准确数；本关未预见的死亡数。
- 程序：被调用次数（动作由其代码发出的批次数）、产出动作数。
- 笔记：最后修改的步数。

### 5.2 何时显示

- 完整清单：新关开始、上下文裁剪后、`work/` 下有文件改动后的那条状态消息。
- 平时：只在动作结果里显示本步触发的能力，例如“claims/x 失败”“本批 8 个动作由 lib/route.py 算出”。
- 清单只报事实，例如“从未适用”。保留、修改还是删除由 agent 决定，任何状态都不阻塞动作。

## 6. 上下文连续性

- `evict()` 实现真正的滞回：保存上一次切点，只有保留部分再次超过上限时才前移，一次退到目标量。
- 裁剪后，在保留部分最前面放回：`GUIDE.md`、`WORKING.md`、能力清单。
- 这一路径不依赖 `ARC_LAYERED_COMPACT_MARGIN`；原压缩摘要中的 `evolutionDigest` 由能力清单取代。

轻量校准中，同样的滞回使不计缓存的 token 降到约 1 千/动作（§1.1）。这是独立于自进化的成本修复，可以先单独落地。

## 7. 三个核心问题的闭环对照

| 问题 | 怎么被看见 | 归因到 | 转化成什么 | 下一关怎么检验 |
|---|---|---|---|---|
| 局部循环，缺少预测→验证→排除 | 每步重复回显；复盘中合并的“同一试法无新局面”段；关内小复盘 | 方法（试法不收敛）、模型（理解错）、记忆（排除过的又试） | GUIDE 中的换假设条件与排除做法；`state_key`；claims；自写守卫 | 最长无新局面段；无效重复 |
| 频繁裁剪，反复重建认知 | 复盘中的裁剪标记、裁剪后重复、当时 WORKING.md 的陈旧程度；裁剪前提醒 | 记忆 | WORKING.md 的写法与更新习惯；能复原状态的程序 | 裁剪后重复；裁剪后到下一次有效动作的调用数 |
| 缺验证闭环，规律提炼复用不足 | 未预见死亡、预测准确率、程序算出占比、上一关程序未被调用；过关时的成功模式 | 模型、工具、方法（复用） | `predict`、claims、`lib` 中的路线程序、GUIDE 中的开局打法 | 预测准确率；程序算出占比；每关动作 |

另外三点（预算语义、工具摩擦、终态自停）：关卡编号与剩余预算在状态行明确列出；报错计入复盘线索，归到工具；止损由 agent
写进 GUIDE，宿主在复盘中提供“本关动作与上一关对比”和“最长无新局面段”。

## 8. 对 ds 建议的取舍

采纳：能力进入决策通路；用实际战绩而不是文件数评价；评审不阻塞 RESET、失败不冻结；成本单独计量。
不采纳：独立进化循环（关卡边界就是天然整理时机）；通用注册表与七种接口（四类文件即可）；宿主判定晋升状态
（改为清单中的战绩事实）；离线回放评估器与主动探测调度（由 agent 的方法决定）；宿主按规则拒绝动作。

## 10. 运行前实验协议

- 目标证据层级：阶段 A/B 各自达到“全链路可达 + 自主采用”；全部完成后再做净收益对照。
- 比较器：当前 middle-layer（mel4d/mel4g 配置）、v3。纯 Pi 基线在净收益阶段加入。
- 配置：az / gpt-6-luna / low，本地离线 ARC，上下文上限 65536、目标 32768（与 mel4 系列一致）。游戏：su15（开发），
  第二款在确认本地可用后选定。
- 样本：开发阶段每阶段 1 次；净收益阶段每臂 3 次。
- 预算：墙钟 4 小时；动作预算按 bridge 默认（人类 5 倍）；provider 长时间无响应导致的终止单独记录，不计入结论。
- 主要指标：过关数；每关动作；死亡；无效重复（内部局面口径与整帧口径）；最长无新局面段；裁剪后重复；程序算出占比；
  预测准确率；token/动作（含与不含缓存）；`REVIEW.md` 条目数、其中指出决策编号与部位的条目数、核对数的变化。
- 负例：agent 从不写复盘或能力（清单为空时无害，表现接近当前配置）；`state_key` 写错（整帧口径并列）；规则从不适用
  （只显示事实）；笔记过长（截断并说明）；内核崩溃（`startup.py` 与 `lib` 自动导入恢复）；复盘被忽略（下一次复盘第一行说明）。
- 遥测：bridge-events、`harness/decisions.jsonl`、layered.jsonl、`work/` git 历史、`work/replay/`、`work/REVIEW.md`、provider usage。

## 11. 风险

- **复盘不被使用。** 没有冻结后，agent 可能跳过复盘。轻量校准显示它不会主动找证据，但当时没有任何证据摆在面前；
  本方案把证据直接放进状态消息，是否足够要看阶段 A 的运行。
- **归因质量。** 没有当时的想法，agent 可能归因错位；补回条件见 §3.7。
- **注入的 token。** 复盘每关一次、约 1500 token；清单只在特定时机完整显示；每步回显最多三行。
- **关卡间过拟合。** 上一关的规则在新关可能失效；新关的未预见死亡与规则失败会在第一时间回显。
- **归因粒度。** 效果只能归到关卡和能力组合，不宣称单项能力的效用。
