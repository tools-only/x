能力层运行视图

让无摩擦的能力缺口成为可见事实 —— 观测服务新增 A4 能力高度与真实零计数

现状：B2 的 agent 实际所见（评审入口观测，词汇只有摩擦/资源/轨迹）
[requests] reflect 36 (…) | execute 32 (…); cache_read 95k [loss] output_cut: request 13 … output cap 8192 [trace] decide receipts 10; self changes 2; reviews 15/14 （没有 [inventory]，没有 [recurrence]； skill/tool/memory 的 0 不出现在任何一行） → 13 次闭合判语（live-self.json:41446）： "Remaining candidates are unexposed/untried with no recorded friction, so no evidence- backed change is warranted."
设计后：同一次运行补上 A4 事实行（示意，数值取 B2 轨迹）
[inventory] prompt 1 (head 每请求; in_path 0/10 跨度) | skill 0 | tool 0 | memory 0 | subagent 0 (写入口拒绝: experiment authorizes one agent) | orchestration 3 步: build 52, review_gate 9, deliver 1 [recurrence] 10 个结果跨度; 共同调用: write 10/10 跨度 (计 86), edit 9/10 (41), office.render 10/10 (12); agent 组件在径: 0/10 跨度 → 徒手重复与空库存成为可引用的 ref； 判断仍然全部归 agent。

B2 交付 10/10，但全程唯一自改是一个参数（maxOutputTokens）。不是判断坏了——是输入里从来没有把"十次同样的手工"与"组件库为空"连起来的那条事实。

§0用户重定义（2026-11-15）

8192→32768 只是参数调整，不是进化。要求的自进化范式：agent 在执行任务过程中，根据自身运行视图（agent 自身 harness 视图 = 已加载 components 与 orchestration、运行状态、任务轨迹、harness 产物/中间交付件——用户给的参考轴），审视自身 harness 短板（orchestration 与五类组件：prompt、skill、tools、memory、subagent），经反射接口做 Erlang 式热修改自我进化。方向有二：产生新的组件/orchestration，与优化已有的组件/orchestration。

§1失败材料：B2 为何只产出参数级变更

  • B2 全程唯一自改 = policy.request.maxOutputTokens（参数）。组件清单从头到尾只有 host 播种的 1 个 prompt（ppt_baseline_guidance@v1）；live_agent_self.jsonl 13 条事件的 components 字段恒为该一项。skill/tool/memory/subagent 创建数 = 0，orchestration 结构变更 = 0。
  • 10 个同构 unit（同一财报、同一产出形态）全部由裸 write/edit/office 徒手完成，每 unit ≈4–6 请求重复相似的 HTML 生产动作；无一次沉淀为可复用组件。
  • 13 次 no-change 闭合是对的推理（见首屏引语）：agent 看到了候选占位（§2.2），用"曝光/使用/摩擦"词汇审它们，结论必然是"无证据"。

结论：这不是判断失败，是输入失败。

2.2能力信息现状：有什么、缺什么

  • 词汇表全部是摩擦/资源/轨迹。A1 重复·成本·拒绝·损失·停止，A2 模式连程·调用·工件写入，A3 结果谱系（in_path / available_not_in_path）。能力缺口若不产生摩擦——任务靠徒手照样成功——在这套词汇里结构性不可见。
  • 候选占位存在但词汇错位。reviewSelfView 对空类补 ${kind}_candidate 条目并带 define 示例（self_root.ts:1181-1185）——创建的操作入口一直在。但条目事实是回溯式使用谱系（exposure/use/effect/untried），对不存在的组件恒为 false，"无证据"永远成立。缺的是工作侧事实，不是候选侧入口。
  • 失真①计数造假。selfCategories 的 .size || 1（self_root.ts:1467）与 categories 把候选占位计入（:1190）：空类永远显示 1，从不显示 0。而系统提示承诺的是 "including zero-count categories"（self_root_system.md:13）——代码未兑现承诺。
  • 失真②空节从 head 消失。context 组装 .filter(Boolean)（ppt_demo_extension.ts:705）使空的 memory/skills 节整段消失；B2 的 agent 从未见过一行"memory: (无)"。
  • 失真③[idle] 只报已存在的工具。零个 tool 组件时整行不出现（self_observation.ts:227）。缺席不是可见事实。
  • orchestration 无执行谱系。当前步定义与 bindings 进 head（ppt_demo_extension.ts:703-704），但没有每步执行计数——"某步从未走过/一切挤在一个步里"不可见，"优化已有 orchestration"缺证据基础。
  • 非评审期能力信息为零。组件清单只在评审 JSON 深处；任务进行中（恰是重复劳动发生时）agent 看不到自己库存。

断裂在"评审入口的事实词汇 → agent 判断"。B2 已证明判断链本身是好的（引用事实 → 定向修改 → 声明效果 → 效果成立）。只改这一个主因：观测服务加能力高度（A4），库存计数真实化。不动触发器、不动判断归属、不加义务/配额/推荐。

§4设计：能力事实（A4）与真实库存

原则不变：服务只供事实——发生了什么、花了什么、路径里有什么/缺什么——不供原因、结论、建议；"你应该创建一个 skill"是禁句。判断与创建都归 agent。

4.1新增事实行（self_observation.ts，与 A1–A3 同渲染管道）

[inventory] —— harness 库存与消费绑定（用户轴 1：自身 harness 视图）

[inventory] prompt 1 (head 每请求; in_path 0/10 跨度) | skill 0 | tool 0 | memory 0 | subagent 0 (写入口拒绝: experiment authorizes one agent) | orchestration 3 步: build 执行 52, review_gate 9, deliver 1
  • 每类真实计数（0 就是 0）＋该类消费绑定的事实短语（进 head / 可调用 / 索引+拉取 / 拒绝——运行时属性，非建议）＋跨结果跨度的 in_path 使用计数与最近使用请求号。
  • orchestration：步数＋每步执行计数——由既有 request_record.pin.step 聚合（self_root.ts:1403,1416），无需新回执；"优化已有"方向的证据基础。

[recurrence] —— 跨结果跨度的重复劳动（用户轴 3：任务轨迹）

[recurrence] 10 个结果跨度; 共同调用: write 10/10 跨度 (计 86), edit 9/10 (41), office.render 10/10 (12); agent 组件在径: 0/10 跨度
  • 机械聚合 A3 既有的 per-span 序列与 in_path：各 span 共同出现的调用名及总量、含任一 agent 创建组件的 span 数。无相似度判断、无任务词汇——纯计数。
  • 这是把 B2 不可见的核心事实——"十次同样的手工，零次复用"——变成一行可引用的 ref。

4.2真实计数与缺席可见

  • 删除 selfCategories 的 || 1；categories 只计 active 组件，候选占位保留但标 candidate: true 且不计入。系统提示 "zero-count categories" 的承诺由代码兑现（提示仅把 observation 节的枚举词补上 inventory/recurrence，约一行，不加义务句）。
  • 非评审摘要行（observationHeads）追加库存段：components prompt 1/skill 0/tool 0/memory 0/subagent 0（≈45 字符/请求）——任务进行中即可见，不等评审。head 的空节 .filter(Boolean) 保持：不往任务 head 塞空段，缺席事实住在 self 视图行里，一处即可。

4.3与既有机制的衔接（零新机制）

  • 能力级变更声明效果时，M-C 的 agent 谓词可直接绑 A4 可比指标（如"后续跨度 write 调用数下降"、"组件在径跨度数上升"）——效果回流复用现有窗口/回执，无新通道。
  • A4 的 ref 可进 evidence_refs；"修改是否引用观测"沿用 M-A 的既有记录。

4.4每条新事实的闭环契约（no dangling artifacts）

产物入环点（未经请求）替代的工作下一步如何回馈退役
[inventory] 行review_frame.observation、reviewSelfView.observation、非评审摘要行agent 自翻 ledger/mirror 数库存与步执行引用进 evidence_refs 被记录；创建后计数即变EVO_A4=0
[recurrence] 行同上（评审两处；摘要行在跨度≥3 时带一段）agent 回看全部 span 序列对比组件入径后 "0/10" 即变；可作 M-C 谓词指标EVO_A4=0
真实零计数categories / 摘要行无（纠正既有事实的失真）创建即 0→1随 A4

新常驻负担：摘要行 +≈45–90 字符/请求；评审 observation 预算内 inventory+recurrence 约 200–400 字符（2400 预算不变，折叠规则沿用）。移除负担：无——B2 已把常驻义务清干净。

4.5不做什么（负例设计）

  • 不加评审触发器、创建配额、组件数奖励、"考虑创建 X"类文本；候选 define 示例维持现状。
  • 不把组件计数当任务回报：诚实的 no-change 闭合（引用了 recurrence/inventory 后判定不值得）仍是合法闭合。
  • 不做 [deposit]（工作区沉积未读事实）：ledger 今天不留读回执，机械推导不成立；列入开放项，避免本轮多因素。
  • 不动 subagent 授权（§6）。

§5可证伪命题与有界评估（B3）

项内容
窄命题同任务同模型同 caps、A4 开启的运行中，agent 至少 1 次能力级自改——kind∈{prompt, skill, tool, memory} 的 define/redefine，或 orchestration steps/decisions/transitions 结构变更（纯 policy 参数不计）——满足：自主发起、运行内被行使（新组件此后 in_path/被调用/入 head；orchestration 变更后该步实际执行）、evidence_refs 引用 A4 事实。
负例
（不判失败）		agent 引用 A4 后诚实判定 no-change（记录"视图可达、判断不同"，读闭合文本定性）；任务无重复结构则 recurrence 自然空。
证伪条件全程 0 次引用 A4 事实（事实未进判断 ⇒ 视图设计失败）；或能力级变更出现但从未被行使（悬空创建 ⇒ 消费路径或事实设计失败）；或成本相对 B2 显著恶化而任务结果不升。
比较器B2：68+1 请求 / 1.75M tokens / 10/10 units。开关 EVO_A4（=0 回 B2 行为）预留逐因子 arm。
预算发射前按惯例向用户声明（预计 B2 同量级；caps 镜像 600 请求 / 14400 s / 2 GiB；组件创建请求计入任务成本，不另设奖励）。
测量全部来自既有工件：能力级变更数与种类、A4 引用数、新组件后续 in_path 跨度数/调用数、recurrence 行前后值、请求与 tokens、units/deliver。

§6开放决定（用户定夺）

  1. subagent：视图将如实显示"0（写入口拒绝）"。是否解除 experimentLimits 的 subagent 拒绝并给它执行路径（run_agent 式，自然语言执行器提案待决）是独立授权，本稿不包含；不解除则五类中四类可进化，subagent 保持可见的拒绝事实。
  2. [deposit]（写后未读的工作区沉积）：需要新增读回执才能机械成立；是否列入下一轮。
  3. 摘要行常驻成本：+≈45–90 字符/请求是否接受（或仅评审期显示库存，非评审只在计数变化时显示）。
