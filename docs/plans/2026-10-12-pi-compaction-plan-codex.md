# Pi 0.87.0 compaction for thin ARC: probe-first plan

Date: 2026-10-12 (Asia/Shanghai). Author: Codex. Status: **design only; implementation requires approval**. This is the change record, not evidence of a compaction run.

## Problem and claim

Committed `--continuity session` reuses the in-process Pi session and projects the last N decisions into each request. It is **not key compaction**: older decisions disappear by count, reasoning is omitted from the ordinary projection, and the projection does not retain a Pi compaction summary. The runner still launches `--no-session`, so contrary to a possible reading of “session file reuse,” it does **not** persist a session across process restarts. It explicitly disables auto-compaction (`src/autoresearch_pi/arc_thin_e2e.py:645-686`; `demo/arc_thin_extension.ts:1493-1564`). The memory-mechanism review reports memory upkeep at 20–45% of output in ten real runs (`docs/reports/2026-10-12-memory-mechanism-review.md`); this motivates a capacity experiment, not an improvement claim.

**Narrow falsifiable claim.** For a long `session`-mode chain, native Pi compaction can turn relevant session evidence into a checkpoint that reaches a later ordinary ARC parent request, with the *current* complete observation intact, without another parent memory-maintenance step. A saved summary invisible to the next request, a refuted hypothesis retained as true, loss of a decisive failure, or net extra management/cost without task progress refutes the intended benefit. First diagnose reachability; only then change the broken boundary. The first move is a **compaction probe**, not a ledger-driven custom summarizer or wholesale context rewrite.

## Current ARC path and predicted break

`src/autoresearch_pi/arc_thin_e2e.py:645-686` selects `ARC_THIN_CONTINUITY=session`, starts local RPC Pi with `--no-session`, and sends `set_auto_compaction(enabled=False)`. Idle and length recoveries keep that in-process session (`:706-760`). `demo/arc_thin_extension.ts:1493-1564` selects earlier user/assistant/tool-result decisions, strips reasoning, shortens skill source and old tool receipts, and then appends the latest user prompt, full working set, and current image. Pi's canonical projection represents a saved compaction entry as a `compactionSummary` custom message (`dist/core/session-manager.js:184-201`); ARC's `historyMessages()` has no custom/summary case and uses earlier user messages as decision boundaries. **Source-level prediction, not runtime observation:** a manual compact may succeed, yet its summary may be missing from the next provider request. The probe must test this exact transition.

## Sequenced protocol

1. **Probe first, without product changes.** In an isolated probe run directory, use the actual local 0.87.0 coding-agent and a scripted provider that captures summary and ordinary requests. Feed several completed representative ARC decisions with tool receipts, an explicit hypothesis followed by a refutation, a >2,000-character receipt with its decisive counterexample near the end, a large reasoning block, and the current grid/image. Keep `--continuity session`, `--no-session`, and auto-compaction off. After settlement, send RPC `{type:compact}` (`PiKernel.send(compact)` or raw RPC); manual compaction works even with auto off (`dist/modes/rpc/rpc-mode.js:419-425`; `docs/rpc.md:397-446`). Observe `session_before_compact` preparation and branch *read-only* if necessary; do not return a custom compaction. Exercise nonsplit and split cut points, second compaction updating a prior summary, and failed/length summary. Script unique markers into a controlled completed summary; scripted textual quality is not real-model evidence. Probe-only fixture/script location and exact orchestration command are **TBD at implementation**; avoid runtime edits just to probe. Reuse `src/autoresearch_pi/pi_kernel.py:177-206` and the existing `run_arc_thin_continuity_smoke()` fixture as starting points, not as proof of compaction.
2. **Interpret by boundary.** Compare raw branch IDs/types, `buildSessionProjection()` messages, the serialized summarizer request, stored entry and `firstKeptEntryId`, extension `context` result, and *actual next ordinary provider transcript*. Classify (a) summary and critical evidence reach parent: no adaptation; (b) summary stored but dropped by ARC projection: adapt only delivery; (c) critical evidence not in summary input because of thinking load, prefix cutoff, or absent image/text receipt: adapt only the relevant input representation and re-probe. Include reasonable non-use (nothing eligible to compact, or evidence cannot be preserved safely). If a synthetic provider cannot exercise a branch, mark it unverified.
3. **Only if required, minimally adapt ARC input.** Keep it behind `--continuity session`; retain `rebuild` as comparator. Change one main factor, repeat the failed trace and negative cases, then consider enabling native auto-compaction. Do not add ledger summarization, another Agent, required parent fields, or new memory schema.
4. **Offline regressions after adaptation.** Run targeted Node projection tests (candidate command: `node --experimental-transform-types --test tests/arc_thin_self_harness.test.ts`; confirm existing runner flags), discover and run relevant Python ARC-thin tests (selection TBD), and existing scripted bridge/Pi/provider continuity smoke. Add/reuse a scripted compaction smoke checking **semantic next-request contents and later ARC action**, not only `status=completed`. Cover success, length/error, split, unanswered/aborted call, repeated compaction, restart if persistence changed, and unchanged `rebuild`. Save commands/exits/environment/artifacts. This proves functional behavior and scripted wiring only.
5. **Final, separately authorized real ARC gate.** The user will run real ARC tasks with **NO time and NO token caps**. Do not use the continuity document's old one-hour budget or invent another cap. The current runner has `experiment_timeout_seconds`, `max_reported_tokens`, decision/idle timeouts and stop logic; the exact safe uncapped invocation/configuration is **TBD** before this phase, without discarding necessary cancellation, permission or environment-integrity protection. Freeze source/dependencies/provider/model/thinking and choose comparable starting tasks and `rebuild`/uncompacted `session` comparator with the user. Record actual official ARC SDK/bridge/Pi identity and all outcomes and unknown provider cost. No fixture establishes this gate.

**Cheap probe budget and artifacts.** Aim for zero paid model calls using a scripted provider, one isolated session per cut-point case, and only a short local stall timeout/abort; these are **not final-run caps**. In a named probe run directory (TBD), save redacted RPC/events, `run-config.json`, preparation and branch-entry metadata, summary-input marker excerpts/hashes/lengths (no credentials or image bytes), actual next transcript and marker assertions, session-entry metadata, `context_budget.jsonl`, summary call count, wall time, result usage (`input/output/reasoning/cache/cost` when returned), `estimatedTokensAfter`, and errors. Pi's post-compact token estimate is heuristic. Separate parent, summary, and child calls (none expected here), including failed/unknown usage. `pi-events.jsonl` currently persists lifecycle events but not `compaction_start/end` (`src/autoresearch_pi/arc_thin_e2e.py:70-74`); capture those in the probe harness rather than claim they already appear.

**Risks and open questions.** Will the hook drop the checkpoint exactly as the source predicts? Does the existing smoke provider support summary calls, or need a probe-only fixture? Which split cut point is reachable in ARC's one-action-per-decision turns? How does the selected real provider bill/reason on summaries, and does registered-provider routing work? Does prefix clipping hide late counterevidence? How do aborted/length turns and completed action receipts interact? Does a level change stale a checkpoint? Is durable restart recovery desired, or only in-process continuity? The probe answers wiring and input; real runs answer semantic quality and economics. If nothing eligible is old enough or no capacity pressure occurs, **do not force compaction to raise invocation counts**.

**Lifecycle and burden.** Runner/operator identifies capacity pressure; Pi prepares the canonical candidate; a scripted or real summarizer invests a call; Pi assembles/persists the checkpoint; ARC projection must deliver it; the authorized parent decides semantic use or justified non-use; task results and full costs drive retain/revise/retire. Pi owns mechanical preparation and persistence, ARC adapter delivery, parent/model game meaning. No new standing prompt, worker, schema field, mandatory review or parent action gate is proposed. Leave auto off/retire an optional adaptation if evidence is lost, cost dominates, or the provider path fails; preserve raw artifacts and unknown costs. Change one main factor and re-probe rather than stacking speculative fixes.
