# Single PPT production demo on agent-native-program-loop

## Opportunity and claim

User wants one complete real PPT deliverable and the harness evolved during its production. Base is the current remote `codex/agent-native-program-loop`, reused in clean adapt-config worktree. Its existing Binder/NativeRuntime provide named-program creation, versioning and fresh WASI execution; ARC actions/phase evidence cannot represent editable office artifacts directly.

Narrow falsifiable claim: a real parent can develop/revise a method while interpreting/building the deck, use that version on later work, and deliver editable PowerPoint objects plus active harness sources. Saved literal slide data alone is not a reusable method. No statistical improvement, general autonomy, five-category closure or causal cost benefit is claimed.

## Design and burden

The PPT extension reuses the actual branch Workspace, Binder, validatePythonComponent and NativeRuntime saveProgram/runProgram. It adds a small scene-local TASK/ADAPT owner instead of importing ARC trajectory counters. Parent selects meaningful work batches via checkpoint; no per-slide turn or forced review schedule. TASK itself can modify methods. ADAPT is an optional independent read-only task-state window, including before production; it can revise methods and return unchanged. No critic/refiner worker or developer-authored narrative recipe.

Programs read source text and create/transform a generic editable object scene. The host maps text/shapes/charts/tables/images to python-pptx, opens the saved PPTX with actual Microsoft PowerPoint 16 COM, exports PDF/PNG, and reports geometry and text-height facts. No host library imports or arbitrary host filesystem access are added to WASI. Binary exports stay outside the text Workspace snapshot. Current deck/feedback/memory plus actual conversation enter TASK/ADAPT; method catalog and selected prompt/skill versions enter at batch boundary. Saving and binding reuse the existing runtime, not reuse tickets. Agent chooses suitability and retention; runtime does mechanical compilation/export/packaging.

Existing files remain unmodified; additions exceed 300 lines because native artifact export, actual rendering, provider runner, integration and evidence are all required. This is one vertical slice, not a generalized platform. No new project gates or AGENTS rules. Current artifact changes do not expire saved methods.

## Correction after the first run: self-harness is the demo objective

The first run completed a deck, but it did not meet the intended demo claim. Its only retained components were two tools; the final deck repeated a text-card layout and had no native charts or tables. The single layout tool addressed renderer overflow, not an evolving production approach across narrative, visual design, data communication, and evidence fidelity. This is an observed miss, not evidence that tools are the only component type the Agent would choose: the extension did not expose subagent creation/consultation and did not show the full active component index in the task head. Also, the benchmark generation instructions contain unrelated space-exploration wording. The run therefore cannot demonstrate high-quality financial-slide generation or broad self-harness construction.

### Revised narrow claim and bounded next run

**Claim:** with the branch's task-local component pool made fully available, an Agent can construct and adapt reusable components in response to recurring production needs, apply those components to later work in at least two distinct presentation dimensions, and deliver a materially stronger, editable financial presentation. The dimensions are narrative/content organization, visual language/layout, quantitative storytelling, and source/number fidelity. This guided production demo does not establish ordinary autonomous opportunity recognition, generality, or causal net benefit.

**Opportunity and burden:** the current adapter's main gap is that the PPT task surface hid part of the branch's self-harness pool and the task brief contradicted the source domain. That made the core branch capability hard to use and gave the Agent poor production guidance. The target burden is a developer having to pre-author the earnings deck methods and repeatedly translate the same design decisions across slides.

**Single main factor:** enable the existing prompt/skill/memory/tool/subagent pool at the PPT adapter boundary and provide a coherent financial-production brief that asks for selective in-process method construction and semantic reuse. No critic worker, forced component checklist, per-slide review loop, or new harness subsystem is added.

**Adoption evidence:** preserve component author/version records, batch exposure, actual calls/consult results, and later slide changes/outputs. A created or exposed component is not adoption. Components count toward the claim only when their specific reusable method affects later production; at least two different presentation dimensions must have this evidence. Record opportunities and justified non-use. Keep the story, design, numeric, and source-fidelity dimensions distinct when reporting.

**Artifact acceptance:** 15 editable slides; exact source-grounded financial values and non-GAAP labels; release citations on data slides; multiple appropriate native editable charts/diagrams rather than repeated cards; legible, consistent typography and visual rhythm; zero material overflow/out-of-canvas renderer warnings. A human visual inspection is required. The PresentBench evaluator remains separate and will not be claimed as a score because the source generation instructions are inconsistent with this case; any later benchmark result is explicitly non-comparable unless that issue is resolved.

**Negative cases:** the claim fails if the Agent only creates a final code dump or one-off overflow fixer; if components do not become available and affect later pages; if the deck remains a repeated text-card layout or misses key numerical/source fidelity; or if content errors/visual defects remain after the completed task. One run is exploratory evidence only; no causal net-benefit claim.

**Budget boundary:** the earlier authorization covered the prior 2-hour run, which has ended. Code, bundled task resources, and no-provider setup can be completed now. A new official OpenAI provider run needs a new explicit budget/deadline authorization before starting; proposed cap must be set in advance. No AZ retry is planned because the account returned repeated `Arrearage` errors.
