# pi-jev 核心功能分析

## 核心定位

pi-jev 的核心思路，是给 Pi 增加一个“快速决策层”：让 Jev 负责选择、分类和评分，让主模型继续负责复杂推理与执行。最值得关注的是能力按需发现、结构化判断，以及考虑缓存成本的模型选择。

## 1. 工具与技能按需发现

`jev_find_tools` 从已经注册、尚未激活的工具中选择合适工具；`jev_find_skill` 推荐相关技能，随后由主模型读取 `SKILL.md`。

实现采用两阶段筛选：先用本地关键词生成候选，再让 Jev 判断每个候选是否适用，默认阈值是 **0.65**。显式工具发现最多提交 10 个候选，技能发现最多提交 12 个候选。技能判断还强调“任务活动、产品和框架必须匹配”，避免仅因话题相似就推荐技能。

价值：适合工具和技能很多的环境，减少主模型扫描整个能力目录的负担，并按需激活工具、推荐技能。

实际边界：

- 候选筛选主要识别英文和数字。纯中文查询可能退化为取目录前几个候选，后续语义判断无法找回遗漏能力。
- 工具激活是追加式的，没有自动淘汰机制，长期会话中工具集合仍可能膨胀。
- 技能发现提供推荐，不等于技能已经被读取或正确应用。
- Jev 未配置或请求失败时，工具路由不自动激活未经判断的工具，关键词候选的概率标为零。

## 2. 结构化判断

`jev_evaluate` 提供三类判断：

| 类型 | 返回内容 | 适合用途 |
| --- | --- | --- |
| `choice` | 预设类别 | 区分 bug、功能、文档任务 |
| `noul` | 是非命题的概率 | 判断工具是否适用、结果是否满足要求 |
| `score` | 按预设标准评分 | 对候选方案或结果排序 |

多个问题可以合并到一次请求中。`/jev test <prompt>` 则由当前主模型设计问题结构，再交给 Jev 判断，因此动态问题设计本身仍需要主模型参与。

价值：减少主模型为简单分类生成长篇文字，再由程序解析的成本。决策结果可以直接作为工作流分支条件。

实际边界：类型明确只解决接口稳定性；返回一个概率，并不意味着该概率已经在你的任务分布上得到校准。问题定义、输入证据和判断质量仍需要验证。


## 3. 模型选择与推理强度调节

`/jev auto-model on` 根据任务选择快速、均衡、推理、长上下文、视觉或 URL 类型的模型。它先比较能力匹配度，再在能力相近的候选中比较成本，特别考虑换模型后重新处理上下文前缀的代价。

成本估算使用模型价格元数据和上下文 token 数，比较切换模型的输入及缓存写入成本与继续使用当前模型的缓存读取成本。配置 Jev 后，还会询问“这次切换是否能改善答案”，切换成本越高，代码要求的概率阈值越高。

`/jev thinking on` 保持模型不变，只调整推理等级；这部分采用本地规则，不调用 Jev。实现会依据 Pi 支持的等级进行约束，并跳过它认为改变等级会破坏缓存的预算式 Anthropic thinking 情况。

价值判断：考虑缓存成本是很实用的设计。长会话里，频繁切换到单价更低的模型未必更省钱；保持模型并调节推理强度是另一个可比较的选项。

实际边界：

- 任务分类依赖英文正则，对中文任务的识别需要单独验证。
- 能力评分主要依据 reasoning 标记、上下文窗口和输入模态等模型元数据，不能视为真实任务质量排名。
- 缓存成本属于估算，并非对实际命中和账单的直接测量。
- Jev 未配置或判断失败时，模型路由仍可能依据本地候选计划切换；这与工具发现失败后不激活工具的策略不同。

## 4. 上下文压缩

开启 `/jev compact on` 后，扩展在 Pi 压缩事件中判断哪些历史记录值得保留，再拼成自定义摘要。未配置或发生异常时，交回 Pi 原生压缩。扩展返回的压缩记录沿用 Pi 的 `firstKeptEntryId` 边界。

价值：尝试将“保留哪些历史证据”的选择交给判断模型，以减少无关历史，同时保留继续任务所需的信息。

这里需要特别谨慎：0.7.0 只处理 `branchEntries` 的前 **24 条**，每条序列化后最多保留 **900 字符**，保留阈值为 **0.55**。候选判断使用字符串是否包含 `tool`、`bash` 或 `assistant`，因此助手消息也可能被筛掉；其他记录虽然直接保留，同样经过字符截取。

它实际更接近“截取记录并选择保留”，尚不足以支持文档中完整保留用户与助手意图的强承诺。对长任务，后面的关键证据和长输出中的细节可能无法进入摘要。保留压缩边界，也不能单独证明后续模型的认知连续性。


## 5. 工具调用检查与失败恢复

`/jev tool-guard on` 会在调用前检查参数是否疑似编造，概率达到 **0.85** 时阻止执行。工具失败后，再分类原因，并对路径不存在、语法错误等情况补充固定提示。

价值：可以作为额外的异常筛查，并帮助主模型在失败后调整重试方法。

实际边界：

- 调用前只提供工具名和参数，没有读取实际文件系统或完整工具规范，所以无法可靠证明路径存在、参数合法。
- 错误恢复提供的是分类与固定提示，并非自动修复。
- 评估异常时会放行，属于 fail-open。
- 每次受检查的调用都会增加请求开销，错误分类还可能再增加一次请求；需要比较减少失败的收益和额外成本。


## 6. 子代理编排与结果门控

`/jev agents <task>` 判断任务类型，再选择固定流程：

| 任务类型 | 工作流 |
| --- | --- |
| 开发 | `scout → worker → reviewer` |
| 研究 | 并行 `scout + researcher`，随后由 `worker` 汇总 |
| 审查 | 并行 `reviewer + evidence-auditor` |
| 通用 | `worker → reviewer` |

实际执行依赖 `pi-subagents` 及相应代理定义，通过事件 RPC 提交异步工作流。这里的编排主要是选择预设模板，而不是动态设计任意代理结构。

工作流中的 `agent: "jev"` 直接返回结构化判断，避免为简单分类启动完整工作代理。这种轻量判断节点值得借鉴。

`jev-gate` 可以读取 diff、文件或标准输入，用自然语言标准判断是否通过，默认阈值为 **0.70**。通常通过退出码表示通过、拒绝或错误，也提供 `--fail-open` 选项。

价值判断：轻量判断节点有明确用途；固定多代理流程则需要核算父子总成本、延迟和管理往返。Gate 适合补充语义审查，但读取 diff 并不能证明测试通过。本文没有证据表明这些编排已经带来净收益。


## 使用判断与证据状态

优先试用结构化判断、工具/技能发现，以及保持模型不变的推理强度调节。自动模式默认关闭；开启后，工具、技能和模型切换判断可以合并请求。压缩、Tool Guard 和自动多代理编排则应先在真实中文任务、长会话和失败场景中验证，再决定是否常驻启用。

云端 Jev 使用 TypeSafe API 配置；也可以通过 `PI_JEV_BASE_URL` 或 `TYPESAFE_BASE_URL` 指向兼容端点。本文未使用任何真实 provider，分析环境为 Windows/PowerShell 下读取公开文档和发布包源码。

| 证据层级 | 本文状态 |
| --- | --- |
| 功能正确性 | 已静态核对实现路径，未运行验证 |
| 全链路可达 | 未验证 Pi、Jev 与 pi-subagents 的实际集成 |
| 自主采用 | 未验证真实主模型是否正确发现、读取并使用能力 |
| 净收益 | 未开展任务质量、父子总成本、延迟和管理轮次对照 |
