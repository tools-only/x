# Research orchestration

Created using Anthropic skill-creator's intent/draft/contrast-evaluation workflow.
This method guides main's decisions; auto_research and its runtime still own
sessions, bounded continuation, reports and delivery. It grants no new permissions.

## Choose a research object

Start with the persistent problem, not the latest trajectory window. Identify the
representation, explanation, algorithm, planning/exploration strategy, context
configuration or component interaction that could be improved. Mechanism research
is legitimate when it helps explain behavior; do not replace necessary evidence
collection with an abstract slogan. Observations are cases, not the research goal.

Inspect the existing agenda and prior reports before opening a duplicate line.
Either provide a bounded question and relevant exact evidence, or allocate an open
research turn so the child selects from the durable agenda/history. A broader goal
needs a reachable milestone; it need not immediately change the next action.

## Decide whether and how to allocate

Compare likely information/capability value with model cost, latency and scarce
environment actions. Continue direct execution if the answer is already known or
research has no reachable test. Defer when missing evidence is the actual blocker;
record what would make research worthwhile. Counts and empty component slots are
reminders to inspect, not reasons to generate a child or component.

Use blocking mode for a decision that genuinely needs a result now; use non_blocking
for a separable method/representation question while main can safely progress.
Reuse a research_session/research_line when the question continues. Avoid launching
one research child per component by default.

## Construct an informative workset

State the problem, competing hypotheses/methods, available evidence, constraints,
criterion, stopping condition and next discriminating test. Choose raw evidence
instead of parent conclusions when an independent view matters. Explain missing
access. Maintain problem/alternatives/next test in the agenda or checkpoint so
continuation does not become another recap.

Ask for a method when appropriate: applicability, inputs, invariant vs variable
conditions, steps/decisions, outputs, uncertainty, failure boundaries and a new
case to test. A method-only result, refutation, null result or unresolved question
is valid. There is no skill/tool/subagent production quota.

## Consume and feed back

Recheck a returning report against current task/episode/level/state. A late map or
probe proposal may be obsolete while its method still has value. Do not copy a
stale action suggestion into task_prompt. Separate observation, inference and
capability candidate; use the relevant creator before publication. Main chooses
adoption and exact-version assembly; report completion alone changes neither.

For requested experiments, inspect prerequisites, alternative predictions, cost
and stop conditions. Main alone decides and executes each real action. Return new
exact evidence to the continuing line. There is no environment rollback, child
action lease or private evaluator access.

After actual use, return inputs, outputs, failures, relevant alternatives and cost.
Distinguish created/exposed/read from applied and from beneficial. Compare new cases
where possible; agreement or repeated reports cannot increase evidence confidence.
Stop, defer or redirect when the criterion is met, the budget is exhausted, access
is insufficient or continued work adds no information. Preserve the unresolved
question and reactivation condition without manufacturing a success.
