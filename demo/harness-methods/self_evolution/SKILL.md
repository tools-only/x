# Ongoing capability development during the presentation task

Keep developing your capability and working system throughout this task so you can do the presentation better now and in later work. This includes the presentation itself and the ways you understand the brief, plan, produce, inspect, coordinate, and learn from the work. The task target remains the requested presentation under its audience, factual, format, and delivery constraints.

The scope is broad: proactively design, create, adjust, or replace your working system's organizational architecture, collaboration relationships, control flows, and operating mechanisms, including its modules, relations, overall organization, and mechanisms that support further evolution. The existing architecture and process are adjustable starting points, not templates to preserve. Create, revise, combine, simplify, or remove prompts, skills, memory, programs/tools, roles, and their organization; improve working methods and higher-level strategies; and consider architecture, runtime, or process changes when a real path is exposed and authorized. Opportunities may come from a success worth generalizing, an anticipated need, analysis, a failure, a newly recognized need, or a promising strategy idea. Do not wait for repeated failures to justify useful capability development.

You decide when to discover or explore, what starting point and method fit, whether to work within the ongoing task or investigate independently, how to implement, and when to try, continue, revise, or abandon an approach. No fixed entry point, preset sequence, cadence, candidate or turn count, particular component, reviewer, rubric, or report is required. Still distinguish the stages: an intended change must actually take effect; it must then be used in later work; and evidence must show that capability or the presentation improved. A saved component, successful tool call, attractive render, or agreement between reviewers does not by itself establish those later stages. If context, evidence, available authority, or remaining effort does not support a useful next action, explain the limit or uncertainty and return a useful direction to the caller.

You choose whether to use `adapt`, when to use it, and what context and exact workspace refs to supply. Make that context useful for the question at hand: it may include the task goal and constraints, current stage, concrete observations or artifacts, what you are uncertain about, and what you want investigated. There is no required schema or sequence. ADAPT sees only your supplied context and refs plus its own core instruction and any `adapt_method` skill body captured at invocation start. It does not see this task's history, task prompt, or active prompts. Workspace references should be exact paths that exist in the workspace; include the actual evidence needed, since ADAPT cannot infer omitted files or hidden runtime/provider logs. It uses the same model and shared task budget. Intermediate ADAPT dialogue stays private to that turn; its final answer returns to you when the loop receives a final response without tool calls. There is no separate exit tool. Tool errors are returned to ADAPT as tool results so it can interpret them and continue or stop.

## What can change, and what cannot

The existing component and workspace tools can author or revise prompts, skills, memory, subagent roles, and named Python programs; edit ordinary workspace files; run or retire programs; use task-local agents; inspect evidence; and render or inspect presentation output. You can combine, simplify, or remove these capabilities and change how you organize and use them. Higher-level methods and strategies can be changed through these components and choices. Architecture/runtime/process design is part of the broader capability-development scope, but the current PPT workspace does not expose arbitrary host-source editing or permission changes: describe or recommend such a design when useful, and implement it only through a separately exposed, authorized path. Do not imply that a design note has changed the running host. These are options to judge, not a prescribed checklist.

The immutable host contract, extension implementation, ADAPT core prompt, permission system, task model loop, and shared budget handling are not task-local editable harness components. ADAPT is excluded from its own tool list and cannot recursively call itself. The optional `adapt_method` is a skill body read at the beginning of each ADAPT invocation. Editing it during a call does not change the already captured method or core prompt in that call; the next invocation reads the latest Binder version. If no such skill exists, the core ADAPT instruction still runs.

Tools describe what the host permits, not what should be done. In particular, the ADAPT tool set is derived from task tools with `adapt` removed. It includes `office`, whose `deliver` operation may be callable; do not assume the host blocks it. The independent turn has no task history, so a delivery action could be inappropriate without the caller's task context. The native runtime's `consult` tool is not included in the ADAPT tool set. Direct file tools and existing component tools may still expose meaningful effects; inspect their exact descriptions and use judgment.

## Discover and change components

Use `ls` and `read` to inspect exact workspace paths. `grep` searches text in workspace files. The task prompt's Harness index lists active component paths, versions, descriptions, and use counts; counts do not establish quality. `read_component({name})` returns a saved component's current source and version, where applicable.

`self_component({kind,name,content,description?,tools?,write_scope?})` creates or revises a task-local component. `kind` is `prompt`, `skill`, `memory`, or `subagent`; `name` is a lowercase identifier using letters, digits, and underscores. Supply the complete desired content. Prompt content is saved active. Skill content is stored as `skills/<name>/SKILL.md` with generated frontmatter; memory goes under `notes/memory/<name>.md`; a subagent role goes under `agents/<name>.md`. For a subagent, `tools` sets its allowed tools and `write_scope` narrows any write/edit access. The tool returns a save receipt; later assembly/use is handled by the existing Binder and runtime.

Example skill authoring call:

```json
{"kind":"skill","name":"claim_checks","description":"Check whether slide claims match source meaning","content":"For each material claim, trace the exact source passage and compare subject, label, unit, period, and caveat. Look for a counterexample that would make a plausible but wrong claim pass. Report unresolved mappings instead of guessing."}
```

The `adapt_method` name is available for a reusable method guiding future ADAPT calls. It is not mandatory. When revising it, write usable instructions grounded in the actual task and evidence, and remember the change applies to later ADAPT calls only. The core prompt remains in force.

## Programs and task-local roles

`save_program({name,description,tags?,body?,source_path?,expected_version?})` creates or revises a named Python program. Supply exactly one of `body` or `source_path`; long source can be drafted with `write`/`edit`, then saved by path. Programs run fresh in WASI with `state`, `args`, and `env`; use Python standard library and workspace files, not host packages or arbitrary host filesystem access. `run_program({name,args?,version?,readonly?})` executes an active or selected version against current workspace state. `readonly=true` refuses workspace writes and `env.agent`/`env.render`, but does not create a historical workspace snapshot. A normal run can write artifacts and can call `env.agent(...)` or `env.render(...)` according to its code and runtime access.

`edit_program` revises a named program through its patch interface; inspect the current tool schema/description for its exact arguments. `retire_program({name,version})` removes an active program from future use while retaining source under `tools_off/` and preserving history. `list_programs({query?})` searches active program descriptions and tags. `run_agent({agent,task,uses?,refs?,save_as?,independent?})` runs a saved role in a fresh context with only permitted tools and declared scope; judge its answer and files for relevance. ADAPT itself cannot call `consult`; `run_agent` is the available task-local delegation entry.

## Explore and inspect presentation evidence

`explore({candidates:[{instruction,refs?}]})` runs the Agent-chosen candidate set sequentially in independent, read-only contexts. Each candidate gets its own instruction and explicit refs, not task history or active prompts, and cannot use tools or modify files. It returns each raw answer or failure separately. One sample does not prove candidate diversity or correctness. The candidate count, use of this tool, and any follow-up are your decisions.

`office({op:"render",source_path?})` renders the canonical HTML/JSON or a selected candidate and returns a receipt/contact sheet. `office({op:"look",revision,pages?})` displays selected rendered slides. Rendered evidence and source are under `results/renders/`; `env.render()` may also return evidence paths from a program. `office({op:"recover",revision,destination})` copies a revision snapshot to a new directory without replacing current work. `office({op:"deliver"})` may be callable from ADAPT; the host does not turn availability into a requirement or recommendation. Use it only if caller context and task authorization make that action appropriate. The ADAPT tool list excludes `adapt` and does not include native `consult`.

## Judge the value of a change

When a system change seems useful, state what observed failure or opportunity it addresses and what later behavior would be different if the idea is right. Prefer a check that could expose a false positive or omission, not only confirm the method's expectation. Where practical, compare against the prior method or a plausible counterexample using the same task evidence. Separate what the tools actually returned from your inference. Consider the cost of writing, validating, maintaining, and using the change against its likely reuse; no fixed scorecard or report is required. A later real use that changes a decision or improves the deliverable is stronger evidence than saving, reading, or praising the component. If no later use or meaningful comparison is available, say so and leave the result unverified rather than claiming improvement.

The parent Agent decides how to use your returned findings, whether to change anything, and when to return to presentation work. This manual is on demand; it does not prescribe a mandatory workflow.
