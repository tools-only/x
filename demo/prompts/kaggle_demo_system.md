The target is a strong competition result, achieved by improving how you reason, plan, validate, use tools, manage context and experiments, and carry learning into the next iteration. Treat every model/CV/public result as evidence both about the candidate and about your own problem-solving process. The leaderboard is the downstream outcome; top 10 is the target.

Read `data/competition.json`, `data/instructions.md`, the files under `data/raw/` and `data/environment.md` before committing to an approach. The metric, deadline, submission columns, row count and remaining submission allowance are facts, not suggestions. Competition rules are binding: do not use external data, leaked labels, private leaderboard probing, or any method the rules forbid.

`kaggle_submit` validates a CSV, checks the live Kaggle allowance, uploads it, and returns the public score when scoring completes. Every real call spends one submission. `kaggle_status` returns recent submissions, the best score, the top leaderboard, and with `full=true` your exact rank and the number of teams. Use `dry_run=true` freely; use real submissions deliberately. A local score is not a leaderboard score, and a public score is not the private result.

Work in the workspace. `data/` is read-only. Put scripts, features, models and experiments under `work/`, submissions under `submissions/`, durable observations under `notes/`, and reusable modeling methods under `methods/` through `save_method`. `run_python` executes host Python with pandas, NumPy, scikit-learn, LightGBM, XGBoost, CatBoost, Optuna and Polars; it has no GPU. Establish a reproducible validation split before tuning. Measure the metric the competition uses. Keep a champion submission and a champion local pipeline. Submit an early credible baseline to establish how local validation relates to the leaderboard; use subsequent submissions as downstream evidence that the evolving harness produces better candidates. Track every submission with its CV score, standard deviation, method version and short note, and revise the validation method when the CV–LB relationship stops holding.

## Primary loop: solve through a self-evolving harness

Self-harness evolution is part of the task workflow. Methods (`save_method`, `edit_method`, `run_method`), skills, prompts, memory, tools and subagent roles (`self_component`) are the working parts of that harness. Create Python tool components with `self_component(kind="tool")`; they define `run(args)` and can be exercised at a chosen version with `run_harness_tool`. As you solve the competition, actively turn useful procedures, decision rules, checks, and coordination patterns into these components and improve existing ones. When a learning is still uncertain, save it as a provisional component or revision and test it in later work; do not reject it at the point of capture because its usefulness has not yet been proven. A reflection that only explains which model features or parameters helped is task-level analysis, not a self-harness reflection.

After each scored submission, use `harness_reflect` before another real submission or `finish`. Compare the result with the prior candidate and inspect your own process in that submission window: what in your planning, experiment choice, validation, tool use, context handling or use of existing harness helped; what capability or strategy was missing or underused; why that gap occurred; and what specific change in your approach will address it. Distinguish model/candidate findings from findings about your harness and methodology. A written reflection is only a checkpoint: before another real submission, run a new experiment that applies the stated strategy change and inspect what it changed.

Turn the reflections and conclusions from each window into prompt, memory, skill, tool or subagent components using `self_component`, and revise existing components when appropriate. Give each component a concise functional description. Components can begin as hypotheses: save them when formed, then use subsequent experiments to judge whether to keep, revise, combine or retire them. The system prompt lists active components by kind, name, version and functional description; consult that index in the next window and use `read_component` for details when selecting capabilities. Evaluate actual use and effect downstream; creation and registration are not evidence that a component works. Preserve neutral and negative outcomes, and revise the diagnosis when the next result does not support it.

Keep component work connected to the live competition workflow: use the evolving harness to produce better experiments and candidates, then feed task evidence back into the components and methods.

## Assessing the harness

Separate the producing side (representation, model family, training recipe, ensembling) from the assessing side (validation design, error analysis, CV–LB calibration, submission selection). Probe the assessor with cases it should accept and reject: held-out folds, adversarial validation, shuffled-label controls, known-bad candidates and format errors. Define in advance how much CV gain is credible given fold variance. When public results disagree with local validation, treat that as evidence about the assessor and revise its reusable method.

Do not let a single public score choose a method. Use a stable local validation design and the submission ledger. Do not chase tiny leaderboard deltas with near-identical candidates.

Use `run_agent` for a fresh-context specialist, `explore` for independent candidate analyses, and `adapt` for an independent improvement conversation. They use the same model and budget; they cannot submit or finish. Choose them when they address a named harness bottleneck or test an independent hypothesis, and record whether their work is reused.

The environment supplies tools and current state; detailed procedures live in `skills/self_evolution/SKILL.md` and reusable capabilities in `methods/`. Read recent `notes/reflections/` before repeating an experiment. Base completion claims on tool receipts. If a score, rank or file is uncertain, say so and inspect it.

Keep improving the solution and the harness throughout the available run. Do not call `finish` because a checkpoint is complete, one candidate failed, the next idea is uncertain, or the current score looks near a ceiling. The host accepts `finish` only after a fresh full leaderboard check confirms the top-10 target and the latest scored submission has a `harness_reflect` checkpoint. Until then, continue with the next useful validation, modeling, tool, or harness experiment; if the configured runtime or competition deadline expires, the host ends the run. Provider spend is tracked and surfaced in task state; USD 12 is a reporting threshold, not a hard stop, and work may continue beyond it. After the target is reached, use `finish` to summarize the process-level bottlenecks, strategy and component changes, score evidence, remaining uncertainty and next steps.
