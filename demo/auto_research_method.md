# Auto-Research method

Use research when it helps resolve an uncertainty; direct execution is also valid.
You choose the questions, evidence, depth, iteration, nesting, revisiting and stopping
conditions for this task. No research stages or harness changes are mandatory.

Treat available capabilities and their documented limits as resources, not research
objectives. Findings may support ordinary actions, further exploration, a change in
execution guidance, or no change. Keep the task goal and boundaries unchanged.
A finding is any provisional conclusion that can change a later choice: a task-local
pattern, a more informative way to explore a local uncertainty, or a reason to change
an execution condition. It need not prescribe the final task answer. It may instead
state which discriminating observation to obtain next and what evidence would revise
the current interpretation. When later evidence changes that choice, update the same
finding so subsequent task execution sees the revised conclusion.
A successful direct tool result may be useful evidence when it establishes a
lower-risk route for several remaining actions; findings are not limited to failures.
Likewise, a repeated failure is worth recording only when it changes a later decision;
uninformative errors and routine successes should not become a work log.
When several similar actions remain, you may compare a disclosed capability's
expected reduction in calls, errors, or context with its extra research/model step;
record and change it only if that tradeoff is material, otherwise continue directly.

Keep research proportional to the decision. If a required task observation already
supplies enough evidence, prefer one concise `action=record` with optional
`continue_with` when that operation is exposed; do not open a prospective goal merely
to satisfy a form. When the current research tool supports an open goal, use it only
when evidence still has to be gathered, then update the same goal rather than creating
duplicates. When a pending effect assessment answers the declared reconsider
condition, absorb it in one update or resolution. Do not spend a whole
model response restating settled task contracts or deliberating without either a
concrete task action, a bounded research-resource change, or a final answer.
For a direct outcome-derived record, the cited observation, concise evidence and
later execution decision are sufficient; question and uncertainty may use the tool's
neutral defaults. When `continue_with` already states that execution decision, do not
repeat it in a separate field. Set remaining_uses to zero when a supported finding no
longer needs to remain visible.

When useful, leave brief working notes in current-task resources: what is uncertain,
what evidence could distinguish explanations, what was observed, and what remains
unknown. These are optional prompts for thinking, not a required form or sequence.
Connect research back to execution: a current finding should identify the later task
choice it changes, the next useful observation, or the execution condition it informs.
Routine action narration and observations that change no later choice need no finding.
If adjusting execution guidance, record the supporting observations and expected
effect; later distinguish observed consequences from expected benefits. A successful
operation alone does not demonstrate improvement.

Execution outcomes update current-task resources, never this method. Notes and
adaptations are not inherited by independent tasks. Tool/model steps are not, by
themselves, research iterations or evidence of an agent-designed research loop.
